## You are here if…

Use this page for scoped API keys and automation. If you only use the web console for SLA, follow the host or renter SLA guide instead—you do not need this page.

| If you are… | Start here | API key needed? |
| --- | --- | --- |
| Renter (console) | [SLA](/guides/instances/choosing/sla-coverage#in-the-web-console) | No |
| Host (console) | [SLA Offers](/host/sla-offers#web-console) | No for listing. Per-machine SLA earnings need the CLI and a `billing_read` key. |
| Automating search, rent, or listing | Continue below ([renter recipe](#renter-sla-scoped-key-recipe) · [host recipe](#host-sla-scoped-key-recipe)) | Yes |

On this page, **renter** means client and **host** means provider. API names may still say client or provider.

The sections below define permission categories and JSON recipes. Categories and endpoint lists apply **platform-wide** (templates, serverless, teams, and other automation)—not only SLA. The SLA recipes are optional shortcuts for that workflow.

For an overview of API key creation and usage, see [Authentication](/api-reference/authentication).

## Permission Categories

Permissions are organized into categories. When you create a scoped API key, you include only the categories the key needs. The available categories are:

| Category | Controls |
|----------|----------|
| `instance_read` | Viewing instances, logs, SSH keys, volumes, deposits |
| `instance_write` | Creating, managing, and destroying instances and volumes |
| `user_read` | Viewing account info, API keys, SSH keys, environment variables, templates |
| `user_write` | Creating/modifying API keys, SSH keys, environment variables, templates, teams |
| `billing_read` | Viewing invoices and earnings |
| `billing_write` | Transferring credit |
| `machine_read` | Viewing machines and reports (hosts) |
| `machine_write` | Managing machines, maintenance, listing/unlisting (hosts) |
| `misc` | Search offers, benchmarks, network volumes, serverless endpoints |
| `team_read` | Viewing team members and roles |
| `team_write` | Inviting/removing team members, managing roles |

## Creating Scoped Keys

Define permissions as a JSON object and pass it when creating a key. The top-level key is always `"api"`, containing the categories you want to grant.

**Example, Instance management with billing access:**

```json
{
  "api": {
    "misc": {},
    "user_read": {},
    "instance_read": {},
    "instance_write": {},
    "billing_read": {},
    "billing_write": {}
  }
}
```

**Example, Instance management without billing:**

```json
{
  "api": {
    "misc": {},
    "user_read": {},
    "instance_read": {},
    "instance_write": {}
  }
}
```

You can create scoped keys using:
- **API**: [Create API Key](/api-reference/accounts/create-api-key)
- **CLI**: [`vastai create api-key`](/cli/reference/create-api-key)
- **SDK**: [`vast.create_api_key()`](/sdk/python/reference/create-api-key)

<a id="client-sla-scoped-key-recipe"></a>
<a id="renter-sla-scoped-key-recipe"></a>

**Renter — search and REST rent.** Search with `has_sla` → rent with `target_reliability` on `PUT /api/v0/asks/{id}/` → verify with `GET /api/v1/instances/`. **If you are a host, do not use this JSON** — use the [Host SLA scoped-key recipe](#host-sla-scoped-key-recipe).

Create the key via [Create API Key](/api-reference/accounts/create-api-key). Do not copy the host recipe.

**Workflow summary:** Search, then REST rent with `target_reliability`, then verify on v1 instances. Charges and **Account → Billing → Charges** show the same net `type: "sla"` row. The console labels it **Service Credit** only when the amount is negative.

- Create a **dedicated** key for this workflow only. `misc` covers offer search **and** unrelated routes such as serverless endpoints and workergroups. Constraints cannot limit `misc` to search only today. Treat a `misc` key as a high-impact secret. Do not reuse a full-access key.
- **Search:** `misc` (no search-only permission exists). Search automation is rate-limited—see [Rate Limits and Errors](/api-reference/rate-limits-and-errors) and [API automation](/guides/instances/choosing/sla-coverage#api-automation) before production search loops.
- **Rent:** `instance_write` on `PUT /api/v0/asks/{id}/` with `target_reliability`.
- **Verify:** `instance_read` with `GET /api/v1/instances/` or `vastai show instances --raw` (that command already calls v1). Store `search.slaPremiumPerHour` from the instance row when the rent succeeds. `instance.slaPremiumPerHour` is a cross-check only while the instance is running. It reads `0` while loading, stopped, or offline.
- **Charges:** add `billing_read` only if you read `sla` fee rows on `GET /api/v0/charges/`. The minimum key above cannot call Charges.

```json
{
  "api": {
    "misc": {},
    "instance_write": {},
    "instance_read": {}
  }
}
```

This is the minimum for search, REST rent, and verification. Add `user_read` if the flow loads templates or account profile data, and `user_write` if it creates SSH keys or templates.

| Task | Category | Console fallback |
| --- | --- | --- |
| Search SLA offers | `misc` | **Search** |
| Rent with an SLA | `instance_write` | Console **RENT** |
| Verify `target_reliability` | `instance_read` | **Instances** |

**Service credits:** **Account → Billing → Charges** and `GET /api/v0/charges/` show the same net row. How that row is labeled is in [Settlement timing](/guides/instances/choosing/sla-coverage#settlement-timing). The call requires `select_filters` with both `day.gte` and `day.lte` (unix seconds, UTC). A call without that range returns HTTP 400. The contract row can appear before settlement. Its `type: "sla"` item is absent until that day settles. Page by sending `next_token` as `after_token`. Stop when `next_token` is `null`. Invoices (`GET /api/v1/invoices/`) are payment transactions, not SLA credits.

```bash
curl -G "https://console.vast.ai/api/v0/charges/" \
  -H "Authorization: Bearer $VAST_API_KEY" \
  --data-urlencode 'select_filters={"day":{"gte":1767225600,"lte":1767311999}}' \
  --data-urlencode "limit=500"
```

<Note title="API integrators">
Each `items[]` entry is the total for the whole query window, so this example is one UTC day (`day.lte` = `day.gte` + 86399). An amount smaller than the SLA fee you expected, or a negative amount, means a credit was applied. The contract row can appear before settlement. Its `sla` item is absent until that day settles. If `next_token` is not `null`, repeat the request with `after_token` before you treat a missing `sla` item as unsettled.
</Note>

<a id="host-sla-scoped-key-recipe"></a>

**Host — list, backtest, and earnings.**

Create the key via [Create API Key](/api-reference/accounts/create-api-key). Do not copy the renter recipe. `machine_write` can change a listing but cannot read current values, backtest, or read earnings. Pair it with `machine_read` so a script can read the current listing, then send a full body, because omitted fields reset. `machine_read` also covers the backtester. Add `billing_read` for earnings. For cron, prefer a `billing_read` key for monitoring and a separate `machine_write` + `machine_read` key for listing changes.

**Workflow summary:** Backtest (optional) → `create_asks` with SLA fields → monitor earnings; host-side settlement is separate from marketplace score.

**Host SLA automation keys:** `machine_write` applies to all machines on the account. You cannot scope `create_asks` or maintenance to a subset of machines via API key constraints today. Use dedicated keys with rotation and monitoring for fleet jobs.

**Listing + earnings only** (no search). For cron jobs, split this into a `billing_read` key for monitoring and a `machine_read` + `machine_write` key for listing changes:

```json
{
  "api": {
    "machine_read": {},
    "machine_write": {},
    "billing_read": {}
  }
}
```

**Verify offers in search** — add `misc` on a **separate**, narrowly scoped key (`misc` also covers serverless and other routes—not search only):

```json
{
  "api": {
    "misc": {}
  }
}
```

| Task | Permission | Console fallback |
| --- | --- | --- |
| List or update an SLA offer (`PUT /api/v0/machines/create_asks/`) | `machine_write` | **Set Pricing → SLA** → **Save**. First publish: **Save** → **LIST**. Already listed: **Save** only ([Web console](/host/sla-offers#web-console)) |
| SLA backtester | `machine_read` | Console SLA preview |
| Schedule / cancel maintenance | `machine_write` | [Set a maintenance window](/host/set-maintenance-window) (Host → Machines → Settings → Machine Maintenances), or CLI/REST. SLA service-credit rules: [Scheduled maintenance](/host/sla-offers#scheduled-maintenance). |
| Monitor `sla_earn` | `billing_read` | Host → Billing / Earnings (console billing needs no API key; API earnings need `billing_read`). Use `per_machine[].sla_earn` for one machine; `per_day[].sla_earn` is fleet-wide even with `machid`. See [Monitoring SLA after listing](/host/sla-offers#monitoring-sla-after-listing). |
| Verify the listing in search | `misc` (separate key) | **Host → Machines** (no API key). Optional CLI: `vastai search offers 'machine_id=12345 verified=any has_sla=true' --storage 10` (`verified=any` is often required when checking your own machine). |

Earnings URL: `GET /api/v0/users/me/machine-earnings/`. The path user id is ignored; the API key owner is used, so do not add `user_read` just to discover an id. Start with [SLA in plain language](/host/sla-offers#sla-in-plain-language).

## Custom Roles

Custom roles let you assign the same set of permissions to multiple team members.

- **Creating roles**: Use the CLI or the Manage page in the web console (requires `team_write` access).
- **Defining permissions**: Select from any combination of the categories listed above.
- **Assigning roles**: Assign created roles to team members through the team management interface or CLI.

## Constraints

Constraints narrow a permission category to specific parameter values. This lets you create keys that can only operate on certain resources.

**Example, Read logs for a single instance only:**

```json
{
  "api": {
    "instance_read": {
      "api.instance.request_logs": {
        "constraints": {
          "id": {
            "eq": 1227
          }
        }
      }
    }
  }
}
```

**Example, Read logs for a range of instance IDs:**

```json
{
  "api": {
    "instance_read": {
      "api.instance.request_logs": {
        "constraints": {
          "id": {
            "lte": 2,
            "gte": 1
          }
        }
      }
    }
  }
}
```

Supported constraint operators: `eq`, `lte`, `gte`.

Host listing (`machine_write` / `create_asks`) cannot be constrained to specific machine IDs today. The examples above apply to `instance_read` (and similar instance-scoped routes), not host SLA listing keys.

<Note>
API keys using constraints must be created via the CLI ([`vastai create api-key`](/cli/reference/create-api-key)) or the API ([Create API Key](/api-reference/accounts/create-api-key)).
</Note>

You can also use **wildcards** in `params` to represent placeholder values, useful when generating many keys that perform similar operations.
