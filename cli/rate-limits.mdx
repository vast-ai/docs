The Vast.ai CLI retries some failed requests. With the default of 3 attempts, those retries finish in under a second and do not read `Retry-After`. For offer search, rent, `create_asks`, and maintenance scheduling, add your own spacing. See [SLA API automation](/guides/instances/choosing/sla-coverage#api-automation).

This page covers the error format, how rate limits work, and how to configure the CLI's built-in retry behavior. For the full details on rate limit mechanics, see the [API Rate Limits and Errors](/api-reference/rate-limits-and-errors) page.

## Error Responses

When a CLI command fails, it prints the error message from the API and exits with a non-zero status code. The underlying API error shape is:

```json
{
  "success": false,
  "error": "invalid_args",
  "msg": "Human-readable description of the problem."
}
```

Some endpoints omit `success` or `error` and return only `msg` or `message`. The CLI surfaces whatever message the API returns.

## How Rate Limits Work

Vast.ai applies rate limits **per endpoint**. For an API key, the limit is on that key's account. Extra keys on the same account share it. The client IP is used only when a request does not resolve to an account.

Some endpoints also enforce **method-specific** limits (GET vs POST) and **max-calls-per-period** limits for short bursts.

For the full breakdown, see [How rate limits are applied](/api-reference/rate-limits-and-errors#how-rate-limits-are-applied).

## Rate Limit Response

HTTP 429 comes in two families. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors#rate-limit-response-behavior).

- Legacy rent, show-instances, `create_asks`, and `show earnings` (machine earnings) return plain text and no `Retry-After`.
- Search, charges, the other earnings routes, schedule maintenance, and the SLA backtester return JSON. A short limit uses `"error": "HTTPTooManyRequests"` and a `Retry-After` header. A daily search quota hit uses `"error": "search_quota_exceeded"` and a `Retry-After` that can be hours.

The CLI never reads `Retry-After`. With the default of 3 attempts, its retries finish in under a second. If your script calls the API directly, wait at least `Retry-After` when it is present.

## Built-in Retry Behavior

The CLI retries a failed request on HTTP 429, 502, 503, and 504, and on connection errors and timeouts. With the default of 3 attempts, those retries finish in under a second. It never reads `Retry-After`.

- `--retry` is the **total number of attempts**, not extra retries after the first try.
- **Default:** 3 attempts (one request plus two retries), with delays of about 0.15 s and 0.225 s.
- **Backoff:** starts at 0.15 seconds, multiplied by 1.5 after each attempt. The CLI does not read `Retry-After`.
- To send a request once, use `--retry 1`. Do not use `--retry 0`. It sends no request and the command fails.

Any rent can be sent twice if the first request reached the server and the connection then failed. Set a unique `--label` and check your instances for it before you rent again. The CLI and SDK cannot turn SLA on; SLA rentals use the console or REST. Use the same label check in your own retry logic. See [SLA API automation](/guides/instances/choosing/sla-coverage#api-automation).

<Tip>
The CLI retries 429, 502, 503, 504, connection errors, and timeouts. Other HTTP errors are reported immediately.
</Tip>

## Configuring Retries

Use the `--retry` flag on any command to change the total number of attempts:

```bash
# Default: 3 attempts
vastai search offers 'gpu_name=RTX_4090 rentable=true'

# One attempt only
vastai search offers 'gpu_name=RTX_4090 rentable=true' --retry 1
```

Raising `--retry` does not replace your own request spacing. On a rent, each extra attempt can send the request again.

## Reducing Rate Limit Errors

If you are consistently hitting rate limits, the best approach is to reduce the volume and frequency of your requests. See [How to reduce rate limit errors](/api-reference/rate-limits-and-errors#how-to-reduce-rate-limit-errors) for practical strategies including batching, reduced polling, and traffic spreading.

If you need higher limits for production usage, contact support with the endpoint(s), your expected call rate, and your account details.
