Confirmed defects

Four items block acceptance of the evidence package. None of them inflates a PASS — every one is conservative in direction. All four were reproduced independently after a reviewer raised them; the re-run block under each is the exact command.

D1 A stale rollup makes the published accounting wrong by one

Step ERR-T04-B02-S03 is recorded NOT_APPLICABLE with the rationale "EVIDENCE_LINKAGE ALL_CHILDREN_NOT_APPLICABLE". Its only child, CLM-720bb6982a2e7948, is UNVALIDATED — because it was correctly demoted from NOT_APPLICABLE/3 to UNVALIDATED/2 in withdrawn_records (the NVSwitch branch that a non-NVSwitch observation had been treated as proving). The parent rollup was never recomputed.

The correct split is N/A 27 / UNVALIDATED 278, not 28 / 277. This also falsifies the reconciliation attempt's own PASS justification in verification/evidence/2026-09-01-host-current-reconciliation-attempt-01/result.md, which states the 972-target accounting is "complete and internally consistent". It is not.

Re-run 
jq -r '.current_status_projection.records[]
  | select(.level=="STEP" and .current_status=="NOT_APPLICABLE")' \
  verification/host-docs-test-results.json

jq -r '.current_status_projection.records[]
  | select(.level=="COMMAND" and .target.step_id=="ERR-T04-B02-S03")' \
  verification/host-docs-test-results.json

Fix: recompute the rollup, correct the split in HOST-DOCS-QA-SUMMARY.md and the handoff, and issue a new reconciliation attempt rather than editing the existing one in place.

D2 Three PASS results cite evidence files that are not in the commit

Four retained evidence records point at detail tables under .orchestra/host-vv-reconciliation-20260901/findings/, which is untracked and outside the review commit. Three of the four back a test-set PASS:

The files exist on this machine, so a local reviewer is unaffected. The detail-audit SHA-256 is recorded in each result, so tamper-detection survives — the artifact itself does not travel.

D3 Every score cites one evidence record that disclaims itself

All 138 scored command records — the 11 score-3 rows included — carry evidence_ids: ["EV-HOST-COMMAND-ASSESSMENT-01"]. That record's own limitations field reads:

"Score-traceability evidence only. All 138 numeric-score carriers remain UNVALIDATED in this assessment evidence… Functional current status is owned by separate exact reconciliation evidence."

So a reviewer following a score-3's citation in search of its proof lands on a record stating it proves nothing functional. The real supporting evidence does exist, in command_results, keyed by command_id — but the citation field does not lead there, so the chain has to be re-derived by hand. This is not dishonest; it is also not independently followable, which is the property an evidence package exists to provide.

Re-run 
jq -c '.records[].evidence_ids' \
  verification/host-docs-command-scores.json | sort | uniq -c
# => 138 ["EV-HOST-COMMAND-ASSESSMENT-01"]

jq -r '.procedure_results[]
  | select(.evidence_id=="EV-HOST-COMMAND-ASSESSMENT-01") | .limitations' \
  verification/host-docs-test-results.json

Fix: populate each score record's evidence_ids with the command_results evidence ID that actually supports it, retaining the assessment record as a secondary traceability reference.

What held up

Seven reviewers were briefed to break the claims below and could not. Each was then spot-checked directly against the repository.

Retained failures

Nothing was laundered

All three original FAQ route-ownership failures and the invalid Hardware Prep multi-target mount check survive verbatim, each linked to its correction retest. The retained failure record even forbids overwriting or relabelling itself.

Self-demotion

The package removes its own passes

Of 7 withdrawn records, 5 are demotions: three PASS/3 → UNVALIDATED/2 on /host/vms after the IOMMU target was ruled unrepresentative, one PASS/3 → STALE, and one NOT_APPLICABLE/3 → UNVALIDATED/2.

Fails closed

The panel cannot fake a pass

No render path turns BLOCKED or UNVALIDATED into passing. The snapshot hash is enforced at load (review-server.mjs:442-443) and every host/*.mdx is hashed too (:330-334) — editing a doc page without re-running the pipeline breaks the panel rather than drifting quietly.

Corrections traceable

Audit → fix → rescore is followable

The two 2-line .mdx edits in this commit add bounded-follow wording with explicit Ctrl+C and exit confirmation to a journalctl -kf and a tail -f. They map exactly onto the two BLOCKED/1 → BLOCKED/2 withdrawals.

Score 1

Real gaps, not scraping noise

All 15 score-1 carriers are well-formed, cross-page-consistent commands with zero retained execution evidence — genuine evidence gaps rather than extraction artifacts. No dangerous advice was found sitting in published documentation.

Gates

Conservative, not an excuse ledger

All 34 BLOCKED command carriers map onto a declared gate class — mutation/installer, external TCP/UDP, Docker GPU injection, paid or state-changing CLI, or live-follow runtime. No harmless read-only command hides among them.

Pages

No page oversells its status

All 8 representative pages' recorded statuses are consistent with what their prose actually claims to a reader. No page implies more readiness than its evidence supports.

Sanitization

No secrets in committed evidence

Pattern scans for API keys, private keys, and non-localhost IP addresses across verification/evidence/ return zero hits. This is the first direct test of that claim.

Non-blocking observations

None of these changes the conclusion. All are worth knowing before the headline numbers are quoted elsewhere.

  • BLOCKED is mostly inherited, not observed. Only 22 command results carry a real named blocker_class (CREDENTIAL_PERMISSION 6, INTERACTIVE_PRIVILEGE 4, TEST_ENVIRONMENT_NOT_REPRESENTATIVE 4, DOCKER_SOCKET_PRIVILEGE 2, STATE_CHANGING_LIVE_ACTION 2, plus 4 singletons). Of 589 BLOCKED targets, 235 carry the single derived rationale NONCOMMAND_LINKAGE BLOCKED_AUTHORITY. The direction is safe — propagating BLOCKED never inflates a PASS — but the label reads as we were prevented where not attempted is equally defensible.
  • The one page-level PASS is small. /host/common-host-questions has exactly one test set, one branch, one step and zero command carriers. Its whole V&V surface is a static route-ownership audit. The PASS is earned, but it should not be read as "a Host page was proven to work".
  • 37% of command PASSes are static catalog conformance. 17 of the 46 are host-teams.mdx:140-148 help-path acceptance, with runtime, permissions and billing explicitly UNVALIDATED in the rationale. Two more validate empty-state behaviour only. verification/HOST-DOCS-COMMAND-COVERAGE.md:41-43 discloses this; the headline table in HOST-DOCS-QA-SUMMARY.md:22 carries no such caveat.
  • All 27 N/A carriers share one blanket approval hash, and that hash (4d5ad9a0…) is simply the test-sets snapshot SHA-256. approval_ref is therefore a pointer to the frozen inventory, not a per-carrier human sign-off. 26 of the 27 were independently confirmed genuinely display-only; the bare tcpdump prose token is borderline but defensible, and its owning manual/WAN procedure remains separately blocked.
  • Score-2 rationales are 73% templated — 112 records across 30 distinct strings. Spot-checks over 20 carriers on 11 pages found the templates do track genuinely repeated evidence situations, so this is phrasing economy rather than a dumping ground. Two minor issues: one template lists "mutations" among unexecuted aspects even for read-only commands, and one template is reused verbatim across both BLOCKED and UNVALIDATED records.
  • 33 of the PR's 72 Host pages sit outside procedure V&V. The generated CLI/SDK reference pages are excluded by an explicit scope decision (HOST-DOCS-PROCEDURE-VV-GOAL.md:116-121) and are covered by the older static registry check instead (179/181 occurrences). Defensible — but that reduction is disclosed only inside a long goal document, not in the handoff's own scope line, and the 182↔165 command mapping is documented nowhere reviewer-facing.
  • One small test gap. Attempt supersession is exercised by the suite, but the two specific throws at review-server.mjs:483-484 — self-reference and dangling pointer — have no fixture of their own.

Scope of this review

What was not done

No command was run against a Vast host. No money was spent. No VM transition, GPU load, privileged change, mutation or WAN test was performed. The working tree was not modified — HEAD remains 3b7e56f and git diff HEAD is empty.

  • The fresh-clone path (gh pr checkout 185 → npm ci → npm run dev:review) was never executed end to end; network access was outside this review. Every component was validated in place, but the published instruction itself is unproven — and a fresh clone would additionally hit the D2 dangling references.
  • PR #185 could not be confirmed as the review target without network access. It is consistent across all four internal documents, despite this checkout being named docs-pr153-*.
  • The absence of every identifier class — hostnames, serial numbers — cannot be proven by pattern scan alone. Credentials, keys and non-localhost IPs were scanned and are clean.
  • The review interface was read as source code, not driven in a browser. If a rendered walkthrough is wanted, that is a separate pass.

Method

Eight independent reviewers were dispatched against separate parts of the package: the 11 score-3 carriers, the 15 score-1 carriers, the 27 approved N/A carriers, the retained failure/correction history, the fail-closed behaviour of review-server.mjs, the eight representative pages named in the handoff, and a cross-page score-2 sample — followed by an adversarial synthesis pass briefed to argue against acceptance. Reviewers received the requirement and the artifact, not the package author's reasoning.

Every finding reported here was reproduced by the orchestrator before being recorded. Claims that did not survive that check were dropped, including one reviewer's assertion that supersession integrity had no test coverage at all — the suite does exercise it; only the two invalid-supersession throws are uncovered.

Reviewer findings are retained at .orchestra/host-docs-vv-review/ — ledger.html for verified facts and findings/<agent>.html for each reviewer.
