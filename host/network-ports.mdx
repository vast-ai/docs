Configure public inbound networking before verification. Vast hosts need direct ports reachable from outside the host LAN.

<span id="ports-per-gpu" aria-hidden="true" />
## Ports Per GPU

Self-test requires at least 3 direct ports per listed GPU. For production hosting, plan for about 100 direct ports per listed GPU. One instance can map up to 64 ports, and a larger range gives headroom while old mappings are being released and new instances are starting.

| Listed GPUs | Minimum | Practical example |
| --- | ---: | --- |
| 1 | 3 | `40000-40099` |
| 4 | 12 | `40000-40399` |
| 8 | 24 | `40000-40799` |

The forwarded router/firewall range must match the range configured in the host software. The 100-port guidance is practical headroom, not a self-test minimum.

<span id="tcp-udp" aria-hidden="true" />
## TCP And UDP

Forward both TCP and UDP for the configured direct port range. TCP-only forwarding can pass some checks while still failing renter workloads that need UDP.

## Set The Host Port Range

In the Host Installer Wizard, enter the same range you forwarded.

For the [raw installer](/host/installing-host-software#headless-fallback), include `--ports 40000 40799` in the install command, replacing the range with your forwarded ports.

<span id="cgnat-starlink-ipv6" aria-hidden="true" />
## CGNAT, Starlink, IPv6-Only, Or No Public IP

Vast hosting requires a public IPv4 address with inbound TCP and UDP forwarding for the configured direct-port range. CGNAT and shared ISP addresses are not supported by the published setup requirements. With double NAT or an IPv6-only service, establish a working public IPv4 forwarding path before listing; an outbound internet connection alone is insufficient.

Compare your router WAN IP with your public IP and test from outside the LAN. If the router does not have a public inbound address or cannot forward the configured ports to the host, use a network connection that provides public inbound connectivity before listing the machine.

<span id="test-ports-outside-lan" aria-hidden="true" />
## Test Ports From Outside The LAN

Test from a different network, such as a cloud VM or a laptop on mobile data with Wi-Fi disconnected. A same-LAN test can fail without NAT hairpinning, or pass through a local hairpin path while Internet connections remain blocked by double-NAT forwarding problems or ISP firewall restrictions. Enabling hairpinning does not validate the external path; test from outside the host’s network even when local tests pass.

**Simple**

On the host, start a temporary TCP listener in an empty directory. Leave it running while you test from another computer:

```bash
VAST_PORT_TEST_DIR=$(mktemp -d) &&
python3 -m http.server 40000 --bind 0.0.0.0 --directory "$VAST_PORT_TEST_DIR"
```

From macOS or Linux outside the LAN:

```bash
curl -v http://PUBLIC_IP:40000/
nc -vz PUBLIC_IP 40000
```

From Windows PowerShell outside the LAN:

```powershell
Test-NetConnection PUBLIC_IP -Port 40000
curl.exe http://PUBLIC_IP:40000/
```

Use the TCP checks above from an external machine to test inbound TCP reachability.

For UDP, open a second session on the host and watch for packets:

```bash
sudo tcpdump -ni any udp port 40000
```

Then send a UDP packet from macOS or Linux outside the LAN:

```bash
printf 'vast-port-test\n' | nc -u -w2 PUBLIC_IP 40000
```

From Windows PowerShell outside the LAN:

```powershell
$udp = New-Object System.Net.Sockets.UdpClient
$bytes = [Text.Encoding]::ASCII.GetBytes("vast-port-test")
$udp.Send($bytes, $bytes.Length, "PUBLIC_IP", 40000)
$udp.Close()
```

When testing is complete, press `Ctrl+C` in the listener session, then remove the empty directory:

```bash
rmdir "$VAST_PORT_TEST_DIR"
```

Stop `tcpdump` with `Ctrl+C` as well. Stop all temporary listeners before running the installer.

<Accordion title="Advanced">

If the external TCP test fails, use a second SSH session on the host to check whether the temporary server is listening:

```bash
sudo ss -ltnp | grep ':40000'
```

Run this check while the server is running. If no listener appears, fix that first; if it does, check the host firewall, router forwarding, and upstream network. Run the check again after stopping the server to confirm the temporary listener is gone.

The empty serving directory keeps the test response predictable and avoids exposing files from your current directory. Port `40000` does not require running the HTTP server as root.

</Accordion>

During self-test, troubleshoot the exact public IP and port reported by the CLI, such as `https://PUBLIC_IP:PORT/progress`.

## Connectivity Failures

`Port Networking Issues` indicates that the platform’s inbound port-reachability check could not connect. A self-test timeout can also involve a missing progress server, a crashed container, or a stalled test; inspect the reported stage and logs. [`vericode=8`](/host/glossary#vericode) means a host-facing machine error is present; use the exact visible message to identify the cause. See [Self-Test Reference: vericode=8](/host/self-test-reference#vericode-8) and [no response for 120s](/host/self-test-reference#no-response-120s).
