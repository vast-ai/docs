Machine Metrics is a monitoring dashboard for the machines you host on Vast. It records how each machine has behaved over time and lets you replay any window of that history, from a few seconds to the machine's full recorded history.

## Why use it

**Machine health:**
- Review reported machine activity and health indicators before or after a rental; check the current machine status separately because metrics can lag.
- Catch hardware problems early, such as a GPU running hot or clocking down

**Troubleshooting:**
- Investigate a client complaint about a slow, unresponsive, or underperforming machine
- Investigate repeated container stops or restarts, then check logs and exit status to determine the cause
- Track down performance issues or unexpected drops in throughput

## Opening the dashboard

Open [Machine Metrics](https://cloud.vast.ai/host/machine-metrics/) in the Host section of the console, then pick a machine from the **Machine** dropdown.

You can also open a specific machine from **Host → Machines** with the **View metrics** option on the machine card.

## What gets collected

The Vast daemon collects the following data from your machines:

| Data | How often it is sampled |
| --- | --- |
| CPU, memory, GPU, disk, and network counters | Every second |
| Container state | Every 15 seconds |

Samples are batched on the machine and uploaded periodically, at a rate that depends on how much data the machine is producing. If uploads are interrupted, locally retained samples can be uploaded when the machine reconnects. Gaps can fill in for those retained samples; data that was never collected or was lost from the local buffer cannot be recovered this way. A very long interruption can lose the oldest buffered data.

<Note>
This is not a real-time tool. The page loads the window ending at the moment you opened it and does not advance while the tab stays open, and the most recent data can be hours behind. Reload the page to pull in whatever has arrived since.
</Note>

## Metrics chart

The chart covers the last 7 days by default. Every metric has a button above it: click to add that series, click again to remove it.

### CPU

| Metric | What it means |
| --- | --- |
| User CPU | Time spent running programs, including your clients' workloads |
| System CPU | Time spent in the kernel on the programs' behalf: syscalls, drivers, filesystem and network work |
| CPU I/O Wait | Time accounted to waiting for I/O. High values are a reason to investigate storage alongside disk metrics and workload behavior; this counter alone does not identify the bottleneck |
| Idle CPU | Time the CPU had nothing to do |
| CPU Steal | Time the CPU was ready to run but the hypervisor gave the cycles to someone else. Only meaningful if the machine is itself a virtual guest; it stays at zero on bare metal |
| Load (1m) | Average number of runnable tasks and tasks in uninterruptible wait, such as disk I/O, over the last minute. Compare it with the available logical CPU count, but also inspect I/O wait: a high load does not by itself prove CPU saturation |

### Memory

| Metric | What it means |
| --- | --- |
| Total Memory | Usable RAM reported by the operating system, excluding reserved memory and kernel binary code |
| Free Memory | RAM currently free. A low value alone does not establish memory pressure; also check Available Memory, which accounts for reclaimable capacity |
| Available Memory | Estimated RAM available for new applications without swapping, including reclaimable cache. Prefer it to Free Memory when checking available capacity |
| Cached | File cache, including tmpfs and shared memory, kept in RAM. Some cache can be reclaimed under memory pressure; Cached is not all immediately available RAM |
| Buffers | Temporary memory used for raw disk blocks |
| Free Swap / Total Swap | Unused and total configured swap capacity. Occupied swap alone does not show active paging; inspect swap-in/swap-out rates and Available Memory before attributing slowness to memory pressure |
| Processes | Total number of processes on the machine |

### GPU, disk, and network

Select the **GPU**, **Disk**, or **Network** tab to chart whole-machine summaries for that hardware:

| Tab | Summary metrics |
| --- | --- |
| GPU | Avg Util (averaged across the machine's GPUs), Max Temp (the hottest GPU), Total Power |
| Disk | Avg Util |
| Network | Total RX, Total TX |

Expand the tab with the arrow on its right to chart each device separately. This is how you spot one card in an eight-GPU box running hotter or slower than the rest.

| Tab | Per-device metrics | Notes |
| --- | --- | --- |
| GPU | Utilization, Memory Utilization, Used Memory, Total Memory, Temperature, Power, SM Clock, Memory Clock | Utilization is the share of the sample period when a GPU kernel was executing, not the fraction of compute capacity used. Falling SM Clock near a temperature or power limit can suggest throttling; check NVIDIA clock-event reasons to distinguish thermal, power and other limits |
| Disk | Utilization, Read and Write IOPS, Read and Write Speed | Utilization estimates time with I/O active. IOPS counts operations per second; read and write speed measure bytes transferred per second |
| Network | RX and TX throughput, RX and TX Packets, RX and TX Errors, RX and TX Drops | RX is traffic in and TX is traffic out. Errors and drops are shown per sample rather than as lifetime totals. Investigate nonzero counts alongside interface and system diagnostics: drops can also result from resource limits, protocol handling or filtering, so these counters alone do not identify a cable, NIC or upstream fault |

### Reading the chart

Each series is drawn between the **hi** and **lo** marks on its own scale, so metrics with different units share one chart. The solid line is the average and the shaded band is the min to max range, which is why a variable series looks like a band when zoomed out.

Hover anywhere to read values at that moment. All timestamps on this page are UTC.

To move around the timeline:

- **Drag** to pan through time, or **scroll** to zoom in and out around the cursor
- Use the **zoom in** and **zoom out** buttons in the toolbar for fixed steps
- **Reset view and filters** returns to the default 7-day window and the default set of metrics
- **All off** clears the chart. **All on** turns on the CPU, memory, and summary metrics, but leaves per-device series off so the chart does not fill with one line per GPU

Zooming in loads finer-grained data, down to per-second samples over short windows.

## Containers

Below the chart, a timeline shows container activity for the time range you are viewing. One row per container appears on the machine during the window, so you can see the rental history at a glance:

| Legend | What it shows |
| --- | --- |
| exists (stopped) | A thin gray lifeline spans the container’s recorded existence. Portions without a running bar indicate time when it existed on the machine but was not running |
| running | A solid blue bar over the periods the container was actually running |
| running (vm) | The same, in purple, for a container running as a VM |
| intermittent (zoom in) | A striped bar covering several runs and the gaps between them, too close together to draw separately at this zoom |

Hover a row to inspect its recorded container details. When metadata is available, these include status, last reported state, first and last seen times, duration, run count and total running time; a row can instead report **no data**. Click a run to zoom the chart to it and compare the rental with GPU, memory and network activity.

<Note>
A striped bar combines runs that are too close together to draw separately at the current zoom. Zoom in to inspect the pattern. Frequent short runs can be a reason to investigate repeated exits or restarts, but the timeline alone does not distinguish a crash loop from intentional activity; check container logs and exit status.
</Note>

## Troubleshooting

| Symptom | Where to look |
| --- | --- |
| A GPU running hot or throttling | Expand the GPU grid and compare Temperature, Power, SM Clock and utilization per card. Investigate cooling, power limits and workload differences, and check NVIDIA clock-event reasons before assigning a cause |
| Clients keep leaving the machine | Find the relevant container activity in the Containers timeline and zoom into it. Repeated short runs warrant checking logs and exit status; the timeline alone does not establish a crash loop or why a client left |
| Unexplained slowness | Investigate high CPU I/O Wait alongside disk metrics and workload behavior. CPU Steal reflects CPU time unavailable to a virtual guest; high values warrant examining host scheduling, but do not by themselves prove oversubscription |
| Bandwidth complaints | Chart Total RX and Total TX over the rental window, then expand the Network grid to check errors and drops on the interface |
| The machine looks idle | GPU utilization near zero indicates little GPU-kernel execution in the reported samples. Check whether the workload is using the GPUs or is waiting on other work before drawing a conclusion |
| No data at all for a machine | Reports may be missing or delayed. Check that the machine is online and running a current Vast daemon, and contact support if the chart stays empty |
| The chart stops short of right now | Expected. The page does not follow the clock. Reload it |

## Limitations

- **VM machines** report everything except GPU metrics for now. The page shows a notice when you are looking at one.
- **History starts when the machine first reported in its current recording format.** A recently set up machine has a shorter history than the default 7-day window, and a daemon update that changes the recording format restarts it.
- **There is no set retention period.** Nothing is deleted on a schedule today, so a machine's history keeps growing for as long as it reports.
