Turn off SSH password login to protect your machine. A machine with it enabled
will not pass verification.

The steps are the same on Ubuntu Server 22.04 and 24.04.

<Warning>
Do not turn off password login until a separate key-only connection succeeds.
Keep your current session open and confirm that you have a recovery route before
changing or restarting SSH.
</Warning>

## 1. Check the current setting

This checks the configuration files and prints the effective settings, then
exits. It does not query the running daemon or test a login. Connection-specific
`Match` rules need an appropriate `-C` connection specification.

```bash
sudo sshd -T | grep passwordauthentication
```

```
passwordauthentication yes
```

If it says `no`, the displayed configuration disables the password
authentication method for that evaluation. Still review applicable `Match`
rules and keyboard-interactive settings, and confirm access after applying
changes. If it says `yes`, continue.

<Note>
OpenSSH defaults `PasswordAuthentication` to `yes` when no applicable setting overrides it. Ubuntu images and SSH drop-ins can change that value, so use the effective-configuration check above instead of assuming a fresh install reports `yes`.
</Note>

## 2. Add your key and confirm it works

From your own computer. Replace `youruser` with your login name on the machine
and `1.2.3.4` with its IP address, here and in every command below.

```bash
ssh-copy-id youruser@1.2.3.4
```

```
Number of key(s) added: 1
```

Open a second terminal while keeping the first session connected. Use the key-only command below with connection sharing disabled so it performs a fresh authentication. A successful connection confirms public-key authentication for that account; it does not by itself identify which configured or agent-held key was used.

```bash
ssh -o ControlPath=none -o PreferredAuthentications=publickey youruser@1.2.3.4
```

Confirm that the fresh connection gives you the expected access without asking for the server account password. A prompt for your private key’s passphrase is normal and is not SSH password authentication.

<Warning>
If you get `Permission denied (publickey)`, stop: that connection did not
authenticate with a key. Check the account, the server’s configured authorized
keys file, ownership and permissions, and the SSH server logs. For the usual
`~/.ssh/authorized_keys` layout, modes `700` for `~/.ssh` and `600` for the file
are restrictive choices; they do not by themselves prove login will work.
</Warning>

## 3. Turn off password login

**Simple**

After the key-only connection works, back up the main configuration and open it
in your editor. `cp -n` leaves an existing backup unchanged; if `.orig` already
exists, choose a fresh backup name before running this command.

```bash
sudo cp -n /etc/ssh/sshd_config /etc/ssh/sshd_config.orig && sudoedit /etc/ssh/sshd_config
```

Set this directive, removing a leading `#` if present:

```
PasswordAuthentication no
```

Check the standard drop-in directory for other password-authentication settings:

```bash
sudo grep -r -i passwordauthentication /etc/ssh/sshd_config.d/ 2>/dev/null
```

Back up each relevant file before opening it with `sudoedit`, then set its
`PasswordAuthentication` directive to `no`. Ubuntu includes these drop-ins at
the start of its shipped configuration, so an earlier global setting can take
precedence over the main-file setting. Also review any custom `Include` paths
and applicable `Match` blocks.

<Accordion title="Advanced">

### Edit the standard configuration files automatically

Use this instead of the manual backup-and-edit commands above if you want to
update matching directives in the main file and all existing standard `.conf`
drop-ins. Check any existing `.orig` backups first and retain fresh copies if
needed: `cp -n` preserves an old backup rather than replacing it.

```bash
sudo cp -n /etc/ssh/sshd_config /etc/ssh/sshd_config.orig &&
sudo sh -c '
for file in /etc/ssh/sshd_config.d/*.conf; do
  [ -f "$file" ] || continue
  cp -n "$file" "$file.orig" || exit 1
done' &&
sudo sh -c '
[ -f /etc/ssh/sshd_config ] || exit 1
for file in /etc/ssh/sshd_config /etc/ssh/sshd_config.d/*.conf; do
  [ -f "$file" ] || continue
  sed -i -E "s/^[[:space:]]*#?[[:space:]]*(PasswordAuthentication)[[:space:]]+.*/\\1 no/I" "$file" || exit 1
done'
```

The script stops on a backup or edit failure. It updates existing directives,
including commented or indented ones, but does not add a missing directive or
search custom include paths. Check for errors before continuing to step 4.

</Accordion>

## 4. Apply and verify

`sshd -t` checks configuration validity and key sanity. The `&&` runs the
restart only after that check succeeds; it cannot guarantee a successful
restart or continued access. Configuration edits affect the daemon after it
reloads or restarts.

```bash
sudo sshd -t && sudo systemctl restart ssh.service
```

Check that both commands completed successfully. Keep the original session
open while you test a new key-only connection; do not rely on silence or assume
that a restart preserves every session.

Recheck the effective configuration on disk. This command does not by itself
confirm that the running service rejects password logins:

```bash
sudo sshd -T | grep passwordauthentication
```

```
passwordauthentication no
```

Repeat the key-only login from step 2 after applying the changes. Review any
connection-specific settings before closing the original session; the `no`
output alone is not a live authentication test.

If it still says `yes`, return to step 3 and find the setting that takes
precedence, including files read by `Include` and applicable `Match` blocks.
Correct that setting, then repeat this validation and connection check.

<Check>
After applying the changes, confirm that a separate key-only SSH connection
works before closing the original session. Recheck the machine’s status; if
the password-login warning persists, contact support with the current warning
and the relevant configuration checks.
</Check>

## If you are locked out

If the original session still works, use it to recover. Otherwise use the
machine’s BMC console (such as IPMI, iDRAC or iLO), or a local monitor and
keyboard. Restore the backups of the files you changed. Use your chosen backup
names, and check that they contain the working configuration you intend to
restore.

If you changed only the main file and used the `.orig` backup above:

```bash
sudo cp /etc/ssh/sshd_config.orig /etc/ssh/sshd_config &&
sudo sshd -t && sudo systemctl restart ssh.service
```

If you also changed drop-ins, restore those before validating and restarting.
A remaining earlier setting can override a later main-file value.

<Accordion title="Advanced">

### Restore the main file and standard drop-ins together

Use this only after checking that each existing `.orig` backup is one you want
to restore. Missing optional backups are skipped; a failed copy prevents the
validation and restart.

```bash
sudo sh -c 'for f in /etc/ssh/sshd_config.orig /etc/ssh/sshd_config.d/*.orig; do
  [ -e "$f" ] || continue
  cp "$f" "${f%.orig}" || exit 1
done' &&
sudo sshd -t && sudo systemctl restart ssh.service
```

</Accordion>

Restore working access through your recovery route, fix the key configuration, and repeat step 2. Do not assume the restored files permit password login. Disable password authentication again and verify a fresh key-only connection before returning the machine to the verification path.
