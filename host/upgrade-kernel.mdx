Ubuntu releases kernel updates regularly. Installing them is part of normal
upkeep on a host machine, and it is one of the
[verification requirements](/host/verification-stages).

This page has two paths. **Full system upgrade** considers available updates for installed packages. **Kernel-focused upgrade** targets the installed kernel metapackages and any dependencies APT needs. Review the proposed changes in either case. With package sources configured for your current Ubuntu release, these commands update its packages; they do not run a release upgrade such as 22.04 to 24.04.

The steps are the same on Ubuntu Server 22.04 and 24.04.

<Note>
A security-patched kernel is one requirement out of several and does not by itself establish verification. The full system upgrade considers updates across installed packages. The kernel-focused path requests the selected kernel metapackages, but dependencies can change too; review APT’s complete proposed changes.
</Note>

<Warning>
Booting an updated kernel normally requires a reboot, which interrupts running workloads. Before starting, review rental and storage commitments and arrange a maintenance window when the hardware is not actively being used. Schedule the window with [`vastai schedule maint`](/cli/reference/schedule-maint) so renters receive the planned-maintenance notice and can prepare.
</Warning>

## Full system upgrade (packages included)

For a machine whose package changes you are prepared to review. Run the three commands below one at a time, checking each result before continuing. Stop on errors, and reboot only after confirming that the intended kernel update was installed.

```bash
sudo apt-get update
sudo apt-get upgrade --with-new-pkgs
sudo reboot
```

This path also covers machines running a non-generic kernel, such as
`linux-oem-22.04` on certified OEM hardware or `linux-nvidia`, where step 1 of
the kernel-only path matches nothing.

<Warning>
This operation can upgrade packages across the system, not just the kernel. APT may keep some packages back, and package scripts may restart services. Review the full change list and keep its output so you can investigate problems after the upgrade.

Take this path when you have reviewed APT’s proposed changes and have a recovery plan. To focus the request on kernel metapackages, use the path below and still review its dependency changes.
</Warning>

Use `--with-new-pkgs` in this upgrade command. When a kernel metapackage needs new versioned dependencies, such as a new `linux-image-...` package, plain `apt-get upgrade` does not install them and can keep the metapackage back:

```
The following packages have been kept back:
  linux-generic linux-headers-generic linux-image-generic
```

If the intended kernel update was kept back, do not assume the reboot applied it. `--with-new-pkgs` allows new dependency packages during `upgrade` without allowing removals; check the installed and running kernel versions afterward.

Confirm the new kernel is the one running, because the reboot on its own proves
nothing:

```bash
uname -r; ls -1 /boot/vmlinuz-* | sed 's|.*/vmlinuz-||' | sort -V | tail -1
```

If the running release differs from the kernel you intended to boot, inspect the installed kernel files and GRUB menu. A different kernel family can also explain the comparison. See [If the machine booted the old kernel](#if-the-machine-booted-the-old-kernel).

<Warning>
`nvidia-smi` checks GPU-driver visibility, not which kernel booted. It can succeed under an older kernel with a compatible driver. Use `uname -r` to compare the running release with the kernel you intended to install, and check GPU visibility separately.
</Warning>

## Kernel-only upgrade

Use this path to focus the upgrade request on your installed kernel metapackages. The steps query their names, review available candidates and dependency changes, request the upgrade, and compare the installed and running versions.

### 1. Find your kernel metapackage

Find the installed `linux-generic*` metapackages selected by this query. Save
the names to a variable for the later commands; other kernel families and
packages with a different dpkg selection state need separate review:

```bash
KERNEL_METAPACKAGES=$(dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'linux-generic*' 2>/dev/null | awk '$1 == "ii" { print $2 }' | sort -V); echo "$KERNEL_METAPACKAGES"
```

Example output when `linux-generic` is installed:

```
linux-generic
```

Example output when the queried HWE metapackage is installed:

```
linux-generic-hwe-22.04
```

If `echo` printed nothing, stop and inspect the package query before continuing.
The later commands need a non-empty list of reviewed metapackage names. An empty
result can mean no matching `ii` records were returned or the query failed.

More than one line is a valid result. The later install command requests an
upgrade for each returned name; review APT’s proposed changes before accepting:

```
linux-generic-hwe-22.04
linux-generic-hwe-22.04-edge
```

Different metapackage names do not by themselves establish separate kernel
stacks. Check each package’s image and header dependencies, and review the
actual package changes and boot entries.

`KERNEL_METAPACKAGES` lives only in the shell session you set it in. If your
connection drops, or you open a second terminal, set it again before
continuing.

<Note>
Ubuntu provides a general availability (GA) kernel and hardware enablement
(HWE) kernels for LTS releases. HWE provides newer kernel support for newer
hardware. Ubuntu Server 22.04 and 24.04 default to GA and offer HWE as an option;
other kernel variants also exist, so inspect the packages on your machine.
</Note>

<Warning>
Query the installed names rather than assuming them. If `linux-generic` is not installed, passing that name with `--only-upgrade` skips it instead of installing or upgrading your HWE metapackage:

```
Skipping linux-generic, it is not installed and only upgrades are requested.
0 upgraded, 0 newly installed, 0 to remove and 24 not upgraded.
```

An otherwise successful command can exit `0` after skipping a package, so the exit status alone does not prove a kernel update occurred. Check the selected metapackage versions and the running kernel in Step 5.
</Warning>

### 2. Check for updates

Refresh the package lists first, or you will be comparing against stale data.

```bash
sudo apt update
```

Then look at what you have against what the archive is offering:

```bash
apt-cache policy $KERNEL_METAPACKAGES
```

```
linux-generic:
  Installed: 5.15.0.25.27
  Candidate: 5.15.0.190.169
  Version table:
     5.15.0.190.169 500
        500 http://archive.ubuntu.com/ubuntu jammy-updates/main amd64 Packages
        500 http://security.ubuntu.com/ubuntu jammy-security/main amd64 Packages
 *** 5.15.0.25.27 500
        500 http://archive.ubuntu.com/ubuntu jammy/main amd64 Packages
        100 /var/lib/dpkg/status
```

This is the comparison that decides whether you go on. Step 1 printing more
than one metapackage gives you one block per name here, and every block has to
be considered, not just the first.

If `Installed` and `Candidate` match for every selected metapackage, the current APT cache proposes no version change for those packages. Confirm that the metadata refresh succeeded and the configured sources are correct. Then compare the running kernel with the release you intended to boot; an earlier update may have been installed without being booted:

```bash
uname -r; ls -1 /boot/vmlinuz-* | sed 's|.*/vmlinuz-||' | sort -V | tail -1
```

If the running release matches the intended updated kernel and the selected metapackages have the expected installed versions, record the version and date. If the intended kernel is installed but not running, investigate the boot selection and plan the reboot in Step 4; do not repeat the package install solely because the release strings differ.

If the selected metapackage has a different available `Candidate`, review APT’s proposed version and dependency changes before accepting the install. Complete the remaining disruptive steps within your maintenance window.

### 3. Install the kernel update

```bash
sudo apt install --only-upgrade $KERNEL_METAPACKAGES
```

The summary line is the part worth reading:

```
The following NEW packages will be installed:
  linux-headers-5.15.0-190 linux-headers-5.15.0-190-generic
  linux-image-5.15.0-190-generic linux-modules-5.15.0-190-generic
  linux-modules-extra-5.15.0-190-generic
The following packages will be upgraded:
  linux-generic linux-headers-generic linux-image-generic
3 upgraded, 5 newly installed, 0 to remove and 24 not upgraded.
```

In this example, the named changes are kernel packages. Your proposed changes
may differ, so inspect the full list, including dependencies, before accepting.
The `not upgraded` count alone does not prove that all other packages stay unchanged.

<Note>
Use the appropriate kernel metapackage so its matching image and header dependencies are considered together. For DKMS-built NVIDIA modules, the target kernel needs matching headers. Ubuntu also supplies precompiled NVIDIA modules for supported kernels. Confirm that the chosen driver-module path supports the kernel you intend to boot before restarting.
</Note>

Before rebooting, confirm that a known working previous kernel is still
installed and available in the boot menu as a recovery option.

### 4. Reboot

The kernel you installed in step 3 does not become the running kernel until the
machine restarts.

<Warning>
A reboot interrupts running workloads. Before running it, confirm the maintenance window, review existing rental and storage commitments, and ensure the hardware is not actively being used.
</Warning>

```bash
sudo reboot
```

### 5. Verify

Once the machine is back, check that the new kernel is the one running:

```bash
uname -r; ls -1 /boot/vmlinuz-* | sed 's|.*/vmlinuz-||' | sort -V | tail -1
```

Compare the running release with the kernel you intended to boot. For a
single kernel stack, the two lines may match as in this example; multiple
variants or a custom boot entry need separate interpretation:

```
5.15.0-190-generic
5.15.0-190-generic
```

If `uname -r` reports an older release than the updated kernel you intended to boot, investigate why that entry was not selected. See [If the machine booted the old kernel](#if-the-machine-booted-the-old-kernel).

After confirming the intended kernel is running, re-check the installed metapackage versions using the same query as Step 2:

```bash
KERNEL_METAPACKAGES=$(dpkg-query -W -f='${db:Status-Abbrev} ${Package}\n' 'linux-generic*' 2>/dev/null | awk '$1 == "ii" { print $2 }' | sort -V); apt-cache policy $KERNEL_METAPACKAGES
```

Compare `Installed` with the metapackage version you approved for installation. If it did not reach that version, inspect APT’s output and package state. `Candidate` may change when repository metadata changes, so a later mismatch alone does not establish why an upgrade failed.

<Note>
The metapackage assignment is repeated because the reboot ended the shell session that held it. Metapackage and kernel release versions use different formats: the examples above show `5.15.0.190.169` and `5.15.0-190-generic`. Check your actual package dependencies and intended kernel release rather than relying on one matching number.
</Note>

Finally, confirm the GPUs came back:

```bash
nvidia-smi
```

<Check>
When the intended kernel is running, the selected metapackages have the expected versions, and the expected GPUs are visible, record the kernel version and date in your maintenance log. Before returning to service, also check the services, storage and connectivity affected by the maintenance. The next package check reads the current APT state rather than relying on the log.
</Check>

## Recovery

Both paths end in a reboot. These two sections cover the ways that reboot goes
wrong, and they apply whichever path you took.

### If the machine booted the old kernel

If `uname -r` differs from the kernel you intended to boot, inspect the
installed kernel files and boot configuration. Matching `Installed` and
`Candidate` values describe the selected metapackage state; they do not by
themselves prove which kernel booted or that the upgrade completed correctly.

If the machine is reachable over SSH, begin by inspecting the kernel files and boot configuration remotely. Keep console access available in case a later repair or reboot requires it.

Start with the entry GRUB is configured to boot. `grub-mkconfig` reads
`/etc/default/grub` first and then every `/etc/default/grub.d/*.cfg`, so a
drop-in overrides the main file and reading the main file alone can show you a
value that is not the one in effect. Resolve it the way `grub-mkconfig` does:

```bash
bash -c '. /etc/default/grub; shopt -s nullglob; for f in /etc/default/grub.d/*.cfg; do . "$f"; done; echo "GRUB_DEFAULT=$GRUB_DEFAULT"; echo "GRUB_SAVEDEFAULT=$GRUB_SAVEDEFAULT"'
```

A standard setup that boots the first generated menu entry may show:

```
GRUB_DEFAULT=0
GRUB_SAVEDEFAULT=
```

Entry `0` is the first entry in the generated menu. GRUB normally creates a
top-level entry for the highest-version kernel it finds, but custom entries
and boot-time overrides can change what starts. Inspect the generated menu
before choosing an entry.

`GRUB_DEFAULT=saved` selects the saved menu entry. With `GRUB_SAVEDEFAULT=true`, selecting an entry can save it for later boots; an explicitly saved or version-specific entry can therefore keep selecting an older kernel. A numeric index selects that position in the generated menu, so inspect the actual entries rather than assuming it always names one kernel:

```
GRUB_DEFAULT="Advanced options for Ubuntu>Ubuntu, with Linux 5.15.0-25-generic"
```

Find which file sets it, since that is the file to edit:

```bash
grep -rE '^GRUB_DEFAULT=' /etc/default/grub /etc/default/grub.d/
```

If the intended kernel is the first generated entry, set `GRUB_DEFAULT` to
`0`, keeping a copy of the configuration first:

```bash
([ -f /etc/default/grub.bak ] || sudo cp /etc/default/grub /etc/default/grub.bak) && sudo sed -i 's/^GRUB_DEFAULT=.*/GRUB_DEFAULT=0/' /etc/default/grub && grep '^GRUB_DEFAULT=' /etc/default/grub
```

The backup is only taken when there is not one already, so running this a second
time keeps the copy of the original rather than overwriting it with the edited
file.

<Note>
`GRUB_SAVEDEFAULT` only has an effect when `GRUB_DEFAULT=saved`, so once the
default is `0` it can stay as it is.
</Note>

If the grep listed a file under `/etc/default/grub.d/`, correct `GRUB_DEFAULT`
there as well. That file is sourced after the main one, so leaving it alone
means it overrides the edit you just made.

Editing the configuration changes nothing on its own. Regenerate the menu:

```bash
sudo update-grub
```

Check the output for the intended kernel and its matching initrd. Investigate
errors or missing files before rebooting:

```
Found linux image: /boot/vmlinuz-5.15.0-190-generic
Found initrd image: /boot/initrd.img-5.15.0-190-generic
Found linux image: /boot/vmlinuz-5.15.0-25-generic
Found initrd image: /boot/initrd.img-5.15.0-25-generic
```

If the intended kernel or its menu entry is missing, stop and inspect the generation errors and actual GRUB menu before rebooting. Check that `/boot` is mounted and that the expected `/boot/vmlinuz-<version>` and `/boot/initrd.img-<version>` files exist. Correct the cause, regenerate the menu, and verify the intended entry before proceeding.

<Warning>
Booting the corrected default takes another reboot, which stops every running
instance. Confirm you are inside a maintenance window before you run it.
</Warning>

```bash
sudo reboot
```

Then repeat step 5 and confirm that `uname -r` reports the kernel you intended
to boot. Investigate a mismatch before returning the machine to service.

### If the machine does not come back

You need access that does not go through SSH: the machine's IPMI, iDRAC, iLO, or
other BMC console, or a monitor and keyboard attached to it.

If a known working previous kernel is still installed and present in the
GRUB menu, try booting it from the console. Holding **Shift** or pressing **Esc**
may reveal the menu, depending on the firmware and GRUB settings. Under
**Advanced options for Ubuntu**, choose the entry for that kernel; its exact
title and version depend on your installation.

If the previous kernel boots successfully, keep the machine on it while investigating why the intended kernel failed. The newer kernel files can remain installed; do not select them again until you understand the failure. If neither entry boots, use the console error output to continue diagnosis.

<Warning>
If the machine boots but `nvidia-smi` reports `NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver`, inspect the module and kernel logs. A missing or failed-to-load module, driver conflict or module-signing problem can cause this message; it does not by itself prove a DKMS rebuild failure. See [Offline Machine](/host/machine-offline) for the next diagnostic checks.
</Warning>
