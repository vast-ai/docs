Self-test checks a listed machine against the CLI’s preflight requirements and attempts a temporary diagnostic rental. It does not by itself establish platform verification or readiness for every renter workload.

<Note>
Passing self-test is one part of preparing for verification; the machine must also meet the published [verification requirements](/host/verification-stages#additional-requirements-for-verification). A pass does not guarantee verification, search placement or rentals.
</Note>

## Before You Run It

- Install the [Vast CLI](https://cloud.vast.ai/cli/), then follow [CLI Hello World](/cli/hello-world) to authenticate and verify the installation. For host-oriented command guidance, see [Host CLI/API/SDK](/host/cli-api-sdk).
- Set the API key for the host-enabled account that owns the machine. For host key guidance, see [Host Account Security](/host/account-security-for-hosts).
- List the machine.
- Make sure no client is actively renting it.
- Run from outside the host LAN when testing ports, such as a cloud VM or mobile connection. Same-LAN tests can be confused by NAT hairpinning.

```bash
vastai set api-key <API_KEY>
```

## What Self-Test Checks

The CLI checks for a rentable offer and evaluates its reported requirements. If those checks allow the run, it attempts a temporary diagnostic rental, starts the selected image, polls progress and reports the result. It also attempts to destroy the temporary instance. If cleanup reports a failure, follow the displayed instructions to check and remove the remaining test instance.

Before attempting the temporary diagnostic rental, the CLI looks for a rentable offer and checks its reported requirements:

- The machine has a rentable offer.
- The API request can find a rentable offer. If no offer is found, diagnostics may query the machine and report access errors.
- Reliability is greater than `0.90`.
- CUDA compatibility is `>= 11.8`.
- Direct ports are at least 3 ports per listed GPU.
- PCIe bandwidth is greater than 2.85 GB/s.
- Upload/download bandwidth meet the VRAM-scaled requirement.
- GPU VRAM is greater than 7 GiB per GPU.
- System RAM is close to total GPU VRAM, capped around 2 TB for very high-VRAM machines.

These are diagnostic preflight checks implemented by the CLI. Compare the [Self-Test Reference](/host/self-test-reference) with the published [verification requirements](/host/verification-stages#additional-requirements-for-verification); a difference needs source/version clarification and does not change the check your installed tester executes.

The CLI and temporary self-test image perform checks that include:

- HTTPS progress endpoint reachability.
- UDP forwarding needs a separate check; the pinned CLI and self-test image do not perform a UDP echo test.
- PyTorch/CUDA import and GPU visibility.
- For each visible GPU, PyTorch allocated plus reserved memory must be at most 2% of its reported VRAM.
- Total system RAM meeting the image’s minimum requirement.
- The image requires at least two physical CPU cores per visible GPU, using `psutil.cpu_count(logical=False)`.
- CUDA ResNet workload across all visible GPUs.
- GPU memory allocation targeting about 95% of each visible GPU’s VRAM. The stage is named “ECC” in the output, but it does not test ECC error correction.
- NCCL initialization and synchronization across visible GPUs; see [`nccl_failed`](/host/self-test-reference#nccl-failed) if this stage fails.
- `stress-ng` and `gpu-burn` running together for 60 seconds.

Hyperthreads and logical CPUs do not count as physical cores.

## Run The Test

<Frame caption="The Machines list exposes the Test machine action for a listed host.">
  ![Test machine action in the Machines list](/images/host-self-test-machine-menu.webp)
</Frame>

<Frame caption="Self-Test confirmation dialog before starting the diagnostic run.">
  ![Self-Test confirmation dialog](/images/host-self-test-status.webp)
</Frame>

Run:

```bash
vastai self-test machine <machine_id>
```

To choose where failure bundles are saved:

```bash
vastai self-test machine <machine_id> \
  --support-bundle-dir /path/to/output
```

Do not paste API keys or account-specific commands into public channels.

If the test passes, the CLI reports success.

If it fails, look up the exact error in the [Self-Test Reference](/host/self-test-reference), fix the cause, and rerun.

## Machine Not Found Or Not Rentable

Check:

- The machine is listed.
- There are active offers.
- The account owns the machine.
- Reliability is above the gate unless using diagnostic mode.
- The Machines page has no red errors.
- Upload speed, download speed, RAM, and ports are populated.

See [Self-Test Reference: machine not rentable](/host/self-test-reference#machine-not-rentable).

## Fresh Install Self-Test

The installer can start self-test automatically after the daemon comes online. On a fresh host, it may wait about 10 minutes before listing the machine and starting the temporary diagnostic instance.

On the host, watch only for the planned self-test window; press `Ctrl+C` when the self-test ends and confirm that `tail` exits:

```bash
sudo tail -f /var/lib/vastai_kaalia/self_test.log
```

When the installer’s helper reaches its self-test command, it uses `--ignore-requirements` regardless of the current reliability value. Treat that result as diagnostic; it does not qualify the machine for verification.

## Ignore Requirements Mode

Use `--ignore-requirements` only to diagnose rentability or runtime behavior. A pass in this mode does not mean the machine meets verification requirements.

<Warning>
Even with `--ignore-requirements`, the machine still needs at least three direct open ports or self-test can fail.
</Warning>
