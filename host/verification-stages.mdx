Vast’s [published verification guidance](https://github.com/vast-ai/docs/blob/175a318c27750ea64da94f043dda39ec5cb26259/host/hosting-overview.mdx#L257-L259) describes ordinary host verification as fully automated, with no manual intervention.

## Lifecycle

Machines move between:

```text
Unverified -> Verified
Verified -> Deverified (active machine error)
Deverified -> Verified (error cleared)
```

Automation evaluates reliability, performance, hardware, network, and current marketplace demand.

<Note>
Top-tier AI GPUs are prioritized for verification because demand for them is
highest. This includes datacenter GPUs such as B300, B200, H200, and H100,
and dense premium builds such as RTX PRO 6000 (Server/WS/Max-Q),
8x RTX 5090, and 8x RTX 4090.
</Note>

## Listing Minimums

Start with [Supported Hardware](/host/supported-hardware) when planning a machine. Listing a machine and passing Self-Test do not guarantee verification; review the verification requirements below before preparing hardware.

## Verification Requirements

Your machine must meet all of the following.

### GPU

| Requirement | Minimum |
| --- | --- |
| GPU | NVIDIA, Maxwell or newer |
| VRAM per GPU | More than 7 GB |
| CUDA version | 11.8 or newer |
| GPU models | All identical, do not mix models in one machine |
| PCIe bandwidth | More than 2.85 GiB/s per GPU |

### CPU

| Requirement | Minimum |
| --- | --- |
| CPU architecture | x86_64 or ARM64 |
| Instruction set | Use an AVX-capable x86_64 CPU. For ARM64, clarify the published AVX requirement with Vast before choosing the hardware. |
| Physical CPU cores | 2 per GPU |

<Note>
The public [Host Setup guide](https://cloud.vast.ai/host/setup) lists CUDA 12.6 or newer for ARM64. The pinned Self-Test image build supports CUDA 11.8 on `linux/amd64`; its CUDA 12.8 and newer variants also target `linux/arm64`. These image build targets do not establish which ARM64 hosts or GPUs are eligible for platform verification.
</Note>

### Memory

| Requirement | Minimum |
| --- | --- |
| System RAM | At least 95% of total GPU VRAM |

<Note>
**Formula:** system RAM >= 0.95 x VRAM per GPU x number of GPUs

**Example:** 8 x RTX PRO 6000 (96 GB) means the min system RAM >= 0.95 x
96 GB x 8 = 730 GB
</Note>

### Network

| Requirement | Minimum |
| --- | --- |
| Download speed | 500 Mbps |
| Upload speed | 500 Mbps |
| Connection type | Wired Ethernet, fiber recommended |
| Public IP | Public IPv4 address |
| Forwarded ports | 5 ports per GPU, 100 ports per GPU recommended |

<Warning>
Verification guidance requires a public IPv4 address with the port range forwarded to the machine. CGNAT and shared ISP IPs are not supported for this configuration.
</Warning>

### Operating System

| Requirement | Minimum |
| --- | --- |
| Operating system | Ubuntu Server 22.04 LTS, 24.04 LTS recommended |
| Kernel | Latest security patch level for your Ubuntu release |
| NVIDIA driver | A currently supported release for your GPU |
| SSH login | SSH keys only, password authentication disabled |
| SSH access keys | A unique key pair per machine, never shared or reused |
| Secure Boot | Recommended: disable before installing the NVIDIA driver |

<Note>
Use a server edition. Desktop editions are not supported.
</Note>

<Note>
Keeping the kernel patched is the host's responsibility. "Latest security patch
level" means the newest patch for the LTS release you are on, not a release
upgrade. Machines running a kernel with a known exploited vulnerability are
restricted on the marketplace and can lose verification. See
[Upgrade the Kernel](/host/upgrade-kernel).
</Note>

<Warning>
SSH password login must be disabled for security. SSH password login enabled
will fail verification. See
[Disable SSH Password Login](/host/disable-ssh-password-login).
</Warning>

<Warning>
Use a separate SSH key pair for each machine you operate. If a reused private key is compromised, every machine that trusts that key may be exposed; separate keys limit that shared access.
</Warning>

### Storage

| Requirement | Minimum |
| --- | --- |
| Storage type | SSD |
| Dedicated partition for Docker container storage | 200 GB |
| Root partition free space | 20 GB |

### Reliability

| Requirement | Minimum |
| --- | --- |
| Reliability score | Over 90% |

<Note>
Reliability starts low on a new machine and grows the longer the machine
stays online. A stable machine typically reaches 90% within a few days.
</Note>

### Self-Test

Use Self-Test to check the CLI’s preflight requirements and run its diagnostic workload. Review the published verification requirements separately. See [How to Self-Test](/host/how-to-self-test).

<Warning>
**Keep the machine dedicated to Vast workloads.** Avoid local mining, gaming, desktop use or other jobs that compete with renter work. Run permitted jobs through the Jobs tab or `create job`. See [Workload Policy](/host/workload-policy).
</Warning>

<Tip>
Meeting these minimum requirements makes your machine eligible for verification, but does not automatically guarantee verification. [Read more about verification](/host/understanding-verification).
</Tip>

The [generated Self-Test Reference](/host/self-test-reference) describes the checks in its pinned CLI and test-image revisions. Those checks are not a substitute for the platform requirements on this page.

<Note>
Meeting requirements makes the machine eligible. It does not guarantee immediate verification, search placement, or rentals.
</Note>

## Unverified

Unverified means the machine is new, under evaluation, or not currently meeting verification conditions.

Do:

- Pass [self-test](/host/how-to-self-test).
- Keep uptime stable.
- Fix driver, network, storage, and daemon errors.
- Avoid background workloads outside the Jobs tab or `create job`.

Avoid unnecessary reboots or hardware/config changes during evaluation.

## Verified

Verified means the machine passed automated checks and currently meets platform standards.

Keep it verified by:

- Monitoring thermals, power, drivers, Docker, and daemon health.
- Keeping networking stable and reachable.
- Avoiding hardware reductions after the machine is created.
- Responding quickly to red machine errors.

## Deverified

Vast’s [published verification guidance](https://github.com/vast-ai/docs/blob/175a318c27750ea64da94f043dda39ec5cb26259/host/hosting-overview.mdx#L281-L285) says an active error causes deverification; the machine is verified again once that error clears. A reliability drop alone does not remove verification.

Common causes:

- Network instability, closed ports or low bandwidth reported as an active machine error.
- GPU, NVML, Xid, PCIe, power, thermal or storage problems reported as an active machine error.
- Machine-level Docker or NVIDIA runtime errors, such as `unknown or invalid runtime nvidia`; some per-instance launch failures are logged without affecting verification.
- Active machine errors, as described in Vast’s [published verification guidance](https://github.com/vast-ai/docs/blob/175a318c27750ea64da94f043dda39ec5cb26259/host/hosting-overview.mdx#L281-L285).
- An administrator-set machine error, such as a machine flagged for investigation.

Fix the underlying issue and monitor the machine’s error and status. Some errors clear automatically after the platform detects recovery; others may need a Vast.ai team member to inspect and clear them. Clearing an error is distinct from manually selecting a machine for verification.
