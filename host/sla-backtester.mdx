The **SLA (Service Level Agreement) earnings backtester** is for hosts. Renters should use [SLA](/guides/instances/choosing/sla-coverage).

How much could SLA settlement cost given your reliability commitment and confidence? Use the console preview on [SLA Offers](/host/sla-offers#web-console), or the API backtester on this page.

## Choose your path

| If you want to… | Use |
| --- | --- |
| Preview SLA on a machine that already has rental history | Web console (**Set Pricing → SLA**) — no API key. A new machine has nothing to replay. |
| New machine, no rental history | No preview of your own fee until you enable SLA. Use the [economics walkthrough](/host/sla-offers#economics-walkthrough) as an estimate. After **Save**, check the **SLA Fee** from a separate client account. |
| Simulate historical earnings for one machine | This page's single-machine `curl` example |
| Review many machines at once | [Fleet workflow](#fleet-workflow) below (advanced; Linux/macOS + `jq`) |

**Console hosts:** the console preview replays rental history. A new machine shows "No historical data available for this machine yet." You do not need this API to list. Use the [economics walkthrough](/host/sla-offers#economics-walkthrough) before you have history.

**API hosts:** this endpoint replays your machine's **real historical compute earnings and uptime** through the same SLA settlement used in production, under the SLA terms you choose. Query parameters `r_claim` (reliability commitment), `p` (confidence), and the optional `r_target` (simulated renter target) are defined under [Query parameters](#query-parameters).

<Note>
**Don't want to use the API?** The backtester is optional. It needs rental history, and so does the console preview. Before you have history, use the [economics walkthrough](/host/sla-offers#economics-walkthrough).
</Note>

## When to use it

Use the backtester before you enable SLA on a listing, or when you want to tune parameters. The machine needs at least a few weeks of rental history. Older windows may have no recorded SLA history. If `has_data` is `false`, move the window toward the present or pick a machine with more recent rental activity. Widening the window further into the past does not help.

Use the backtester to:

- Pick a reliability commitment and confidence before you enable SLA on a listing
- See how SLA fees and service credits change when renters choose a lower target than your commitment
- Find your **break-even reliability** (`r_be`): the reliability below which SLA would have cost you money

For how SLA offers work once listed, see [SLA Offers](/host/sla-offers).

## How it works

1. You choose a machine, a date range, your reliability commitment (`r_claim`), your confidence (`p`), and optionally a simulated renter target (`r_target`).
2. The API loads your machine's per-day compute earnings and uptime for the range.
3. It replays those days as **one simulated SLA contract** through production SLA settlement.
4. It returns one row per UTC day showing the money that moved that day, plus two summary reliabilities (`r_eff`, `r_be`).

<a id="how-sla-money-moves"></a>
**How SLA money moves.** On an SLA contract, the renter's daily compute payment and SLA fee go into an SLA escrow for that contract. Escrow pays service credits to the renter and releases the rest to you. Each row in `days` shows those four flows for one day. Over the full window, what went in equals what came out, so your **net SLA result** is the SLA fees paid in minus the service credits paid out.

**Simulated vs live renters.** If you omit `r_target`, the simulation assumes the renter targeted your full reliability commitment (`r_target = r_claim`). That is a conservative what-if: it produces the highest SLA fees and the most credit exposure. Live renters choose their own targets, often below your commitment. Pass `r_target` (for example `0.95` with `r_claim=0.99`) to model those renters.

**Active vs idle days.** Days with no rental earnings appear as rows with all flows `0` and `reliability: null`. They are not outages: the simulated contract simply pauses.

<a id="simulation-limits"></a>
<Note>
**Simulation limits**
- The replay treats all historical compute as one SLA contract, so it overstates fees and credits when few renters chose SLA. The whole machine is replayed as one contract. Live settlement runs per rental contract, so several concurrent SLA renters on a sliced machine can produce more credits on one day than the simulation shows. Pair this output with [SLA and GPU slicing](/host/sla-offers#sla-and-gpu-slicing).
- **Days that already had SLA rentals are under-counted.** Compute earned on SLA contracts is stored separately from `gpu`, `storage`, and bandwidth, and the replay does not add it back. On those days the simulated fees and credits are too low. Run the backtester before you enable SLA, or on a window with no SLA rentals.
- For renter-visible pricing (`dph_total`), use **Set Pricing → SLA** in the console or a REST search with a realistic `target_reliability` (the CLI cannot send `target_reliability` today).
- How recent versus long-term uptime is weighted is set automatically from the renter target. It is not a host setting; the value used is echoed in `params.beta`.
</Note>

## Before you start

**Prerequisites:** an API key with `machine_read` permission, your machine ID, and `curl` (or Postman). On Windows, use WSL or Postman. The machine ID is the same number as `machid` on the earnings API and `machine` in listing requests.

1. Open **Account → API Keys** in the console and create a key with **`machine_read`** enabled.
2. Use `Authorization: Bearer YOUR_API_KEY` in the examples below. See [Create API Key](/api-reference/accounts/create-api-key) and [Authentication](/api-reference/authentication).
3. Find your machine ID on the [Host Machines page](https://cloud.vast.ai/host/machines). With no rental history the backtester returns `has_data: false`. If **Set Pricing** has no **SLA** section, see [checklist step 4](/host/sla-offers#sla-host-checklist). This backtester does not return `sla_not_approved`. That error comes from listing.
4. Run the baseline request in [Example request](#example-request) and check `has_data` in the response.

## API reference

<Note>
The backtester is available through the REST API only, for hosts. You must own the machine and use an API key with **`machine_read`** permission. The Python SDK does not support the backtester; use the `curl` examples below.
</Note>

```
GET /api/v0/host/sla_backtest/
```

Requires Bearer authentication. Rate-limited to about one request every two seconds (`x-rate-limit` threshold `2.0`); see [Rate Limits and Errors](/api-reference/rate-limits-and-errors).

### Query parameters

| Parameter | Required | Description |
| --- | --- | --- |
| `machine_id` | Yes | ID of your machine |
| `r_claim` | Yes | Reliability commitment to simulate (the `sla_r_claim` you plan to list), greater than 0 and at most `0.99999`. Example: `0.99` = 99%. |
| `p` | No | Host confidence, greater than 0 and less than 1. Uses a different scale from listing `sla_sigma_x` — see [Confidence values](#confidence-values-p). Default: `0.6667` (console **Medium**; Normal band). |
| `r_target` | No | Renter reliability target to simulate. Must be greater than 0 and at most `r_claim`. Default: `r_claim`. |
| `start_date` | No | Range start as Unix epoch seconds. Default: 90 days before `end_date`. |
| `end_date` | No | Range end as Unix epoch seconds. Default: now. |

`beta` is not a host setting. If you send it, it must be between 0 and 1. Any valid value is ignored, and the value actually used is echoed in `params.beta`. Any other unknown query parameter is rejected with `400 bad_request`. The older `r` and `reliability` parameters are no longer accepted; use `r_claim` (and `r_target`).

### Limits

| Limit | Value |
| --- | --- |
| Default lookback | 90 days before `end_date` (91 inclusive UTC-day rows; today's row is usually empty) |
| Maximum range | 366 days (inclusive) |
| Ownership | Must own the machine |
| Rate limit | About one request every two seconds |

### Example request

Baseline (default 90-day lookback, renter target = your commitment):

```bash
curl -s -H "Authorization: Bearer YOUR_API_KEY" \
  "https://console.vast.ai/api/v0/host/sla_backtest/?machine_id=12345&r_claim=0.99&p=0.6667"
```

Model renters who choose a 95% target against your 99% commitment:

```bash
curl -s -H "Authorization: Bearer YOUR_API_KEY" \
  "https://console.vast.ai/api/v0/host/sla_backtest/?machine_id=12345&r_claim=0.99&r_target=0.95&p=0.6667"
```

Custom date range:

```bash
# Linux (GNU date). macOS: start=$(date -u -v-90d +%s)
start=$(date -u -d '90 days ago' +%s)
end=$(date -u +%s)
curl -s -H "Authorization: Bearer YOUR_API_KEY" \
  "https://console.vast.ai/api/v0/host/sla_backtest/?machine_id=12345&r_claim=0.99&p=0.6667&start_date=$start&end_date=$end"
```

Compare two confidence levels on the same history:

```bash
# Medium (p=0.6667)
curl -s -H "Authorization: Bearer YOUR_API_KEY" \
  "https://console.vast.ai/api/v0/host/sla_backtest/?machine_id=12345&r_claim=0.99&p=0.6667"

# p=0.50 (Low): recommended starting confidence when you first enable SLA. A machine with no rental history returns has_data false.
# Renters pay a higher SLA fee. Credit rules are the same.
curl -s -H "Authorization: Bearer YOUR_API_KEY" \
  "https://console.vast.ai/api/v0/host/sla_backtest/?machine_id=12345&r_claim=0.99&p=0.50"
```

## Reading the response

**If you only read three things:** check `has_data` (if `false`, move the window toward the present or wait for more rental history), compare `r_eff` with `r_be`, then look at your [net SLA result and largest single-day credit](#summarize-with-jq).

A successful response looks like this (one `days` row shown). These numbers are an illustrative response to the baseline request above (`r_claim=0.99`, `p=0.6667`, `r_target=0.99`). They match the OpenAPI example. They are not the `$0.97/day` walkthrough on the host SLA page.

```json
{
  "success": true,
  "machine_id": 12345,
  "has_data": true,
  "start_day": 20567,
  "end_day": 20657,
  "r_eff": 0.9987,
  "r_be": 0.9712,
  "days": [
    {
      "day": 20567,
      "client_compute_to_escrow": 78.12,
      "client_premium_to_escrow": 0.19,
      "escrow_to_client_balance": 0.0,
      "escrow_to_host_balance": 76.4,
      "reliability": 1.0
    }
  ],
  "params": {
    "r_claim": 0.99,
    "r_target": 0.99,
    "beta": 0.46,
    "p": 0.6667
  }
}
```

### Top-level fields

| Field | Meaning |
| --- | --- |
| `has_data` | `true` if the range had at least one day of rental activity to replay. `false` means no usable history in the window. Move the window toward the present, or wait for more rental history. Older windows may have no recorded SLA history. When `false`, every `days` row is zero with `reliability: null`, and `r_eff` is `null`. |
| `start_day`, `end_day` | UTC day indices, `day = floor(epoch_seconds / 86400)`. `day × 86400` is exactly 00:00 UTC on that date. Convert with `date -u -d "@$((day * 86400))" +%F` (Linux) or `date -u -r $((day * 86400)) +%F` (macOS). Show Earnings `sday` / `eday` use the same day index. |
| `r_eff` | **Effective reliability**: the constant reliability that would have produced the service credits paid in this window. `null` when nothing was paid into escrow in the window (all `client_*_to_escrow` values are zero, as with `has_data: false`). |
| `r_be` | **Break-even reliability**: the reliability at which SLA fees and service credits cancel out. Always present. |
| `days` | One row per UTC day from `start_day` to `end_day` (see below). |
| `params` | The SLA terms the replay actually used: `r_claim`, `r_target` (after defaulting), `p`, and the automatically derived `beta`. |

**`r_eff` vs `r_be`:** if `r_eff` is above `r_be`, SLA would have been net positive for you over this window (fees exceeded credits). If it is below, SLA would have cost you money. The gap tells you how much reliability headroom you had.

### Per-day fields (`days`)

Every value is money (in $) that moved on that day. All flows are zero or positive.

| Field | Meaning |
| --- | --- |
| `day` | UTC day index |
| `client_compute_to_escrow` | The renter's compute payment for the day, net of the platform fee, held in escrow (what would reach you if there were no credits) |
| `client_premium_to_escrow` | The SLA fee paid in for the day |
| `escrow_to_client_balance` | Service credits paid to the renter that day |
| `escrow_to_host_balance` | Money released from escrow to you that day |
| `reliability` | Raw measured uptime fraction for the day (0–1), or `null` when the machine had no rental data that day |

`reliability` is that day's raw uptime. Credits settle on the blended recent-plus-longer-term measure (see [SLA in plain language](/host/sla-offers#sla-in-plain-language)), so a day can carry a credit even when its `reliability` is at or above `r_target`.

Releases to you are spread over time rather than paid out the same day, and the final active day includes the contract's closing settlement. Read individual days as cash movement, not as that day's profit or loss.

### Summarize with jq

```bash
curl -s -H "Authorization: Bearer YOUR_API_KEY" \
  "https://console.vast.ai/api/v0/host/sla_backtest/?machine_id=12345&r_claim=0.99&r_target=0.95&p=0.6667" \
  | jq '{has_data, r_eff, r_be,
         sla_fees:   ([.days[].client_premium_to_escrow] | add),
         credits:    ([.days[].escrow_to_client_balance] | add),
         net_sla:    (([.days[].client_premium_to_escrow] | add) - ([.days[].escrow_to_client_balance] | add)),
         largest_day_credit: ([.days[].escrow_to_client_balance] | max)}'
```

- **`net_sla`** — SLA fees minus service credits over the window. Positive means SLA would have added income.
- **`largest_day_credit`** — the most credit paid out on any single day. Use it as your single-day tail-risk reference. The largest value often falls on the last active day, because that day includes the contract's closing settlement.

## Interpreting results

### `r_eff` well above `r_be`

Your historical reliability was strong relative to the simulated target. SLA would likely have been net positive: small fees on most days and few credits.

### `r_eff` close to `r_be`

Break-even territory: fees and credits roughly balance. A few bad days would tip you negative.

### `r_eff` below `r_be`

Under these terms, SLA would have cost you money over this window. Improve reliability, lower your reliability commitment, or move **Confidence** toward **Low** (wider margin, larger fee) before listing.

### Large `largest_day_credit`

A single outage day can cost far more than many days of fees. Check that you can absorb this amount, and remember it is a machine-level figure: concurrent SLA renters on a sliced machine can add up to more.

## Confidence values (`p`)

<Warning>
**`p` and `sla_sigma_x` use different scales** — do not copy numeric values between them. For example, `p=0.5` (Wide) maps to `sla_sigma_x ≈ 1.0`, not `0.5`. Use the table below to translate between the two.
</Warning>

The two values are exactly related: `p = 1 / (1 + sla_sigma_x)`, and `sla_sigma_x = 1/p − 1`. To backtest a custom `sla_sigma_x`, pass `p = 1/(1 + sla_sigma_x)` (for example `sla_sigma_x` 0.3 → `p` 0.7692). `sla_sigma_x` is capped at 3.0, so any `p` at or below 0.25 behaves like `p=0.25`.

| Confidence `p` | Console | Band | Listing equivalent |
| --- | --- | --- | --- |
| `0.8333` | High | Tight | `sla_sigma_x ≈ 0.2` |
| `0.6667` | Medium (default) | Normal | `sla_sigma_x ≈ 0.5` |
| `0.50` | Low | Wide | `sla_sigma_x ≈ 1.0` |

Tighter confidence (higher `p`) lowers the SLA fee renters pay. It does **not** reduce the credit owed on a miss.

## Error responses

| HTTP | `error` | Cause |
| --- | --- | --- |
| 400 | `bad_request` | Missing `r_claim`, an out-of-range value, or an unknown parameter (for example the old `r` or `reliability`) |
| 400 | `invalid_params` | The SLA terms don't combine, for example `r_target` greater than `r_claim` |
| 400 | `invalid_range` | `start_date` is after `end_date` |
| 400 | `range_too_large` | The window is longer than 366 days |
| 401 | `auth_error` | Unknown or invalid API key. |
| 401 | *(no `error` field)* | The key is valid but lacks `machine_read`. `success` is `false` and `msg` names the missing permission. |
| 403 | `auth_error` | No `Authorization` header ("This action requires login.") |
| 403 | `not_owner` | The machine belongs to another host |
| 403 | `sla_disabled` | SLA is not currently enabled on the platform. Try again later or contact support. |
| 404 | `machine_not_found` | Invalid `machine_id` |
| 404 | `auth_error` | Malformed API key (wrong length) |
| 429 | `HTTPTooManyRequests` | JSON body and a `Retry-After` header. Wait at least that long (otherwise at least two seconds) and retry. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors). |

## Recommended workflow

1. **Run a baseline** on a machine with at least a few weeks of rental history, with `r_claim` set to the commitment you plan to list and `p=0.6667` (Medium). If this machine already has rental history and you are about to enable SLA, also run `p=0.50` (Low), the recommended starting confidence. A machine with no rental history returns `has_data: false`. There is nothing to replay. If `has_data` is `false` on a machine that has been rented, move the date range toward the present. Don't rely on the dashboard reliability score alone (see [Machine reliability score vs SLA reliability](/host/sla-offers#machine-reliability-score-vs-sla-reliability)).
2. **Compare `r_eff` with `r_be`** to see whether you had headroom.
3. **Add `r_target`** at the targets renters are likely to choose (for example `0.95`) and compare `net_sla`.
4. **Check `largest_day_credit`** — can you absorb that from one bad day?
5. **List with `sla_r_claim`** and `sla_sigma_x` on the offer; renters choose their own targets in search (see [SLA Offers](/host/sla-offers)).

## Fleet workflow

Optional, for API automation only. To check one machine, use the single-machine request above. `vastai show machines --raw` leaves out machines offline for more than about 10 hours. To include them (up to about 3 days), list machines with `GET /api/v0/machines/?include_offline=true`. For machines that already have SLA enabled, the replay under-counts days that already had SLA rentals. Treat `largest_day_credit` as a lower bound. `net_sla` can be off in either direction, because both fees and credits are understated. For a cleaner estimate, set `START` and `END` (Unix seconds) to a window from before SLA was enabled, and set `T` to the renter target you want to model (for example `0.95`, and not above the commitment you send). See [Simulation limits](#simulation-limits).

**Prerequisites:** [CLI hello world](/cli/hello-world) and an API key with `machine_read` (see [API permissions](/api-reference/permissions)).

1. Run backtests **sequentially**, one machine at a time:
   - The loop reads each machine's `sla_reliability_claim` and `sla_confidence` label from `show machines`.
   - For machines whose terms are not visible, set `R` (commitment) and `P` (confidence `p`) as fallbacks. That covers machines without SLA yet, and machines whose terms are hidden because they are unlisted, have an outdated daemon, or lack SLA approval. The loop logs every fallback it uses, so check those rows before trusting them.
   - Machines missing either value, with no `R`/`P` fallback, are skipped and logged.
   - The confidence label is a band. The loop uses one `p` per band: `high` → 0.8333 (console **High**, σ 0.2), `medium` → 0.6667 (console **Medium**, σ 0.5), `low` → 0.50 (console **Low**, σ 1.0). `low` covers every σ above 0.71, so a machine listed at σ 2.0 is backtested at `p` 0.50, not at its real `p`. For an exact value, use the single-machine request with `p = 1/(1 + sla_sigma_x)`.
2. Responses are written to a private temp directory that is deleted when the loop exits.

```bash
: "${VAST_API_KEY:?export VAST_API_KEY first (needs machine_read)}"
# Optional fallbacks for machines without SLA yet (machines with SLA keep their own terms): R=0.99 P=0.6667
BT_DIR=$(mktemp -d)
trap 'rm -rf "$BT_DIR"' EXIT
# Optional: START and END are Unix seconds for a pre-SLA window. T is a renter target at or below the commitment.
extra=""
[ -n "${START:-}" ] && extra="${extra}&start_date=${START}"
[ -n "${END:-}" ] && extra="${extra}&end_date=${END}"
[ -n "${T:-}" ] && extra="${extra}&r_target=${T}"
# The CLI prints HTTP errors to stderr and exits 0. Check stdout, not $?.
machines=$(vastai show machines --raw --api-key "$VAST_API_KEY" 2>"$BT_DIR/cli.err")
printf '%s' "$machines" | jq -e '.machines | type == "array"' >/dev/null
if [ $? -ne 0 ]; then
  echo "show machines failed (check machine_read):" >&2
  cat "$BT_DIR/cli.err" >&2
  exit 1
fi
echo "note: machines offline more than about 10 hours are not in this list; compare the count with Host → Machines" >&2
for id in $(echo "$machines" | jq -r '.machines[].id'); do
  machine=$(echo "$machines" | jq -c --arg id "$id" \
    '.machines[] | select((.id|tostring) == $id)')
  # Treat 0 (SLA off) and null (terms hidden) as absent; R only fills in for those machines.
  r=$(echo "$machine" | jq -r '(.sla_reliability_claim // 0) | if . > 0 then . else empty end')
  used_r_fallback=0
  if [ -z "$r" ] && [ -n "${R:-}" ]; then r="$R"; used_r_fallback=1; echo "machine $id: using fallback R=$R" >&2; fi
  if ! jq -e -n --arg r "$r" 'try (($r | tonumber) > 0) catch false' >/dev/null 2>&1; then
    echo "skip $id: no SLA terms visible; set R=0.99 (or your planned commitment) as a fallback" >&2; continue
  fi
  # show machines returns confidence as a label: high = Tight, medium = Normal, low = Wide.
  # P only fills in for machines without SLA terms.
  # When R was used, the machine's SLA terms are off or hidden, so any confidence label is stale: use P.
  label=$(echo "$machine" | jq -r '.sla_confidence // empty')
  [ "$used_r_fallback" = 1 ] && label=""
  case "$label" in
    high)   p=0.8333 ;;
    medium) p=0.6667 ;;
    low)    p=0.50 ;;
    *)      p="${P:-}"
            [ -n "$p" ] && echo "machine $id: using fallback P=$P (sla_confidence null)" >&2 ;;
  esac
  if [ -z "$p" ]; then
    echo "skip $id: no sla_confidence; set P=0.6667 (Normal) to backtest before enabling SLA" >&2; continue
  fi
  out="$BT_DIR/sla_bt_$id.json"
  http=$(curl -s -o "$out" -w "%{http_code}" \
    -H "Authorization: Bearer $VAST_API_KEY" \
    "https://console.vast.ai/api/v0/host/sla_backtest/?machine_id=$id&r_claim=$r&p=$p${extra}")
  if [ "$http" != "200" ] || ! jq -e '.success == true' "$out" >/dev/null 2>&1; then
    echo "machine_id=$id failed http=$http body=$(jq -c '{success,error,msg}' "$out" 2>/dev/null)" >&2
    sleep 3; continue
  fi
  jq -c --arg id "$id" --arg start "${START:-}" --arg end "${END:-}" --arg t "${T:-}" '{machine_id: $id, params, has_data, r_eff, r_be,
      start_date: $start, end_date: $end, r_target: $t,
      net_sla: (([.days[].client_premium_to_escrow] | add) - ([.days[].escrow_to_client_balance] | add)),
      largest_day_credit: ([.days[].escrow_to_client_balance] | max)}' "$out"
  sleep 3
done
```

Expect about three seconds per machine (`sleep 3` plus request time), so budget a few minutes for 50 machines. The example logs a failure and moves on after one attempt. On HTTP **429**, wait and retry that machine before treating it as failed. Don't run requests in parallel unless you implement backoff. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors).

3. Compare `r_eff`, `r_be`, `net_sla`, and `largest_day_credit` across machines. Skip and failure messages go to stderr, so stdout is one JSON object per machine. Save the script as `bt.sh`, pass any fallbacks on the same line, and sort the results: `R=0.99 P=0.6667 bash bt.sh > results.jsonl && jq -s 'map(select(.has_data)) | sort_by(.net_sla)' results.jsonl`. Rows with `has_data: false` are left out of that sort. For machines that already have SLA on, the default window under-counts risk. See [Simulation limits](#simulation-limits).
4. Apply matching `sla_r_claim` / `sla_sigma_x` when listing via the API (see [SLA Offers](/host/sla-offers#api-for-automation)).

## When stuck

- **`has_data: false`** — Move the window toward the present, or wait for rental history. Widening it further into the past does not help. Older windows may have no recorded SLA history.
- **`400 bad_request` on a request that used to work** — Replace `r=` with `r_claim=` and remove `reliability=`.
- **`401` / `403 auth_error` / `404 auth_error`** — Check that the `Authorization: Bearer` header is present, the key is complete (64 characters), and it has `machine_read`.
- **Still stuck** — Ask in the [host Discord](https://discord.gg/hSuEbSQ4X8).
