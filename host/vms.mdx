Vast can run KVM virtual machines in addition to Docker containers. VM support is optional and depends heavily on hardware, BIOS, kernel, and GPU configuration.

<Warning>
VMs interact more directly with hardware than containers. Enable them only when the machine supports IOMMU and remains stable.
</Warning>

Default host onboarding should still start from the official [Vast host setup page](https://cloud.vast.ai/host/setup/). Use this page only for optional VM/IOMMU planning or troubleshooting after the normal host setup path is understood.

## When VM Support Helps

VM support can make a host visible to renters using VM templates and can help with workloads that need:

- Systemd, Docker Compose, Kubernetes, or Docker build workflows.
- Non-Linux OS images.
- `ptrace` tooling such as NVIDIA Nsight.

Consider VM support for single-GPU machines and suitable multi-GPU RTX 40-series hosts after reviewing disk, network and workload needs. For multi-GPU datacenter hosts, the published VM guide recommends waiting for better VM P2P/NVLink support.

## Tradeoffs

- IOMMU settings can reduce PCIe peer-to-peer performance on some multi-GPU systems.
- VMs can use more disk than containers.
- Hosts with VM support may need higher disk and bandwidth prices.

## Check VM Status

```bash
python3 /var/lib/vastai_kaalia/enable_vms.py check
```

Results:

| Status | Meaning |
| --- | --- |
| `on` | VM support is enabled. |
| `off` | VM support is disabled, a previous test failed, or the status helper could not read its configuration. |
| `pending` | The helper did not read a completed-attempt marker (`y`). The marker may be absent, unreadable, or contain a different value; this result alone does not establish when an enablement attempt will run. |

These values describe VM configuration state only. They do not confirm that the Host is idle or that a VM workload is healthy.

## Disable VM Support

<Warning>
Disabling VM support changes Host configuration and can disrupt running work. Prevent new rentals during the approved maintenance window, then confirm the machine has no active rentals or other workloads.
</Warning>

```bash
sudo python3 /var/lib/vastai_kaalia/enable_vms.py off
```

The command marks VM enablement disabled and removes the VM configuration entry when present. It does not stop workloads, end rentals, or verify that the Host is safe to change.

Run [Check VM Status](#check-vm-status) afterwards and confirm it reports `off`. Most hosts do not need to disable anything; unsupported machines are detected automatically.

## Hardware Requirements

VM support requires CPU/chipset support for Intel VT-d or AMD-Vi, plus BIOS virtualization support.

In BIOS, enable virtualization and IOMMU/VT-d/AMD-Vi options.

## Kernel Options

Edit `/etc/default/grub` without removing existing boot options. For the Intel example below, add `intel_iommu=on` and the Vast VM setting `nvidia_drm.modeset=0`:

```text
GRUB_CMDLINE_LINUX="intel_iommu=on nvidia_drm.modeset=0"
```

On AMD platforms, enable virtualization and IOMMU in firmware and verify IOMMU groups before retrying VM enablement. Supported AMD IOMMUs normally initialize without `amd_iommu=on`; Linux 6.8 does not implement that value. Follow the [Ubuntu IOMMU checks](https://ubuntu.com/server/docs/how-to/graphics/gpu-virtualization-with-qemu-kvm/) if groups are missing.

Some hosts may also need:

```text
rd.driver.blacklist=nouveau modprobe.blacklist=nouveau
```

During maintenance, after confirming there are no active rentals or other workloads, regenerate the GRUB configuration. Reboot only if that command succeeds:

```bash
sudo update-grub && sudo reboot
```

## Display Managers And GPU Processes

Disable display managers, XOrg/Wayland sessions, and background GPU processes. `nvidia-persistenced` is okay because it is managed by the host stack.

## Retry Enablement

If VM support is off and you want to retry after fixing the host:

<Warning>
This is a forced, state-changing setup retry—not a simple toggle. It can install VM packages, pull a test image, restart Host services, and run a GPU-passthrough test. Prevent new rentals during the approved maintenance window, then confirm there are no active rentals, containers, or GPU workloads.
</Warning>

```bash
sudo python3 /var/lib/vastai_kaalia/enable_vms.py on -f
```

Do not use process exit status alone as evidence of success. The helper can print an error such as `IOMMU groups not set up for VMs, aborting.` while exiting with status `0`.

After the command finishes, check the resulting state and basic Host health:

```bash
python3 /var/lib/vastai_kaalia/enable_vms.py check
nvidia-smi -L
systemctl is-active vastai.service docker.service
```

Require exact `on` status, the expected GPUs and an `active` result for each listed service before proceeding. These are basic configuration and Host-health checks, not proof that a VM workload is healthy. Stop and investigate `pending`, `off`, error or abort text, an unexpected status, a missing GPU or an inactive service. If IOMMU groups are missing, correct the BIOS and kernel configuration, reboot during maintenance, and verify the grouping before retrying.
