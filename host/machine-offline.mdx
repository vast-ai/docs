If your host machine appears **Offline**, follow the steps below in order to identify and resolve common connectivity, service, and GPU-related issues.

> **Important:** Do not reboot the machine, stop customer containers, force-stop VMs, or delete instance data while there are active rentals, unless instructed by Vast.ai Support. These actions may interrupt customer workloads.

## 1. Verify Internet Connectivity

Before checking Vast.ai-specific services, use the checks below to gather point-in-time evidence of outbound connectivity and DNS resolution. Compare each result with the explanation; passing these checks does not establish stable access to every Vast.ai endpoint.

### Check basic connectivity

This command sends 4 test packets directly to Cloudflare's public IP address (`1.1.1.1`). It tests reachability of that IP over ICMP while bypassing DNS. A successful result does not prove that DNS or every outbound service works; if the next check fails, treat name resolution and target reachability as separate signals to investigate.

```bash
ping -c 4 1.1.1.1
```

Expected result:

```
PING 1.1.1.1 (1.1.1.1) 56(84) bytes of data.
64 bytes from 1.1.1.1: icmp_seq=1 ttl=56 time=35.7 ms
64 bytes from 1.1.1.1: icmp_seq=2 ttl=56 time=36.0 ms
64 bytes from 1.1.1.1: icmp_seq=3 ttl=56 time=35.7 ms
64 bytes from 1.1.1.1: icmp_seq=4 ttl=56 time=35.9 ms

--- 1.1.1.1 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3005ms
rtt min/avg/max/mdev = 35.681/35.806/35.962/0.109 ms
```

What to look for: **`4 packets transmitted, 4 received, 0% packet loss`** shows that this ICMP test received replies. `100% packet loss`, `Network is unreachable`, or a hang is not conclusive proof of a general outbound outage: ICMP can be filtered, rate-limited, or blocked on one path. Compare it with the DNS and web-request checks below, then involve the network owner before changing cables, routing, or firewall configuration.

### Check DNS resolution

This command asks the configured DNS server for address information about `vast.ai`. It tests that lookup at that moment. A failure needs investigation, but it does not by itself show that every DNS lookup or connection is broken; also check the exact hostname reported in the daemon’s error log.

```bash
nslookup vast.ai
```

Expected result:

```
Server:		127.0.0.53
Address:	127.0.0.53

Non-authoritative answer:
Name:	vast.ai
Address: 76.76.21.21
```

What to look for: a `Name:` line followed by an `Address:` line containing an IP address shows that the configured resolver answered this query (the exact IP returned may differ). `;; connection timed out; no servers could be reached` or `server can't find vast.ai: NXDOMAIN` shows that this query did not resolve; it does not by itself identify a global DNS fault. Involve the network owner before changing resolver or network configuration.

### Check your public IPv4 address

This command contacts an external service (`ifconfig.me`) and returns the public IPv4 address it reports for this request. It provides one observed HTTP egress address, not a test of HTTPS, inbound reachability, or NAT/port-forwarding configuration.

```bash
curl -4 ifconfig.me
```

Expected sample result:

```
203.0.113.45
```

What to look for: a single public IPv4 address is the egress address observed by this request (your own address will differ from the example). A timeout or an error such as `Could not resolve host` shows that this request did not complete; it does not establish why. A different address can result from a proxy, VPN, or multi-egress NAT. Confirm the network topology with the network owner before changing firewall, NAT, or port-forwarding configuration.

Also review any proxy or VPN client configuration on the host. Proceed to Step 2 only after the network availability needed by this host is understood. If a check is filtered or inconclusive, pause and involve the network owner instead of changing configuration.

## 2. Confirm the Vastai Service Is Running

Check the current status:

```bash
sudo systemctl status vastai
```

Example output when the service is running normally:

```
● vastai.service - Vast.ai Host Daemon
     Loaded: loaded (/etc/systemd/system/vastai.service; enabled; preset: enabl>
     Active: active (running) since Tue 2026-08-04 07:47:51 +07; 6h ago
   Main PID: 2966 (launch_kaalia.s)
      Tasks: 2 (limit: 143635)
     Memory: 3.5G (peak: 6.5G)
        CPU: 5min 41.404s
     CGroup: /system.slice/vastai.service
             ├─2966 /bin/bash /var/lib/vastai_kaalia/latest/launch_kaalia.sh
             └─2975 /var/lib/vastai_kaalia/latest/kaalia backend=DKR installpat>
```

How to read the `Active:` line:

- **`active (running)`** means systemd currently considers the service running. It does not establish that the daemon can reach Vast.ai or use every GPU. If the state is `inactive (dead)`, `failed`, or `activating (auto-restart)`, inspect the status details and recent logs to determine what happened.
- **`since Tue 2026-08-04 07:47:51 +07; 6h ago`** shows when the service last started and how long it has been running continuously — here, 6 hours without interruption, which is a good sign of stability.
- **Repeated recent starts deserve investigation.** If the "ago" value repeatedly resets and the `Main PID` changes, the service is restarting. A single `activating (auto-restart)` state or `Scheduled restart job` message is not enough to establish a loop. Check several observations and the recent logs for exits, timeouts, manual actions or other restart causes; do not assume every restart is a crash.

### Verify GPUs are detected

This command shows NVIDIA driver information and status fields for GPUs available through that driver, including supported temperature, power and memory readings. Compare the listed GPUs with those you expect on the host. Missing GPUs or driver errors need investigation; this output alone does not establish whether the Vastai service can start.

```bash
nvidia-smi
```

Illustrative output format, not a captured result for your host. Your GPU model, driver version, supported fields and values will differ:

```
Mon Aug 10 15:18:38 2026
+-----------------------------------------------------------------------------------------+

+-----------------------------------------------------------------------------------------+
| Processes:                                                                              |

```

What to look for: the GPUs you expect to be available through the NVIDIA driver, with their names and supported readings. `N/A` can be normal for an unsupported field. Investigate unexpected missing devices or errors using the checks below:

- **`NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver`** — `nvidia-smi` cannot communicate with the driver. Check the driver and kernel state; this message alone does not show whether the GPUs remain visible on PCIe.
- **Fewer GPUs listed than expected** — investigate device visibility, driver/module configuration, power and PCIe connectivity. The count alone does not identify the cause or prove a hardware fault.
- **`ERR!` or `Unknown Error` in a field** — record the exact message and inspect the driver and kernel logs. An error reading does not by itself establish a hardware fault.
- **The command hangs or takes unusually long** — record when it happens and inspect the driver and kernel logs. The delay alone does not identify the underlying cause.

If the service is not running, or GPUs are not detected correctly, investigate the root cause with the commands below.

### Debugging commands

Attempt to start the service, then check the command result and service status. If it does not start or stops again, inspect the recent logs for the reason:

```bash
sudo systemctl start vastai
```

Re-check the service state after starting it, and confirm the `Active:` line reaches `active (running)` and stays there (see the explanation above about restart loops):

```bash
sudo systemctl status vastai
```

Show up to the last 100 lines of the Vastai daemon log. Look for relevant messages before the service exited or crashed; the cause may also require the service journal or kernel logs:

```bash
sudo tail -n 100 /var/lib/vastai_kaalia/kaalia.log
```

Show a detailed per-GPU report from the driver, including supported ECC, clock-event or throttle, and PCIe fields. Unsupported fields may show `N/A`. Use the readings with the logs when investigating a detected GPU; the report alone does not establish overall health:

```bash
nvidia-smi -q
```

Search the kernel ring buffer for NVIDIA (`NVRM`, `Xid`) and PCIe/AER messages. `dmesg -T` shows human-readable timestamps, which can be inaccurate after suspend/resume. Xid messages are NVIDIA driver error reports and provide starting points for investigation; they do not always identify a single root cause:

```bash
sudo dmesg -T | grep -iE 'nvrm|nvidia|xid|pcie|aer'
```

Search retained kernel journal entries for the current boot for the same NVIDIA/PCIe error patterns. Entries already captured by journald may remain after the kernel ring buffer overwrites them; availability depends on journal collection and retention:

```bash
sudo journalctl -k -b | grep -iE 'nvrm|nvidia|xid|pcie|aer'
```

Possible areas to investigate include NVIDIA driver state, GPU power and PCIe connectivity, BIOS configuration, and recent kernel or OS changes.

> **Note:** Do not restart or modify NVIDIA drivers while active customer instances are running unless instructed by Support.

Continue debugging until the service is active and all GPUs are detected. Once Vastai is confirmed running with GPUs correctly detected but the machine is still Offline in the Console, proceed to Step 3.

## 3. Reset the Controller Connection and Restart Vastai

If the service is running and the expected GPUs are detected but the machine remains Offline, the recovery sequence below stops the service, clears the named controller-connection state paths, restarts it, and runs `send_mach_info.py`. Review existing rental and storage commitments and use a suitable maintenance window. Check the installed script before running it: the current public version can change managed packages or settings, download components, and run disk/network checks as well as submit machine information. This is not a read-only status check or a guarantee that the machine will return Online.

```bash
sudo systemctl stop vastai.service && \
sudo rm -rf /var/lib/vastai_kaalia/data/last_try_get_controller && \
sudo rm -rf /var/lib/vastai_kaalia/data/get_controller_delay && \
sudo rm -rf /var/lib/vastai_kaalia/controller_connection && \
sudo systemctl restart vastai.service && \
(cd /var/lib/vastai_kaalia && sudo python3 ./send_mach_info.py)
```

Wait a few minutes, then check whether the machine returns Online in the Vast.ai Console.

Confirm the service remains active:

```bash
sudo systemctl status vastai
```

## 4. Contact Vast.ai Support

If the machine remains Offline after completing the steps above, contact Vast.ai Support and provide the following information:

- The machine ID.
- The approximate time the machine went Offline, including timezone.
- Whether the host has active Docker or VM rentals.
- Whether the issue began after a driver, kernel, network, hardware, or configuration change.
- The output of the following commands:

Current state of the Vastai service, including its activation time and recent log messages. Repeated status checks and journal entries can help identify a restart loop:

```bash
sudo systemctl status vastai
```

Current GPU and driver information — shows Support which GPUs the NVIDIA driver reports and their available status readings; this is not a complete GPU health test:

```bash
nvidia-smi
```

- The Vastai daemon log, `/var/lib/vastai_kaalia/kaalia.log`, and relevant rotated `kaalia.log*` files when available.

Please redact any passwords, private keys, API keys, tokens, customer information, or other sensitive data before sharing logs.
