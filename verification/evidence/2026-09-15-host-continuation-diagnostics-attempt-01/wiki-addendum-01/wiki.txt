1. bad bandwidthtest2: {'ERROR_CONDITION': 'not r_H2D or not r_D2H or not r_D2D', 'gpu_idx: N}
Frequency:
71 occurrences
First seen:
2024-02-05T01:34
Error message:
bad bandwidthtest2: {'ERROR_CONDITION': 'not r_H2D or not r_D2H or not r_D2D', 'gpu_idx': 0}
Expert Answer
This is best read as a failed GPU copy-path sanity check: host-to-device, device-to-host, and/or device-to-device transfer validation did not return acceptable results. NVIDIA's current tooling for this area is DCGM's PCIe/GPU bandwidth diagnostics and NVBandwidth, and NCCL explicitly warns that VT-d/IOMMU/ACS can interfere with GPU-direct traffic or even hang it. On a Vast host, repeated hits usually mean an unhealthy GPU, PCIe/topology problem, or driver/runtime/container exposure problem, not just an application bug.
Diagnostic commands:
nvidia-smi -q
dcgmi diag -r 3
journalctl -k | grep -i 'NVRM: Xid|AER|fallen off'
lspci -vvv | grep ACSCtl
References:
NVIDIA CUDA Samples – Bandwidth Test
,
Vast.ai Host Docs

Community Answer 3 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
This bandwidth test error indicates a GPU failure or communication problem between the host and GPU memory. The error means the GPU failed one or more bandwidth tests: Host to Device (H2D), Device to Host (D2H), or Device to Device (D2D) transfers. This typically indicates the GPU has a hardware problem, is missing, or is not functioning properly for data transfers. If this is a one-time occurrence, it may be a temporary glitch that disappears on the next bandwidth test run. If the error persists, investigate the following: First, check system logs using sudo dmesg -T | grep -E "NVRM|AER|fallen" or journalctl -o short-precise -k -b -1 | grep -E "NVRM|AER|fallen" to diagnose the issue. Second, verify that nvidia-persistenced mode is enabled by running nvidia-smi -pm 1. Third, check that the GPU is properly seated in its PCIe slot. Fourth, verify the GPU power connector (especially the 12-pin connector) is fully seated and secure, as a loose or disconnected power connector is a common cause. Fifth, ensure adequate power delivery to the GPU. The gpu_idx number in the error message indicates which specific GPU is affected (gpu_idx 0 means the first GPU, gpu_idx 3 means the fourth GPU, etc.).

2. No such file or directory
Frequency:
42 occurrences
First seen:
2024-03-02T17:53
Error message:
No such file or directory
Expert Answer
This is generic Linux
ENOENT
, but on Ubuntu it is often more subtle than "the file is missing." For executed programs,
execve
also returns
ENOENT
when the script interpreter or ELF interpreter does not exist, so a file can be present and still fail with this message if its shebang or loader path is wrong. On Vast hosts this commonly comes from stale script paths, moved binaries, broken symlinks, or mounts that exist on the host but not inside the container.
Diagnostic commands:
ls -la /path/to/file
file /path/to/binary
ldd /path/to/binary
References:
errno(3) man page

3. error: Bind to port NNNNN on 0.0.0.0 failed: Address already in use.
Frequency:
32 occurrences
First seen:
2024-02-07T01:25
Error message:
error: Bind to port 50200 on 0.0.0.0 failed: Address already in use.
Expert Answer
This is plain Linux
EADDRINUSE
: something is already bound to that port, or in rarer cases the ephemeral port range is exhausted. On Docker dual-stack hosts, one published port can occupy both IPv4 and IPv6, so stale listeners or parallel tests can collide across both families.
Diagnostic commands:
ss -ltnp
lsof -i :PORT
Look for reused fixed test ports in your automation.
References:
bind(2) man page
Community Answers
Community Answer 1 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
This error occurs when trying to bind SSH to a port that is already in use by another process. However, the port bind message itself is often not the actual root cause of the problem. First, check if another process is already using the port, which would prevent the SSH daemon from binding to that address. More importantly, check the kaalia logs (not the service logs) located in /var/lib/vastai_kaalia folder for the real underlying cause of the problem. Also verify you are looking at the correct logs - sometimes users mistakenly look at their own vastai instance logs rather than the relevant client connection attempt logs.
Community Answer 2 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
The port bind error message in vastai.service logs is often not the actual underlying problem. First, check the kaalia logs located in /var/lib/vastai_kaalia folder instead of the service logs, as the real issue will be shown there. If the problem persists, try restarting both the vastai and docker services using these commands: sudo systemctl restart vastai and sudo systemctl restart docker. This can resolve port binding conflicts where the SSH daemon cannot bind because the port is already in use by another process. Additionally, verify that you have explicitly configured which ports your server should use in the Vast.ai host settings, as not specifying ports causes Vast.ai to default to using 0 ports, which can cause SSH binding failures. If none of these solutions work, contact Vast.ai web chat support through the website.
Community Answer 3 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
This error occurs when the vastai service cannot bind to port 20000 because another process is already using it. Here are the steps to resolve this issue.
First, identify what is using port 20000 by running:
sudo lsof -i :20000
or
sudo netstat -tlnp | grep 20000
If you find an sshd process or another service using the port, stop it. For lingering sshd processes:
sudo pkill -f "sshd.*20000"
Next, ensure the host port range file is configured correctly. Create or edit the file:
sudo nano /var/lib/vastai_kaalia/host_port_range
Add the following content specifying your desired port range:
18000-20000
Make sure no other services on your system are configured to use ports in this range.
After making these changes, restart the vastai service:
sudo systemctl restart vastai
Then check the service status:
sudo systemctl status vastai
If the service still fails, check the logs for more details:
sudo journalctl -u vastai -f
For 8xRTX 5090 setups specifically, ensure your NVIDIA drivers are properly installed and all GPUs are detected by running nvidia-smi before starting the vastai service.
If the issue persists after these steps, try rebooting the machine to clear any stuck processes, then restart the vastai service. You can also try using a different port range in the host_port_range file, such as 15000-17000, to avoid conflicts with other services.
For additional troubleshooting scripts and host management tools, refer to the JJZiets VastTools repository at
https://github.com/jjziets/vasttools
. The official Vast.ai Host Guide at
https://docs.vast.ai/documentation/reference/host
also provides detailed configuration guidance.

Community Answer 5 — ★★★☆☆ (3/5)
Source: Community Knowledge Base (quality score: 3.0)
This error occurs when Vast.ai launches a duplicate service that tries to bind to the same port (commonly port 16484 or 32768). According to users, this is generally harmless and does not prevent the service from working - clients can still rent, payments still process, and rigs remain verified. The duplicate service fails to bind but the main service continues to function normally. The error happens because the vastai.service is already running with an sshd process bound to that port, and when the service tries to restart or spawn another instance, it fails because the port is already occupied. One user reports that adding a single character 'r' as a patch to Vast.ai scripts fixes the issue and has worked for them for half a year without problems. If you need to resolve it manually, you can kill the existing sshd process occupying the port.

5. error: Broken pipe
Frequency:
16 occurrences
First seen:
2024-05-13T15:34
Error message:
error: Broken pipe
Expert Answer
This is Linux
EPIPE
: your process wrote to a pipe or socket after the read side had already closed, and the writer may also receive
SIGPIPE
. Treat it as a downstream disconnect symptom, not the primary cause; the important question is what exited or crashed first on the other side of the pipe or socket.
Diagnostic approach:
Check what process was on the other end of the pipe/socket
Look at logs for the receiving process to find the real crash or exit reason
On Vast hosts, this commonly appears in SSH/sshd logs when a client disconnects unexpectedly
References:
errno(3) man page

Community Answer 1 — ★★★★☆ (4/5)

These errors during Vast.ai host software installation can have two main causes. First, the broken pipe error with send_mach_info.py on Ubuntu 22.04.5 is caused by using a minimized installation that is missing required packages. A broken pipe error indicates that the connection attempt failed due to network connectivity issues. This means the system wasn't able to establish or maintain a connection to the remote host. Common causes include: internet connection problems, network interruptions, faulty ethernet cables, dirty ports, issues with network switches, or problems with the physical cable itself (especially long cables like 20m CAT8 that may have twists or damage). The port itself is unlikely to be faulty unless physically damaged. To troubleshoot: check cable connections, test with different cables, and verify all network equipment in the connection path.

6. No devices were found
Frequency:
12 occurrences
First seen:
2025-02-05T06:46
Error message:
No devices were found
Expert Answer
nvidia-smi
uses NVML underneath, so this means NVML currently sees zero usable GPUs. NVIDIA's troubleshooting guidance treats this as the driver not loading correctly or the GPU not being accessible; NVIDIA also documents container cases where a running container suddenly loses GPU access after
systemctl daemon-reload
on
runc
/
systemd
-cgroup setups.
Diagnostic commands:
lsmod | grep nvidia
sudo modprobe nvidia
dmesg | grep -i nvrm
nvidia-smi -L
lspci | grep -i nvidia
Check on the host first, then in the container, and inspect
dmesg | grep -i nvrm
plus Xid logs before blaming the application layer.
References:
NVIDIA NVML API Reference
Community Answers
Community Answer 1 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
The machine is running under virtualization with GPU passthrough, so nvidia-smi on the host won't show any devices — that's expected. The GPUs are passed through to the renter, which is why the host reports no devices. Vast should not be querying nvidia-smi when all cards are in VMs. The error will go away once one of them is free from the VM. If all of your cards are in VMs then they're all being used properly.
Community Answer 2 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
These nvidia-smi errors on Vast.ai can have multiple causes depending on your setup. For GPU passthrough virtualization: When all GPUs are passed through to VMs and rented out, nvidia-smi on the host will not detect any devices because the GPUs are assigned to the renter's VM. This is expected behavior and Vast.ai should not be querying nvidia-smi when all cards are in VMs. The error will go away once one of the GPUs is freed from the VM and available for the host system to query directly. Since the machine works normally for renters, no urgent fix is needed. For non-virtualized setups: The error may be related to a kaalia binary update (such as the one on Oct 15, 2024). The error appears on the Vast machine page only, not in dmesg, and machines continue to work perfectly fine despite the error. A reboot typically clears the error. For machines that genuinely cannot detect GPUs: This typically requires reinstalling NVIDIA drivers after purging them completely.
Community Answer 3 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
There are several possible causes for nvidia-smi not detecting GPUs:
Missing GPU power connection: If you just installed a new GPU card (especially a second card), verify that power cables are properly connected to the GPU. The system may boot and be accessible via SSH even without GPU power connected, but nvidia-smi will not detect any devices.
Driver installation requires reboot: After installing NVIDIA drivers, you must reboot the system before nvidia-smi will detect devices.
GPU passthrough to virtual machines: When running virtualization with GPU passthrough, nvidia-smi on the host will show no devices because the GPUs are assigned to VMs. This is expected behavior - the host system cannot see GPUs while they are in use by VMs. The error will go away once one of the GPUs is no longer passed through.
Driver version or installation method issues: Some driver versions may have compatibility issues. If apt install does not work properly, try using the .run installation method instead. To install driver version 570.124.04 using the .run method: First uninstall the old version with sudo apt-get remove --purge '^nvidia-.*' -y, then reboot. Download the driver with wget
https://us.download.nvidia.com/XFree86/Linux-x86_64/570.124.04/NVIDIA-Linux-x86_64-570.124.04.run
then install with sudo bash NVIDIA-Linux-x86_64-570.124.04.run.

Community Answers
Community Answer 1 — ★★★★☆ (4/5)
Source: Community Knowledge Base (quality score: 4.0)
Permission requirements depend on whether you are operating as a host or as a client renting a machine.
As a host configuring your own Ubuntu system, most system-level operations require root access. This includes installing packages, modifying system configurations, managing Docker and KVM services, and running maintenance scripts. For example, disabling auto-updates to protect your NVIDIA drivers requires root:
sudo apt remove unattended-upgrades -y
As a client renting a machine through vast.ai, your access level depends on how the instance was configured. Docker instances typically run as root inside the container by default, so you should have full permissions within that container environment. However, you cannot access the underlying host system. If you are getting permission denied errors in a rented Docker instance, try prefixing your command with sudo, or check if the container was launched with restricted permissions.
For KVM virtual machines, you typically have root access within the VM itself but again no access to the host.
If you are a host and receiving permission denied errors while running system maintenance or monitoring scripts from tools like vasttools, prefix your commands with sudo or switch to root using sudo su. Most host-level operations for GPU management, driver maintenance, and system configuration require elevated privileges.
