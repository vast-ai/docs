A guide for users moving GPU workloads from Runpod to Vast.ai. Whether you use Runpod Pods for training and development or Runpod Serverless for inference, this guide maps every concept to its Vast.ai equivalent and walks you through the transition.

**What is different:** In a nutshell, you have more control. You choose your specific machine, see the exact specs you are getting, and set the reliability level you need, rather than relying on an opaque allocation. This guide addresses each of these differences head-on so there are no surprises.

<Note>
**What Runpod users need to know about Vast.ai:**

1. **Your existing Runpod images may work as-is.** Many Runpod-compatible Docker images run on Vast with little or no modification.
2. **You pick the individual machine, not just the GPU type.** Every offer shows reliability score, network speed, CPU, location, and other critical specs. Two A100s at the same price can be very different machines. Vast gives you the data to choose the right one.
3. **Bandwidth billed separately.** Providers set rates for bandwidth use per GB, which you can view in the price breakdown by hovering over the price of an instance offer. Filter for instances with lower bandwidth rates using the pricing filters on the search page. Note that both inbound and outbound traffic are billed, so pulling large models or datasets counts toward your bandwidth costs.
4. **Set your disk size right at launch.** Resizing requires recreating the container. Storage is cheap, so err on the side of more space.
5. **Often lower prices for the same GPU performance.** Marketplace competition drives prices down. You'll frequently find the same hardware at lower rates than fixed-tier providers.
</Note>

<Warning>
Runpod is retiring the APIs that automation scripts use: rate limits on its GraphQL API start October 27, 2026, REST API v1 stops working November 15, 2026, and the GraphQL API stops working in January 2027. If your code calls these APIs, see [Migrating API Code](#migrating-api-code).
</Warning>

## Concept Mapping

| Runpod | Vast.ai | Notes |
|---|---|---|
| Pod | Instance | Docker container with exclusive GPU access |
| Serverless Endpoint -> Worker | Serverless Endpoint -> Workergroup -> Worker | Vast has managed autoscaling inference. See [Migrating from Serverless](#migrating-from-serverless) |
| Community Cloud / Secure Cloud | Verified Machines (default) / Secure Cloud | Vast defaults to verified machines; Secure Cloud filters to datacenter-grade hosts |
| Template | Template / Docker image | Specify a Docker image and configuration at launch |
| Volume Disk | (Local) Volume | Machine-local storage that can attach to any GPU on the same physical node. See [Storage](#storage) |
| Network Volume | Object Storage (S3, R2, GCS) | Vast has no cross-host network volume. For data that persists across machines, use object storage. See [Storage](#storage) |
| Hub | [Model Library](/guides/serverless/quickstart) + [Template Library](/guides/templates/introduction) | Official templates for popular inference engines and applications, plus specific model configs through the model library |
| Pod API | Vast REST API / `vastai` CLI | Full programmatic control over instances |
| GPU Type selector | Search filters (CUDA, VRAM, price/hr) | Vast is a marketplace: you search and filter offers |
| On-Demand Pod | On-Demand Instance | Fixed pricing, guaranteed resources |
| Spot Pod | Interruptible Instance | You set a max $/hr; higher-priority on-demand renters can displace you |
| Savings Plan | Reserved Instance | Pre-pay an on-demand instance for up to 50% discount |
| Runpod Console | [Vast Console](https://cloud.vast.ai) | Web UI for managing instances, billing, and templates |

## Account Setup

1. **Create an account** at [cloud.vast.ai](https://cloud.vast.ai)
2. **Add credits.** Similar to Runpod, Vast is prepaid. Add funds via the [Billing page](https://cloud.vast.ai/billing/) before renting.
3. **Add your SSH public key** at [cloud.vast.ai/manage-keys/](https://cloud.vast.ai/manage-keys/). If you do not have one, generate it with `ssh-keygen -t ed25519`. Keys are applied at container creation time. If you forgot, use the SSH key button on the instance card to add one without recreating.

That's all you need to get started via the console. **If you plan to use the CLI or REST API**, also:

4. **Generate an API key** from the [Keys page](https://cloud.vast.ai/manage-keys/) and authenticate:

```bash Vast CLI
curl -fsSL https://vast.ai/install.sh | bash
vastai set api-key <YOUR_API_KEY>
```

## Migrating from Pods

A Runpod **Pod** is a Docker container running on a GPU-equipped machine. You pick a GPU type and a template (Docker image + config), and Runpod assigns you a machine from its managed fleet. The Vast.ai equivalent is an **Instance**: also a Docker container with exclusive GPU access, but rented from an open marketplace of independent hosts rather than a single provider.

The core workflow is the same (pick a GPU, choose an image, launch), but how you find that GPU is different.

### Finding and Creating Instances

Runpod presents a curated list of GPUs at set prices. Vast.ai is a marketplace: hosts list their machines with specs and asking prices, and you search through available offers using filters. Two A100 80GB offers at the same price can be on very different machines. Vast surfaces reliability scores, network speeds, and location for every offer so you can pick the right one for your workload.

**Always check these before renting:**
- **Reliability score**: historical uptime percentage. Look for 0.95+ for production workloads. If reliability is critical, filter for Secure Cloud machines only.
- **Network speed**: `inet_down` and `inet_up` in Mbps. Matters for model downloads and data transfer.
- **Geolocation**: filter by region for latency-sensitive workloads.

<Tabs>
  <Tab title="Console">
    1. Go to [Search](https://cloud.vast.ai/create/)
    2. Use the GPU type, VRAM, reliability, and region filters to narrow results
    3. Review each offer's reliability score and network speed before renting
    4. Click **Rent** on your chosen offer and configure image, disk, and Docker options in the dialog
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod API
    curl -X POST "https://rest.runpod.io/v1/pods" \
        -H "Authorization: Bearer $RUNPOD_API_KEY" \
        -H "Content-Type: application/json" \
        -d '{
            "name": "my-pod",
            "imageName": "pytorch/pytorch:latest",
            "gpuTypeIds": ["NVIDIA GeForce RTX 4090"],
            "containerDiskInGb": 50,
            "cloudType": "SECURE"
        }'
    ```

    ```bash Vast CLI
    # Step 1: Search for matching offers
    vastai search offers 'gpu_name = RTX_4090 reliability > 0.95' \
        --order "dph_base" --limit 5

    # Step 2: Create instance from an offer ID
    vastai create instance <OFFER_ID> \
        --image pytorch/pytorch:latest \
        --disk 50
    ```


    </CodeGroup>

    Common GPU searches:

    ```bash Vast CLI
    # RTX 4090 (24GB) — popular for inference
    vastai search offers 'gpu_name = RTX_4090' --order "dph_base" --limit 5

    # A100 80GB — training and large model inference
    vastai search offers 'gpu_name in ["A100 SXM4","A100 PCIE"] gpu_ram >= 80' --order "dph_base" --limit 5

    # H100 — highest performance
    vastai search offers 'gpu_name in ["H100 SXM","H100 NVL"]' --order "dph_base" --limit 5

    # Multi-GPU for distributed training
    vastai search offers 'num_gpus >= 4 gpu_ram >= 80' --order "dph_base" --limit 5

    # US only
    vastai search offers 'gpu_ram >= 24 geolocation = US' --order "dph_base" --limit 10
    ```
  </Tab>
</Tabs>

### Docker Environment

#### Images

If you have a working Runpod template, you likely already have a Docker image that works on Vast. Many Runpod-compatible images may run as-is. Just specify the image in the `--image` flag.

To minimize cold start times:
- Use [**Vast base images**](https://github.com/vast-ai/base-image/) (also on [DockerHub](https://hub.docker.com/u/vastai)), which are pre-cached on many hosts
- Use smaller, optimized images where possible
- For very large images, build on top of a pre-cached base

#### Environment Variables

On Runpod, environment variables are set in the template UI or passed as a JSON object in the API. Vast works the same way.

<Tabs>
  <Tab title="Console">
    In the instance creation dialog or template editor, set environment variables using the GUI fields or the **Docker Options** field with Docker syntax:

    ```
    -e HF_TOKEN=hf_xxxxx -e MODEL_NAME=meta-llama/Llama-3-8B
    ```
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod API
    curl -X POST "https://rest.runpod.io/v1/pods" \
        -H "Authorization: Bearer $RUNPOD_API_KEY" \
        -H "Content-Type: application/json" \
        -d '{
            "name": "my-pod",
            "imageName": "your-image:latest",
            "gpuTypeIds": ["NVIDIA GeForce RTX 4090"],
            "env": {
                "HF_TOKEN": "hf_xxxxx",
                "MODEL_NAME": "meta-llama/Llama-3-8B"
            }
        }'
    ```

    ```bash Vast CLI
    vastai create instance <OFFER_ID> \
        --image your-image:latest \
        --env "-e HF_TOKEN=hf_xxxxx -e MODEL_NAME=meta-llama/Llama-3-8B" \
        --disk 100
    ```

    </CodeGroup>

    <Note>
    The Vast CLI `--env` flag takes **raw Docker run options**, not just `KEY=VALUE` pairs. Port mappings go here too, for example: `--env "-e MY_VAR=foo -p 8080:8080"`.
    </Note>
  </Tab>
</Tabs>

#### Entrypoint Arguments

Runpod's "Docker Command" field passes arguments to the container's ENTRYPOINT (`"dockerStartCmd"` in the API). On Vast, use `--args`.

<Tabs>
  <Tab title="Console">
    In the template editor or instance creation dialog, enter entrypoint arguments in the **Docker Options** field.
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod API
    curl -X POST "https://rest.runpod.io/v1/pods" \
        -H "Authorization: Bearer $RUNPOD_API_KEY" \
        -H "Content-Type: application/json" \
        -d '{
            "name": "vllm-server",
            "imageName": "vllm/vllm-openai:latest",
            "gpuTypeIds": ["NVIDIA GeForce RTX 4090"],
            "containerDiskInGb": 40,
            "ports": ["8000/http"],
            "dockerStartCmd": ["--model", "Qwen/Qwen2.5-7B-Instruct", "--max-model-len", "4096"]
        }'
    ```

    ```bash Vast CLI
    vastai create instance <OFFER_ID> \
        --image vllm/vllm-openai:latest \
        --env "-p 8000:8000" \
        --disk 40 \
        --args --model Qwen/Qwen2.5-7B-Instruct --max-model-len 4096
    ```

    </CodeGroup>
  </Tab>
</Tabs>

#### Startup Scripts

Vast has an on-start script that runs a shell command *after* the container starts. Runpod does not have a direct equivalent; the closest is baking the command into a custom Docker image.

<Tabs>
  <Tab title="Console">
    In the template editor or instance creation dialog, enter your startup commands in the **On-start Script** field.
  </Tab>
  <Tab title="CLI">
    ```bash Vast CLI
    vastai create instance <OFFER_ID> \
        --image pytorch/pytorch:latest \
        --env "-p 8000:8000" \
        --disk 50 \
        --onstart-cmd "cd /workspace && pip install -r requirements.txt && python server.py"
    ```
  </Tab>
</Tabs>

#### Converting a Runpod Template

Runpod templates bundle an image, environment, ports, and a Docker command into a reusable config. Here is how each field maps to Vast:

| Runpod template field | Vast console | Vast CLI flag |
|---|---|---|
| Container Image (`imageName`) | Image field | `--image` |
| Container Disk (`containerDiskInGb`) | Disk field | `--disk` |
| Exposed Ports (`"8000/http"`) | Docker Options: `-p 8000:8000` | `--env "-p 8000:8000"` |
| Environment Variables (`env: {...}`) | Docker Options: `-e KEY=VALUE` | `--env "-e KEY=VALUE"` |
| Docker Command (`dockerStartCmd`) | Docker Options (entrypoint args) | `--args` |
| *(no equivalent)* | On-start Script | `--onstart-cmd` |

**Full example:** a Runpod vLLM template converted to Vast:

<CodeGroup>

```bash Runpod (API)
curl -X POST "https://rest.runpod.io/v1/pods" \
    -H "Authorization: Bearer $RUNPOD_API_KEY" \
    -H "Content-Type: application/json" \
    -d '{
        "imageName": "vllm/vllm-openai:latest",
        "containerDiskInGb": 40,
        "ports": ["8000/http"],
        "env": {"HF_TOKEN": "hf_xxxxx"},
        "dockerStartCmd": ["--model", "meta-llama/Llama-3.1-8B-Instruct"]
    }'
```

```bash Vast CLI
vastai create instance <OFFER_ID> \
    --image vllm/vllm-openai:latest \
    --disk 40 \
    --env "-p 8000:8000 -e HF_TOKEN=hf_xxxxx" \
    --args --model meta-llama/Llama-3.1-8B-Instruct
```

</CodeGroup>

Once you have a working configuration, save it as a reusable **Vast template** in the [console](https://cloud.vast.ai/templates/). See the [Templates guide](/guides/templates/introduction) for details.

### Storage

For model weights and datasets, the recommended approach is to pull from object storage on boot. This works across any host and keeps your instance stateless:

- **Object storage** (S3, R2, GCS): pull weights on boot. Most flexible, works across any host.
- **[Cloud Sync](/guides/instances/storage/cloud-sync)**: Vast's built-in sync tool supports S3, Google Drive, Backblaze, and Dropbox. Access it via the console or `vastai cloud copy`. Docker instances only; use IAM credentials with S3 for bucket-scoped access rather than account-level credentials.

<Note>
Vast local volumes are tied to the physical machine they were created on. For data that needs to persist across instances or move to a new host, use cloud object storage (S3, R2, GCS), a more portable and provider-agnostic approach than any single vendor's proprietary network volume.
</Note>

### Networking and Ports

Both platforms provide proxy access to services. On Runpod, proxy URLs are static: `https://<POD_ID>-<PORT>.proxy.runpod.net`. On Vast, there are two proxy mechanisms:

- **HTTP/HTTPS proxy**: instances using [Vast base images](https://github.com/vast-ai/base-image/) get auto-generated Cloudflare tunnel URLs (`https://four-random-words.trycloudflare.com`) per open port via the [Instance Portal](/guides/instances/connect/instance-portal). These tunnels are best-effort and may not always be available; for reliable HTTPS access, use direct connections or the built-in Jupyter certificate (see [Jupyter / IDE Access](#jupyter-/-ide-access)).
- **SSH proxy**: instances using SSH-compatible images support proxy SSH through Vast's proxy server, which works even on machines without open ports. Direct SSH (faster) is preferred when available.

Instances also have direct access via a **random external port** on the host's public IP, which you discover after launch.

#### Declaring Ports at Launch

<Tabs>
  <Tab title="Console">
    In the instance creation dialog or template editor, enter port mappings in the **Docker Options** field:

    ```
    -p 8000:8000 -p 8080:8080
    ```
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod API
    # Ports configured in template UI or API "ports" field
    # e.g. "ports": ["8000/http", "22/tcp"]
    # Accessed via proxy URL: https://<POD_ID>-8000.proxy.runpod.net
    ```

    ```bash Vast CLI
    vastai create instance <OFFER_ID> \
        --image your-image:latest \
        --env "-p 8000:8000 -p 8080:8080" \
        --disk 50
    ```

    </CodeGroup>
  </Tab>
</Tabs>

**Limits:** Maximum 64 open ports per container. For a stable external port number, use internal ports above 70000, which are identity-mapped (the external port matches the internal port).

#### Discovering Your External Port

<Tabs>
  <Tab title="Console">
    After the instance starts, click the **Open Ports** button on the instance card to see the external port mapping.
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod
    # Access via proxy URL (automatic)
    curl https://<POD_ID>-8000.proxy.runpod.net/v1/models
    ```

    ```bash Vast CLI
    vastai show instance <INSTANCE_ID> --raw | jq '.ports'
    ```

    </CodeGroup>
  </Tab>
</Tabs>

Vast also sets `VAST_TCP_PORT_<N>` environment variables inside the container for each mapped port. Use these in your application code to construct external URLs.

### Connecting to Your Instance

#### SSH

On Runpod, you SSH into a pod using the connection info from the console. On Vast, SSH uses key-only authentication (make sure you've added your public key in [Account Setup](#account-setup)).

<Tabs>
  <Tab title="Console">
    Click the **SSH** button on the instance card to see the full connection command, then paste it into your terminal.
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod
    # SSH connection string from Runpod console
    ssh <POD_ID>@ssh.runpod.io -i ~/.ssh/id_ed25519
    ```

    ```bash Vast CLI
    # Get SSH connection details
    vastai ssh-url <INSTANCE_ID>
    # Example output: ssh://root@142.214.185.187:20544

    # Then connect using the host and port from the output above
    ssh -p 20544 root@142.214.185.187
    ```

    </CodeGroup>
  </Tab>
</Tabs>

Instances using [Vast base images](https://github.com/vast-ai/base-image/) connect to a tmux session by default. Use `Ctrl+B C` to open a new window and `Ctrl+B N` to cycle between windows. To disable tmux, create `~/.no_auto_tmux` inside the container.

**Port forwarding** works the same as any SSH connection:

```bash Bash
ssh -p <PORT> root@<VAST_IP> -L 8080:localhost:8080
```

#### Jupyter / IDE Access

Both platforms support JupyterLab. On Vast, Jupyter is available out of the box with two access modes:

- **Proxy mode** (default): Click the Jupyter button in the [Vast console](https://cloud.vast.ai). Works immediately, no setup needed. Uses Cloudflare tunnels, which are best-effort.
- **Direct HTTPS** (recommended): Faster, more reliable connection that bypasses the proxy. Instances using Vast base images include a built-in Jupyter TLS certificate. Install the Vast TLS root certificate (`jvastai_root.cer`), downloadable from the [Vast console](https://cloud.vast.ai), to connect directly over HTTPS without browser warnings.

Both platforms support VS Code / Cursor via Remote-SSH.

### Instance Lifecycle and Cost

#### Start, Stop, and Destroy

<Tabs>
  <Tab title="Console">
    Use the buttons on the instance card: **Stop** to pause compute, **Destroy** to delete the instance and stop all charges.
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod API
    # Stop pod
    curl -X POST "https://rest.runpod.io/v1/pods/$POD_ID/stop" \
        -H "Authorization: Bearer $RUNPOD_API_KEY"

    # Terminate pod
    curl -X DELETE "https://rest.runpod.io/v1/pods/$POD_ID" \
        -H "Authorization: Bearer $RUNPOD_API_KEY"
    ```

    ```bash Vast CLI
    # Stop — pauses compute, storage keeps billing
    vastai stop instance <INSTANCE_ID>

    # Destroy — stops all charges, deletes all data
    vastai destroy instance <INSTANCE_ID>
    ```

    </CodeGroup>
  </Tab>
</Tabs>

| Action | Compute Charges | Storage Charges | Data Preserved |
|---|---|---|---|
| **Stop** | Stop | **Continue** | Yes |
| **Destroy** | Stop | Stop | **No** |

**If you are done with an instance, destroy it.** Stopped instances continue to cost money for storage. Only stop instances you plan to resume soon.

#### On-Demand vs Interruptible

| Type | Runpod Equivalent | Price | Interruption Risk |
|---|---|---|---|
| On-Demand | On-Demand Pod | Standard marketplace rate | None (guaranteed) |
| Interruptible | Spot Pod | Often significantly cheaper | Can be displaced by on-demand renters |

<Tabs>
  <Tab title="Console">
    On the [Search](https://cloud.vast.ai/create/) page, use the **Instance Type** toggle to switch between on-demand and interruptible offers before renting.
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod API
    # On-Demand (Secure Cloud)
    curl -X POST "https://rest.runpod.io/v1/pods" \
        -H "Authorization: Bearer $RUNPOD_API_KEY" \
        -H "Content-Type: application/json" \
        -d '{
            "name": "my-pod",
            "imageName": "pytorch/pytorch:latest",
            "gpuTypeIds": ["NVIDIA GeForce RTX 4090"],
            "cloudType": "SECURE"
        }'

    # Spot (Community Cloud)
    curl -X POST "https://rest.runpod.io/v1/pods" \
        -H "Authorization: Bearer $RUNPOD_API_KEY" \
        -H "Content-Type: application/json" \
        -d '{
            "name": "my-pod",
            "imageName": "pytorch/pytorch:latest",
            "gpuTypeIds": ["NVIDIA GeForce RTX 4090"],
            "cloudType": "COMMUNITY"
        }'
    ```

    ```bash Vast CLI
    # On-demand — guaranteed, higher price
    vastai search offers 'gpu_ram >= 24' --type=on-demand --order "dph_base" --limit 10

    # Interruptible — cheapest, may be interrupted
    vastai search offers 'gpu_ram >= 24' --type=bid --order "dph_base" --limit 10
    ```

    </CodeGroup>
  </Tab>
</Tabs>

Use interruptible instances for batch inference, training with checkpointing, or any workload that can be restarted if interrupted. Save checkpoints frequently.

#### Reserved Instances

If you run an on-demand instance for days or weeks, convert it to a **reserved instance** for up to 50% savings. Reserved instances lock in a discounted rate in exchange for a time commitment:

<Tabs>
  <Tab title="Console">
    Not all machines support reserved pricing. To find eligible machines before renting, go to [Search](https://cloud.vast.ai/create/) and switch the **On-demand** filter to **Reserved**. After renting, go to the **Instances** page and click the **green discount badge** on your instance card to open the pre-payment dialog.
  </Tab>
  <Tab title="CLI">
    ```bash Vast CLI
    vastai prepay instance <INSTANCE_ID> 100
    ```
  </Tab>
</Tabs>

<Note>
Reserved instances cannot migrate between hosts. If the host machine goes down, your reservation is tied to that machine.
</Note>

## Migrating from Serverless

Runpod **Serverless** lets you deploy a handler function that scales to zero. You send a request, Runpod spins up a worker, runs your handler, and tears it down. You pay per second of compute, not for idle GPUs.

Vast **Serverless** delivers autoscaling inference at marketplace rates, with per-second billing across 68+ GPU types globally. Vast handles routing, queueing, and autoscaling automatically. You can deploy using a pre-built template (vLLM, TGI, ComfyUI) or implement a custom handler with PyWorker, analogous to RunPod's handler pattern.

**Pricing:** Serverless workers run on the same marketplace instances you'd rent directly, you pay the same per-second rate, just with autoscaling on top.

### Vast Serverless Architecture

The system has three layers:

| Component | Purpose |
|---|---|
| **Endpoint** | Routes requests, manages autoscaling |
| **Workergroup** | Defines what code runs and how workers are recruited |
| **Worker** | Individual GPU instance running your model via PyWorker |

### Deployment Options

Vast Serverless supports two deployment paths:

**PyWorker (Custom Handlers)** is the core framework for building serverless workers. You implement a handler function in Python, analogous to RunPod's handler pattern, with full control over request preprocessing, model loading, and response formatting. Most production deployments use custom PyWorker handlers. See the [PyWorker documentation](/guides/serverless/creating-new-pyworkers) to get started.

**Pre-built Templates** serve as ready-to-use starting points and examples. Vast provides templates for common frameworks (vLLM, TGI, ComfyUI) that you can deploy directly or use as a reference for building your own handlers.

### Creating Endpoints and Workergroups

<Tabs>
  <Tab title="Console">
    1. Go to [Serverless](https://cloud.vast.ai/serverless/) in the console
    2. Click **New Endpoint** and configure name, max workers, and scaling parameters
    3. Add a workergroup: choose a pre-built template (vLLM, TGI, ComfyUI) for quick setup, or configure a custom PyWorker by specifying your Docker image and `PYWORKER_REPO` environment variable
  </Tab>
  <Tab title="CLI">
    <CodeGroup>

    ```bash Runpod
    # Create a serverless endpoint from a template
    runpodctl create endpoint \
        --name "my-llm-endpoint" \
        --templateId "runpod-vllm" \
        --gpuIds "NVIDIA RTX A5000" \
        --minWorkers 0 \
        --maxWorkers 5
    ```

    ```bash Vast CLI
    # Create an endpoint
    vastai create endpoint \
        --endpoint_name "my-llm-endpoint" \
        --max_workers 5 \
        --cold_workers 1 \
        --target_util 0.9

    # Option 1: Create a workergroup with a custom PyWorker handler
    # PYWORKER_REPO points to your worker code (see github.com/vast-ai/pyworker for examples)
    vastai create workergroup \
    ```

## Migrating API Code

Runpod is retiring its REST API v1 and its GraphQL API, so code that calls either one has to be updated. This section shows how to move that code to Vast.ai using the `vastai` CLI, the Python SDK or the REST API. Commands were checked against `vastai` 1.9.1.

**Scope:** this section covers code that manages Runpod **pods** (Vast calls them **instances**): finding a GPU, creating it, running work on it, moving files and deleting it. Moving **Serverless endpoints** or **network volumes** takes separate work; see [Migrating from Serverless](#migrating-from-serverless) and [Storage](#storage).

Requests to a running Runpod Serverless endpoint don't use the retiring APIs, but creating and managing endpoints through REST v1 or GraphQL does.

### What Runpod Is Changing

| Date | Change |
|---|---|
| October 27, 2026 | Rate limits start on the GraphQL API (`api.runpod.io/graphql`) |
| November 15, 2026 | REST API v1 (`rest.runpod.io/v1`) stops serving requests |
| January 2027 | The GraphQL API stops serving requests |

Pods and endpoints that are already running are not affected; only code that calls these APIs is. Runpod's replacement, REST API v2, has new paths and response shapes, so the code has to be rewritten either way. Recent versions of the `runpod` Python SDK already use the new API for pod commands, and `runpodctl` has a new command set, so if you only use those tools, updating them may be enough. Sources: [Runpod Q3 2026 update](https://www.runpod.io/blog/runpod-q3-2026-releases), [Runpod migration guide](https://docs.runpod.io/api-reference-v2/migrate-from-v1).

### Migrate in Four Steps

#### Step 1: Set Up Your Account

1. Create an account at [cloud.vast.ai](https://cloud.vast.ai) and add credit on the [Billing page](https://cloud.vast.ai/billing/). Vast is prepaid and bills per second.
2. Create a new API key on the [Keys page](https://cloud.vast.ai/manage-keys/). Your Runpod key does not work on Vast.
3. Install the CLI (it includes the Python SDK), sign in and register your SSH public key:

```bash
pip install vastai
vastai set api-key YOUR_VAST_API_KEY
vastai show user                                        # confirms the key works and shows your balance
vastai create ssh-key "$(cat ~/.ssh/id_ed25519.pub)"    # pass the key's contents, not the file name
```

In scripts and CI, store the Vast key as the `VAST_API_KEY` environment variable or secret.

#### Step 2: Try One Instance

```bash
# Find offers under $0.60/hour, priced with a 30 GB disk. The first column is the offer ID.
vastai search offers 'gpu_name=RTX_4090 num_gpus=1 reliability>0.98 direct_port_count>=1 dph_total<=0.60' --storage 30 -o dph_total --limit 5

# Rent one. The reply's "new_contract" value is your instance ID.
vastai create instance OFFER_ID --image vastai/pytorch:@vastai-automatic-tag --disk 30 --ssh --direct --cancel-unavail

# Repeat until the status is "running", then print the SSH command
vastai show instance INSTANCE_ID
vastai ssh-url INSTANCE_ID

# Delete it, then confirm it no longer appears in your list
vastai destroy instance INSTANCE_ID -y
vastai show instances
```

#### Step 3: Update Your Code

On Runpod, one call finds a GPU and creates the pod. On Vast it takes two calls:

1. `search offers` lists machines that match your requirements and price limit.
2. `create instance` rents one of them.

Search every time you launch, because an offer disappears once someone rents it. The [example migration](#example-migration-before-and-after) shows a complete Runpod program and its Vast replacement. Translate the rest of your calls with the [task map](#task-map).

#### Step 4: Test, Then Clean Up

Run your updated code once with one inexpensive GPU. Confirm that it creates the instance, reaches `running`, does its work, saves its results and deletes the instance. Then run `vastai show instances` and confirm nothing from the test is left, including stopped instances, which still bill for storage.

### Example Migration: Before and After

A small program that rents a GPU with a given image, environment variable, start command and HTTP port, waits for the job's output, saves it and deletes the GPU.

#### Before: Runpod REST API v1

```python
import os, time, requests

API = "https://rest.runpod.io/v1"
HEADERS = {"Authorization": f"Bearer {os.environ['RUNPOD_API_KEY']}"}
IMAGE = "pytorch/pytorch:2.4.0-cuda12.4-cudnn9-runtime"
START = ('mkdir -p /workspace/out && cd /workspace/out && '
         'python -c "import torch; print(torch.cuda.get_device_name(0))" > report.txt && '
         'echo "mode=$MODE" >> report.txt && python -m http.server 8000')

pod = requests.post(f"{API}/pods", headers=HEADERS, json={
    "name": "report-job",
    "imageName": IMAGE,
    "gpuTypeIds": ["NVIDIA GeForce RTX 4090"],
    "gpuCount": 1,
    "containerDiskInGb": 30,
    "env": {"MODE": "fast"},
    "ports": ["8000/http"],
    "dockerStartCmd": ["bash", "-c", START],
}).json()
pod_id = pod["id"]

try:
    url = f"https://{pod_id}-8000.proxy.runpod.net/report.txt"
    for _ in range(120):
        try:
            r = requests.get(url, timeout=10)
            if r.ok:
                open("report.txt", "w").write(r.text)
                break
        except requests.RequestException:
            pass
        time.sleep(10)
finally:
    requests.delete(f"{API}/pods/{pod_id}", headers=HEADERS)
```

#### After: Vast.ai Python SDK

What changed: the search and the price limit (Runpod picks the machine for you), the unique label, `env` and `-p` instead of `env` and `ports`, `args` instead of `dockerStartCmd`, the port lookup instead of the proxy URL, and the checks that the instance started and was deleted.

```python
import os, secrets, time, requests
from vastai import VastAI

v = VastAI(api_key=os.environ["VAST_API_KEY"])
IMAGE = "pytorch/pytorch:2.4.0-cuda12.4-cudnn9-runtime"
START = ('mkdir -p /workspace/out && cd /workspace/out && '
         'python -c "import torch; print(torch.cuda.get_device_name(0))" > report.txt && '
         'echo "mode=$MODE" >> report.txt && python -m http.server 8000')
MAX_PRICE = 0.60                                   # dollars per hour, including the disk
DISK_GB = 30
LABEL = f"report-job-{secrets.token_hex(4)}"       # unique per run, so we can always find what we rented

def my_instance_ids():
    return [i["id"] for i in v.show_instances() if i.get("label") == LABEL]

def rent():
    offers = v.search_offers(
        query=f"gpu_name=RTX_4090 num_gpus=1 reliability>0.98 direct_port_count>=1 dph_total<={MAX_PRICE}",
        order="dph_total", limit=5, storage=DISK_GB)        # storage= prices the real disk size
    for offer in offers:
        try:
            r = v.create_instance(id=offer["id"], image=IMAGE, disk=DISK_GB, label=LABEL,
                                  env="-e MODE=fast -p 8000:8000", args=["bash", "-c", START],
                                  cancel_unavail=True)
            if r.get("new_contract"):
                return r["new_contract"]
            continue                                # Vast declined this offer: nothing was rented
        except requests.HTTPError as e:
            if e.response is not None and 400 <= e.response.status_code < 500:
                continue                            # Vast declined this offer: nothing was rented
        except requests.RequestException:
            pass
        # An uncertain create may have succeeded: look before renting again.
        time.sleep(20)
        found = my_instance_ids()
        if found:
            return found[0]
        raise SystemExit(f"Rental result unknown and no instance labeled {LABEL} was found. "
                         "Check https://cloud.vast.ai/instances/ before running again.")
    raise SystemExit(f"No offer at or under ${MAX_PRICE}/hour could be rented")

def destroy(instance_id):
    v.destroy_instance(id=instance_id)
    for _ in range(12):                             # confirm it's gone; a stopped instance still bills
        if instance_id not in [i["id"] for i in v.show_instances()]:
            return
        time.sleep(5)
    raise RuntimeError(f"Instance {instance_id} still exists. Check https://cloud.vast.ai/instances/")

instance_id = rent()
print(f"Rented instance {instance_id} ({LABEL})")
try:
    deadline = time.time() + 20 * 60                # give up after 20 minutes
    saved = False
    while not saved and time.time() < deadline:
        inst = v.show_instance(id=instance_id) or {}
        status = inst.get("actual_status")
        if status in ("exited", "unknown", "offline"):
            raise RuntimeError(f"Instance {instance_id} failed: {status}")
        port = (inst.get("ports") or {}).get("8000/tcp")
        if status == "running" and port:
            url = f"http://{inst['public_ipaddr'].strip()}:{port[0]['HostPort']}/report.txt"
            try:
                r = requests.get(url, timeout=10)
                if r.ok:
                    open("report.txt", "w").write(r.text)
                    saved = True
            except requests.RequestException:
                pass
        if not saved:
            time.sleep(10)
    if not saved:
        raise RuntimeError("Timed out waiting for report.txt")
finally:
    destroy(instance_id)    # this report is quick to recreate; see the bash example for keeping results
print(open("report.txt").read())
```

This deletes the GPU even if the download failed, which is fine for a report you can recreate. For results that are expensive to rerun, keep the instance on failure, like the bash example does.

### Example: Bash Batch Job

Uploads sample input, runs a GPU job, downloads results and deletes the instance. Job/download failures keep the instance for recovery. Requires `vastai`, `jq`, `python3`, `ssh` and `scp`. Each transfer has a portable 1,800-second Python timeout; no local `timeout` utility is needed.

```bash
#!/usr/bin/env bash
set -euo pipefail

MAX_PRICE=0.60                  # dollars per hour, including the disk
DISK_GB=30
JOB_SECONDS=3600                # the job is stopped after this long
QUERY="gpu_name=RTX_4090 num_gpus=1 reliability>0.98 direct_port_count>=1 dph_total<=$MAX_PRICE"
IMAGE='vastai/pytorch:@vastai-automatic-tag'
LABEL="my-job-$(date +%s)-$RANDOM"   # unique per run, so we can always find what we rented
OPTS=(-o StrictHostKeyChecking=accept-new -o ConnectTimeout=10 -o ServerAliveInterval=30 -o ServerAliveCountMax=4)
mkdir -p inputs && echo "hello" > inputs/example.txt     # sample input: replace with your files

scp_timeout() {
  python3 -c 'import subprocess, sys; subprocess.run(["scp", *sys.argv[1:]], timeout=1800, check=True)' "$@"
}

mine() { vastai show instances --raw | jq -r --arg L "$LABEL" '.[] | select(.label == $L) | .id'; }

# 1. Rent the cheapest offer under MAX_PRICE
ID=""
for OFFER in $(vastai search offers "$QUERY" --storage "$DISK_GB" -o dph_total --limit 5 --raw | jq -r '.[].id'); do
  OUT=$(vastai create instance "$OFFER" --image "$IMAGE" --disk "$DISK_GB" --ssh --direct \
          --cancel-unavail --label "$LABEL" --raw 2>&1) || true
  ID=$(jq -r '.new_contract // empty' <<<"$OUT" 2>/dev/null) || true
  [ -n "$ID" ] && break
  # Vast declined the offer (for example, it was just taken): nothing was rented
  if jq -e '.success == false or ((.status_code // 0) >= 400 and .status_code < 500)' <<<"$OUT" >/dev/null 2>&1; then
    continue
  fi
  # An uncertain create may have succeeded: look before renting again.
  sleep 20
  ID=$(mine | head -n 1)
  [ -n "$ID" ] && break
  echo "Rental result unknown and no instance labeled $LABEL was found." >&2
  echo "Check https://cloud.vast.ai/instances/ before running again." >&2
  exit 1
done
[ -n "$ID" ] || { echo "No offer at or under \$$MAX_PRICE/hour could be rented" >&2; exit 1; }
PRICE=$(vastai show instance "$ID" --raw | jq -r '.dph_total * 1000 | round / 1000')
echo "Rented instance $ID ($LABEL) at \$$PRICE/hour"

# 2. On exit, confirm deletion unless results need recovery
KEEP=0
cleanup() {
  if [ "$KEEP" = 1 ]; then
    echo "Kept instance $ID because its results weren't downloaded. It bills \$$PRICE/hour until you delete it." >&2
    echo "Copy /workspace/outputs off it soon, then run: vastai destroy instance $ID -y" >&2
    return
  fi
  vastai destroy instance "$ID" -y >/dev/null || true
  CHECK=unknown
  for _ in $(seq 12); do
    LIST=$(vastai show instances --raw 2>/dev/null) || LIST=""
    CHECK=unknown
    if jq -e 'type == "array" and all(.[]; type == "object" and (.id | type == "number"))' <<<"$LIST" >/dev/null 2>&1; then
      CHECK=listed
      jq -e --argjson I "$ID" 'any(.[]; .id == $I)' <<<"$LIST" >/dev/null || return 0
    fi
    sleep 5
  done
  echo "Deletion not confirmed for instance $ID (last check: $CHECK). It may still bill. Check https://cloud.vast.ai/instances/" >&2
  exit 1
}
trap cleanup EXIT

# 3. Wait for "running" (up to 15 minutes)
STATUS=""
for _ in $(seq 90); do
  STATUS=$(vastai show instance "$ID" --raw | jq -r '.actual_status')
  [ "$STATUS" = "running" ] && break
  case "$STATUS" in exited|unknown|offline) echo "Instance failed: $STATUS" >&2; exit 1;; esac
  sleep 10
done
[ "$STATUS" = "running" ] || { echo "Timed out waiting for instance" >&2; exit 1; }

# 4. Wait for SSH (up to 18 attempts, then a final check)
read -r HOST PORT < <(vastai show instance "$ID" --raw | jq -r '"\(.ssh_host) \(.ssh_port)"')
for _ in $(seq 18); do ssh "${OPTS[@]}" -p "$PORT" "root@$HOST" true 2>/dev/null && break; sleep 10; done
ssh "${OPTS[@]}" -p "$PORT" "root@$HOST" true || { echo "SSH never came up on instance $ID" >&2; exit 1; }

# 5. Upload, run the job with a time limit, download the results
ssh "${OPTS[@]}" -p "$PORT" "root@$HOST" 'mkdir -p /workspace'    # not every image has /workspace
scp_timeout "${OPTS[@]}" -P "$PORT" -r ./inputs "root@$HOST:/workspace/"
KEEP=1
ssh "${OPTS[@]}" -p "$PORT" "root@$HOST" "timeout $JOB_SECONDS bash -c \
  'cd /workspace && mkdir -p outputs && nvidia-smi > outputs/gpu.txt && cp inputs/* outputs/'"
scp_timeout "${OPTS[@]}" -P "$PORT" -r "root@$HOST:/workspace/outputs" ./
KEEP=0
echo "Results are in ./outputs"
```

- Add `--raw` to CLI commands for JSON output. `vastai COMMAND --help` lists every option.
- Run `vastai show user` successfully once without `--curl` before using `--curl` to inspect a request. On a fresh configuration, role detection otherwise prints its account lookup and exits before reaching your command. After that initialization, `--curl` prints the command request without sending it; redact the API key before sharing the output.
- `dph_total` in search results includes the disk only at the size you pass with `--storage` (default 5 GB). Pass your real disk size. Bandwidth is billed separately.
- With `--raw`, a failed command prints `{"error": true, "status_code": ..., "msg": ...}` to stderr.
- `vastai` exits with code 0 even when the request fails. Check the JSON (`new_contract`, `success`, `error`), not the exit code.
- The CLI and SDK try each request up to 3 times when it times out, can't connect, or gets a 429, 502, 503 or 504 response, waiting as long as the server's `Retry-After` asks (up to 60 seconds). A 429 for the daily search quota is not retried; it resets at midnight UTC. If `create instance` still fails without a clear error, check for an instance with your label before you rent again.
- `vastai execute` runs only `ls`, `rm` and `du`. Use SSH to run anything else.
- The Python SDK's `copy()` does not transfer files to or from your computer. Use `scp`, or call the `vastai copy` CLI.

#### Pod Settings

`N` is the number of GPUs. Runpod sets some limits per GPU; Vast filters on the machine total, so multiply.

| Runpod field | Vast equivalent |
|---|---|
| `imageName` | `--image IMAGE` |
| `name` | `--label NAME` |
| `gpuTypeIds` | `gpu_name=...` in the search query ([GPU names](#gpu-names)) |
| `gpuCount` | `num_gpus=N` in the search query |
| `containerDiskInGb` | `--disk GB`, and the same number in the search's `--storage` so prices include it. It cannot be resized later |
| `volumeInGb`, `volumeMountPath` | A larger `--disk`, or a Vast volume: `--create-volume VOLUME_OFFER_ID --volume-size GB --mount-path /data` |
| `networkVolumeId` | No direct equivalent ([Differences](#differences-from-runpod)) |
| `env` | `--env '-e KEY=value -e OTHER=value'` |
| `ports` | `--env '-p 8000:8000'`. `--ssh` opens port 22 for you |
| `dockerStartCmd` | Without `--ssh`: `--args ...` (must be the last option; SDK `args=[...]`). With `--ssh`: `--onstart-cmd 'COMMANDS'` |
| `dockerEntrypoint` | `--entrypoint COMMAND` (CLI only, without `--ssh` or `--jupyter`) |
| `templateId` | `--template_hash HASH` ([templates](https://cloud.vast.ai/templates/)) |
| `containerRegistryAuthId` | `--login '-u USER -p TOKEN REGISTRY'` |
| `cloudType: "SECURE"` | `datacenter=true` in the search query. This limits results to machines in datacenters. Check host requirements separately; this is not a one-to-one mapping to Runpod Secure Cloud |
| `cloudType: "COMMUNITY"` | The default search |
| `interruptible: true` | Search with `--type bid`, then create with `--bid_price` of at least the offer's `min_bid` |
| `countryCodes`, `dataCenterIds` | `geolocation in [US,CA]` in the search query |
| `allowedCudaVersions` | `cuda_vers>=12.4` in the search query |
| `vcpuCount` | `cpu_cores_effective>=vcpuCount` |
| `minVCPUPerGPU` | `cpu_cores_effective>=` (minVCPUPerGPU × N) |
| `minRAMPerGPU` | `cpu_ram>=` (minRAMPerGPU × N), in GB |
| `minDownloadMbps`, `minUploadMbps` | `inet_down>=...`, `inet_up>=...` |
| `minDiskBandwidthMBps` | `disk_bw>=...` |
| `supportPublicIp` | `direct_port_count>=1` in the search query, and `--direct` when you create |

#### Instance Fields and Status

| Runpod pod field | Vast instance field (`show instance --raw`) |
|---|---|
| `id` (string) | `id` (integer). `create instance` returns it as `new_contract` |
| `desiredStatus` (the state you asked for) | `intended_status` (the state you asked for) |
| Pod is ready | `actual_status` is `running` (the state the machine reports; see below) |
| `publicIp` | `public_ipaddr` |
| `portMappings: {"8000": 41234}` | `ports: {"8000/tcp": [{"HostIp": "...", "HostPort": "41234"}]}` |
| SSH host and port | `ssh_host`, `ssh_port` |
| `costPerHr` | `dph_total` (dollars per hour) |
| `name` | `label` |

Always decide from `actual_status`. `intended_status` only says what was requested.

| `actual_status` | Meaning | What to do |
|---|---|---|
| `null`, `created`, `loading` | Starting up | Keep waiting, with a time limit |
| `running` | Ready. GPU charges apply | Connect |
| `stopped` | Stopped. Storage still bills | Start it or destroy it |
| `exited`, `unknown`, `offline` | Failed. It will not reach `running` | Destroy it and try another offer |

#### Environment Variables Inside the Instance

Vast documents these predefined variables in its [Docker execution environment guide](https://docs.vast.ai/guides/instances/docker-environment). Map the values your application needs rather than assuming Runpod's names also exist on Vast.

| Runpod information | Vast variable |
|---|---|
| `RUNPOD_POD_ID` | `CONTAINER_ID` |
| `RUNPOD_PUBLIC_IP` | `PUBLIC_IPADDR` (captured at startup; query instance metadata for a current address) |
| `RUNPOD_TCP_PORT_22` | `VAST_TCP_PORT_22`; other mapped TCP ports use `VAST_TCP_PORT_X` |
| `RUNPOD_GPU_COUNT` | `GPU_COUNT` |
| CLI access from inside the instance | `CONTAINER_API_KEY`, scoped to that instance; not a replacement for your account key |
| Datacenter or volume ID | No automatic mapping; review placement and storage separately |

Set application variables explicitly, for example `--env '-e MODE=fast'`. In SSH/Jupyter launch modes, variables reach onstart but may be missing from login sessions. The documented onstart workaround is `env | grep _ >> /etc/environment;` for names containing underscores (or `env >> /etc/environment;` for all names). Vast-published images handle this in their entrypoint. Persist only the variables the session needs; do not print credentials to logs.

#### Differences from Runpod

1. **You choose the machine and the price.** Each offer has its own price, reliability, network speed and location. Put a price limit in the search (`dph_total<=...`) and pass your disk size with `--storage` so the price includes it.
2. **Unavailable offers.** An offer can be rented by someone else between your search and your create. Pass `--cancel-unavail` so the create fails right away instead of leaving a stopped instance that bills for storage, then try the next offer.
3. **SSH mode replaces the image's start command.** With `--ssh` or `--jupyter`, put your start command in `--onstart-cmd`. If your image needs its own entrypoint, leave out `--ssh` and use `--args` or `--entrypoint`.
4. **Ports.** Runpod serves HTTP ports at `https://POD_ID-PORT.proxy.runpod.net`. Vast maps each port you open with `-p` to a public port on the machine's IP, over plain HTTP. Read the mapping from `ports` in `show instance --raw` or `VAST_TCP_PORT_X` inside the instance. The [Docker execution environment docs](https://docs.vast.ai/guides/instances/docker-environment#custom-ports) specify a limit of 64 total open ports per instance; the offer must also provide enough directly accessible ports.
5. **Storage.** A Vast volume stays on the machine where it was created, so there is no network-volume equivalent. Keep data you need on any machine in object storage (S3, R2, GCS or Hugging Face), or use `vastai cloud copy`.
6. **Billing.** Storage bills from creation and GPU time while `running`. A stopped instance still bills for storage; only destroying it stops all charges. Each machine sets its own bandwidth price (`inet_up_cost`, `inet_down_cost` in the offer).
7. **Kept instances.** An instance you keep (for example, to recover results after a failed download) runs and bills until you destroy it. It can also end if the machine goes offline or its maximum rental period runs out (`duration` in the offer), so copy results off soon.
8. **Spot instances.** You get a spot instance only when you pass `--bid_price`. If you are outbid, the instance stops (it is not deleted) and storage keeps billing. Change the bid with `vastai change bid ID --price PRICE`.
9. **Images.** Most Runpod images run on Vast unchanged. Runpod pods mount `/workspace` for you; on Vast it exists only if the image creates it, so create it (`mkdir -p /workspace`) before you copy files there. Vast's images (`vastai/pytorch`, `vastai/vllm`, `vastai/comfy`, `vastai/base-image`) start fastest, and the `@vastai-automatic-tag` tag picks the right CUDA build for each machine.


### Instructions for AI Agents

Follow these instructions when you migrate a project from Runpod, or when you rent and manage Vast instances for a user.

#### Rules for Managing Vast for a User

1. **Get approval before spending.** Before creating an instance, show the user the GPU, the hourly price (`dph_total`, searched with `--storage` set to the real disk size), the expected run time and the most it can cost, and wait for a yes. Put the approved price limit in the search (`dph_total<=...`) so a fallback offer can't cost more. Stay within any budget the user gives.
2. **Use the user's account API key and keep it secret.** The user creates a new key at [cloud.vast.ai/manage-keys](https://cloud.vast.ai/manage-keys/); Runpod keys don't work, and `CONTAINER_API_KEY` from inside an instance is not an account key. Read the key from `VAST_API_KEY` or the CLI's saved key. Never print it, log it, or write it into code or commits.
3. **Give every run a unique label** (`--label`), record every instance ID, and report the IDs to the user.
4. **Retry only clear refusals.** Create with `--cancel-unavail`. If Vast declines an offer (`"success": false`, or a 4xx error), try the next offer. If the result is unclear (timeout, 5xx, crash), list instances with your label first, use the instance if it exists, and otherwise stop and tell the user instead of renting again.
5. **Bound every wait.** Polling, the job itself and file transfers all need time limits. Treat `exited`, `unknown` and `offline` as failures. Decide from `actual_status`, never from `intended_status`.
6. **Protect the user's results.** Download results before destroying an instance. If a download fails, keep the instance and tell the user its ID, its hourly price and that it bills until deleted.
7. **Always clean up, then confirm.** Destroy instances when their work is done and results are safe, including after errors. Then confirm each one no longer appears in `vastai show instances --raw`. Stopped instances count: they still bill for storage.
8. **Only destroy instances you created**, unless the user names one.
9. **Use machine-readable output.** Add `--raw` to CLI commands and parse the JSON. Pass `-y` to `vastai destroy instance`.
10. **Run commands over SSH and copy files with `scp`**, not with `vastai execute` or the SDK's `copy()`.
11. **Finish with a report.** Tell the user what ran, on which instance IDs, for how long, what it cost, and that nothing you created is left (or what was kept and why).

#### Procedure for Migrating a Project

Run this from the project root to find every Runpod touchpoint:

```bash
grep -rnE "rest\.runpod\.io|api\.runpod\.io|api\.runpod\.ai|(^|[^[:alnum:]_])runpod([^[:alnum:]_]|$)|runpodctl|RUNPOD_" . \
  --include='*.py' --include='*.ipynb' --include='*.sh' --include='*.js' --include='*.ts' --include='*.go' \
  --include='*.yml' --include='*.yaml' --include='*.toml' --include='*.json' --include='*.md' \
  --include='Dockerfile*' --include='requirements*.txt' --include='.env*'
```

1. **List every match** from the search above and what it does. If the project manages Serverless endpoints or network volumes, tell the user those need separate work ([Scope](#migrating-api-code)).
2. **Choose one interface.** Python: the `VastAI` class. Shell and CI: the `vastai` CLI with `--raw` and `jq`. Other languages: the [REST API](#rest-api).
3. **Replace each call** using the [Reference Tables](#reference-tables). Each Runpod "create pod" becomes a search with a price limit, followed by a create. Base the lifecycle code on the [example migration](#example-migration-before-and-after) and the [bash example](#example-bash-batch-job).
4. **Replace the credential.** Remove `RUNPOD_API_KEY` from code and CI secrets. Read the key from `VAST_API_KEY`, and in `.env.example` write only a placeholder: `VAST_API_KEY=your-vast-api-key`. The user sets the real value.
5. **Move start commands.** `dockerStartCmd` becomes `args` (or `--onstart-cmd` with `--ssh`).
6. **List the gaps.** Note anything without a Vast equivalent (network volumes, Runpod proxy URLs, pod reset) with a workaround from [Differences from Runpod](#differences-from-runpod).
7. **Ask before testing.** Show the user the changes and the test command, with the GPU, hourly price and price limit. After approval, run one end-to-end test on one inexpensive GPU, following the rules above.
8. **Report back:** the files changed, the test result and its cost, the gaps, and confirmation that no test instance is left. The migration is done when no Runpod API calls remain (unless the user chose to keep some), the test passed, its results were saved, and no test instance is left.
