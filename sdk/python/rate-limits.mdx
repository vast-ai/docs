The Vast.ai SDK retries some failed requests. With the default of 3 attempts, those retries finish in under a second and do not read `Retry-After`. For offer search, rent, and listing calls, add your own spacing. See [SLA API automation](/guides/instances/choosing/sla-coverage#api-automation).

This page covers the error format, how rate limits work, and how to configure retry behavior for each client. For the full details on rate limit mechanics, see the [API Rate Limits and Errors](/api-reference/rate-limits-and-errors) page.

## Error Responses

The underlying API error shape is:

```json
{
  "success": false,
  "error": "invalid_args",
  "msg": "Human-readable description of the problem."
}
```

Some endpoints omit `success` or `error` and return only `msg` or `message`.

After its built-in retries are used up, the `VastAI` client raises `requests.HTTPError` for a non-2xx response. Read the status with `err.response.status_code` and the body with `err.response.json()`. `raw=True` only changes successful return values. The serverless client also raises after its retries are used up.

## How Rate Limits Work

Vast.ai applies rate limits **per endpoint**. For an API key, the limit is on that key's account. Extra keys on the same account share it. The client IP is used only when a request does not resolve to an account.

Some endpoints also enforce **method-specific** limits (GET vs POST) and **max-calls-per-period** limits for short bursts.

For the full breakdown, see [How rate limits are applied](/api-reference/rate-limits-and-errors#how-rate-limits-are-applied).

## Rate Limit Response

HTTP 429 comes in two families. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors#rate-limit-response-behavior).

- Legacy rent, show-instances, and `create_asks` calls return plain text and no `Retry-After`.
- Search, charges, earnings, schedule maintenance, and the SLA backtester return JSON. A short limit uses `"error": "HTTPTooManyRequests"` and a `Retry-After` header. A daily search quota hit uses `"error": "search_quota_exceeded"` and a `Retry-After` that can be hours.

The SDK never reads `Retry-After`. With the default of 3 attempts, its retries finish in under a second. If your script calls the API directly, wait at least `Retry-After` when it is present.

## Built-in Retry Behavior

The SDK includes two clients with different retry strategies.

### VastAI Client

The main `VastAI` client retries on HTTP 429, 502, 503, and 504, and on connection errors and timeouts:

- `retry` is the **total number of attempts**.
- **Default:** 3 attempts (one request plus two retries), with delays of about 0.15 s and 0.225 s.
- **Backoff:** starts at 0.15 seconds, multiplied by 1.5 after each attempt. The SDK does not read `Retry-After`.
- To send a request once, use `retry=1`. Do not use `retry=0`. It sends no request.

Any rent can be sent twice if the first request reached the server and the connection then failed. Set a unique `label` and check your instances for it before you rent again. The SDK cannot turn SLA on; SLA rentals use the console or REST. Use the same label check in your own retry logic. See [SLA API automation](/guides/instances/choosing/sla-coverage#api-automation).

```python
from vastai import VastAI

# Default: 3 attempts (2 retries)
vast = VastAI(api_key="your-api-key")
vast.search_offers(query="gpu_name=RTX_4090 rentable=true")
```

### Serverless Client

The serverless client has a broader retry scope, covering transient server errors in addition to rate limits:

- **Retried status codes:** 408 (timeout), 429 (rate limit), and 5xx (server errors)
- **Default retries:** 5
- **Backoff strategy:** exponential with jitter -- `min(2^attempt + random(0, 1), 5.0)` seconds
- **Max delay:** 5 seconds per retry

The jitter (random 0--1 second addition) prevents multiple clients from retrying in lockstep, which reduces the chance of repeated collisions.

<Note>
The serverless client retries on a wider range of errors than the `VastAI` client. Server errors (5xx) and timeouts (408) are retried automatically -- you do not need to handle these yourself.
</Note>

## Configuring Retries

### VastAI Client

Pass the `retry` parameter to the constructor to change the total number of attempts:

```python
from vastai import VastAI

# One attempt only
vast = VastAI(api_key="your-api-key", retry=1)
```

The retry count applies to all requests made through that client instance.

### Serverless Client

The serverless client defaults to 5 retries. The retry count is configured internally per request through the `_make_request()` method's `retries` parameter.

## Reducing Rate Limit Errors

If you are consistently hitting rate limits, the best approach is to reduce the volume and frequency of your requests. See [How to reduce rate limit errors](/api-reference/rate-limits-and-errors#how-to-reduce-rate-limit-errors) for practical strategies including batching, reduced polling, and traffic spreading.

If you need higher limits for production usage, contact support with the endpoint(s), your expected call rate, and your account details.
