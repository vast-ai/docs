Some Vast.ai offers include a **Service Level Agreement (SLA)** — an optional reliability promise on an **on-demand** rental. You pay a small hourly **SLA fee** only after you set a **reliability target** at rent time. If measured uptime falls short of that target, you receive a **service credit**. Search can quote the price; it does not turn the SLA on by itself.

This page explains SLA from the renter side: how to find SLA offers, how pricing works, and when you get credited.

## SLA in plain language

An SLA is an optional reliability promise on an **on-demand** GPU rental. You do not have to use it.

1. The **host** states a **reliability commitment**: how often they expect the machine to be up.
2. **You** choose a **reliability target**: how much uptime you want. A higher target costs more.
3. You pay an **SLA fee** (a service level fee) on top of the GPU price.
4. Each day, Vast checks how long your instance was actually up.
5. If uptime met your reliability target, the host keeps the SLA fee.
6. If uptime missed your reliability target, you receive a **service credit**. That credit can be larger than the SLA fee you paid that day.

A few things people mix up:

- The **reliability score** on an offer card is a separate marketplace signal. It is not your SLA.
- The GPU bill does **not** stop during an outage. SLA pays you back later as a credit, usually after the next UTC midnight.
- A search filter does **not** turn on an SLA. You have to set a reliability target when you rent, in the web console or with the API. The CLI cannot turn SLA on today.
- SLA is only for **on-demand** rentals, not interruptible (spot) or reserved rentals.
- If the price breakdown has **no SLA fee line**, you do not have an SLA. The console may also label that line **SLA charge**. In API responses the same amount is `slaPremiumPerHour`.

Hosts who want the same idea from the listing side can read [SLA in plain language](/host/sla-offers#sla-in-plain-language).

**Console quick start (no API key):**

1. Open [Search](https://cloud.vast.ai/create/) with **On-demand** selected.
2. Set **Reliability target**, confirm an **SLA fee** line, set instance disk on the slider, then **RENT**. Console default disk is 10 GB; if you quoted via CLI/REST, match that disk number or rent can fail with `invalid_price`.
3. Verify under **Instances**; after UTC settlement, check credits in **Account → Billing**.

**If you used the CLI to search:** set **Reliability target** again in the web console before you click **RENT**. CLI filters do not carry over.

Full steps: [In the web console](#in-the-web-console). CLI/API limits for automation are under [API automation](#api-automation).

## What SLA protects

SLA is a **contractual, per-rental** reliability guarantee with automatic daily settlement. It is **not** the same as verification or the **reliability score** on offer cards — those are platform trust signals (see [Machine Tiers](/guides/instances/choosing/find-and-rent#machine-tiers)).

For on-demand contracts with an SLA:

- You are charged for **compute, storage, and the SLA charge** for the rental day, including periods when the instance is unavailable.
- Offline time is tracked as an outage in reliability measurements.
- If you qualify for compensation, a **service credit** posts after daily settlement (UTC) — typically within a few hours after UTC midnight for the prior day — not in the same hour as the outage.

SLA is most useful for **long-running production workloads** where unexpected downtime has a real cost beyond the hourly rate.

## How pricing works

Quoted hourly cost with SLA in search (`dph_total`):

```
dph_total ≈ GPU + storage + SLA charge
```

Bandwidth is billed separately from usage (`inet_*` rates) and is **not** included in `dph_total`.

| Factor | What it means for you |
| --- | --- |
| Your reliability target | Higher target → higher SLA charge |
| Host reliability commitment | Maximum reliability the host advertises on the listing (`expected_reliability`). Higher commitment → lower SLA fee at a given reliability target |
| Host confidence | Host-side pricing setting that affects SLA charge size. **You do not set this** — the host chooses it, and it is **not shown on offer cards**. Compare offers using `dph_total` or the SLA charge line in the price breakdown |

**Rule of thumb:** pick a reliability target **at or below** the host's reliability commitment for the best value. Asking for a 99% reliability target on a host whose reliability commitment is only 95% costs much more than asking for 95% on a host whose reliability commitment is 99%. In search results, the host reliability commitment appears as **expected reliability** on the offer (API: `expected_reliability`) — not the Reliability Score on the card.

### Example: H100 at $3.50/hr GPU

Searching with a **reliability target of 95%** on an offer where the host's **reliability commitment is 99%** with normal confidence:

| Cost component | Approx. rate |
| --- | --- |
| GPU compute | $3.50/hr |
| Storage (at search allocation) | ~$0.01/hr |
| SLA charge | ~$0.008/hr |
| **Total (`dph_total`)** | ~$3.52/hr |

## Finding SLA offers

<Warning>
Search **quotes** SLA pricing. The SLA starts only when you set **Reliability target** at **RENT** (console) or pass `target_reliability` on REST `PUT /api/v0/asks/{id}/`. No SLA fee line in the price breakdown means you do not have an SLA. The CLI cannot enable SLA—see [API automation](#api-automation).
</Warning>

### In the web console

1. Open [Search](https://cloud.vast.ai/create/) and confirm **On-demand** is selected (SLA does not apply to interruptible rentals).
2. In Search filters (left filter bar), set **Reliability target** to your desired reliability target — for example **95%** or **99%**. If you do not set a target, you are not opting into SLA.
3. Optionally narrow results with an SLA-enabled / `has_sla` filter if shown. Filtering listings is **not** the same as enabling the SLA.
4. Before you click **RENT**, confirm the price breakdown shows an **SLA fee** line. No SLA fee line means that rental has no SLA.
5. **Disk before RENT:** Set instance disk on the console slider before **RENT**. If you quoted via CLI or REST, match `allocated_storage` / `disk` to that quote (REST `disk` ≥ 8 when set)—mismatched defaults cause `invalid_price`. See the storage table in [API automation](#api-automation).
6. Rent as usual. Your target is locked at rent time.

<Note>
**Console-only:** You can stop here. SLA rental in the web console does not require CLI or API keys. Continue below only if you automate search or rent.
</Note>

### Search filters

| Filter | Meaning | Example |
| --- | --- | --- |
| `target_reliability` | Your desired reliability level. Also drives SLA charge calculation and ranking. | `target_reliability=0.95` |
| `has_sla` | Restrict to offers with (or without) SLA enabled. | `has_sla=true` |
| `expected_reliability` | Filter by the host's advertised reliability commitment. | `expected_reliability>=0.99` |

<Note>
**API integrators:** `reliability` is the historical machine score, not the host’s reliability commitment. Use `has_sla=true` and/or `expected_reliability` to find SLA listings.
</Note>

**CLI examples:**

```bash
# SLA offers where the host's reliability commitment is at least 99%
vastai search offers 'has_sla=true expected_reliability>=0.99 target_reliability=0.95'

# Compare total cost including SLA charge
vastai search offers 'has_sla=true target_reliability=0.95 num_gpus=1' --order dph_total
```

When you set `target_reliability`, search results include:

| Response field | Meaning |
| --- | --- |
| `search.slaPremiumPerHour` | SLA charge for this offer at your target (API field name) |
| `dph_total` | Total hourly cost **including** the SLA charge |
| `expected_reliability` | Host's reliability commitment |

Hover over the price breakdown on an offer card to see GPU, storage, bandwidth, and the SLA charge separately.

<Note>
When you search with an SLA target, reserved-instance discounts may not apply to the displayed total. Confirm in the console price breakdown. SLA charges are never discounted.
</Note>

### Comparing offers

| Offer | GPU/hr | Host commitment | Your target | SLA charge/hr |
| --- | --- | --- | --- | --- |
| A | $3.50 | 99% | 95% | ~$0.008 |
| B | $3.50 | 95% | 95% | much higher |

Always compare **`dph_total`**, not just GPU price, when SLA matters. Sort by `dph_total` to compare total quoted cost.

**Rent body (SLA):** Send only `target_reliability` when creating a rental. Do not send `sla_r_claim`, `sla_r_target`, or other host listing fields on rent—they are ignored or invalid on create.

**Prerequisites (happy path):** Search with `has_sla` and your storage size, rent with `PUT` and the same `target_reliability`, then confirm the SLA on the instance. Console users can skip this section.

See the [Automation limits](#automation-limits) note in this section before you script search → rent → verify.

For repeated search calls, `POST /api/v0/bundles/` is rate-limited. On HTTP 429, wait and retry. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors).

Renters set **`target_reliability`** on search and on REST rent. Do not send **`sla_r_target`** or **`sla_r_claim`** in the rent body.

**1. Search** (prices `dph_total` at your target — include storage explicitly so quotes are comparable). Set `limit` explicitly when you compare many offers. Bundles search has **no pagination** (no offset or page token)—one response returns at most `limit` rows for that query. OpenAPI does not document a maximum `limit`; do not assume a single call walks the full market. To scan a broader SLA market, shard queries with filters such as `gpu_name`, `geolocation`, or `machine_id`, and back off on HTTP 429. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors).

```bash
curl -s -X POST "https://console.vast.ai/api/v0/bundles/" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "limit": 20,
    "type": "ondemand",
    "verified": {"eq": true},
    "rentable": {"eq": true},
    "allocated_storage": 50,
    "order": [["dph_total", "asc"]],
    "target_reliability": {"eq": 0.95},
    "has_sla": {"eq": true},
    "expected_reliability": {"gte": 0.99}
  }'
```

**2. Rent** the chosen offer. Use `offers[].id` from the search response as `{id}` in `PUT /api/v0/asks/{id}/`. Prefer `id` over `ask_contract_id` when both appear. Never use `bundle_id`. Save `new_contract` from the rent response. Pass the **same** reliability target you searched with:

```bash
curl -s -X PUT "https://console.vast.ai/api/v0/asks/OFFER_ID/" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "image": "pytorch/pytorch:2.1.0-cuda12.1-cudnn8-runtime",
    "disk": 50,
    "target_reliability": 0.95
  }'
```

See [Create Instance](/api-reference/instances/create-instance) and [Search Offers](/api-reference/search/search-offers).

**Rent with a template** (the template supplies the image; still send the same target and enough disk):

```bash
curl -s -X PUT "https://console.vast.ai/api/v0/asks/OFFER_ID/" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "template_hash_id": "YOUR_TEMPLATE_HASH",
    "disk": 50,
    "target_reliability": 0.95
  }'
```

`template_hash_id` is the content hash of a saved template. Include `template_hash_id` to rent from the template. Add `image` only when you want to override the template image. A request needs at least one of those fields. A template rent can send `template_hash_id` alone. Request fields override template defaults. `target_reliability` must match the value you searched with, and `disk` must meet the offer minimum, or rent can fail with `invalid_price`. See [Create Instance](/api-reference/instances/create-instance).

**API key permissions:** create a scoped key with `misc` (search/bundles), `instance_write` (create-instance), and `instance_read` (verify with `GET /api/v1/instances/` or `vastai show instances-v1 --raw`). These three categories are the minimum for search → rent → verify. See [Authentication](/api-reference/authentication) and [Client SLA scoped-key recipe](/api-reference/permissions#client-sla-scoped-key-recipe).

**3. Verify.** Save `new_contract` from the rent response. Look that contract up with URL-encoded `select_filters` (`id` is a filterable column):

```bash
curl -G "https://console.vast.ai/api/v1/instances/" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  --data-urlencode 'select_filters={"id":{"eq":NEW_CONTRACT}}' \
  --data-urlencode "limit=25"
```

Replace `NEW_CONTRACT` with the id from the rent response. Confirm top-level `target_reliability` on that row. For the SLA fee: if the instance is not yet **running**, use `search.slaPremiumPerHour` (search-context pricing); once **running**, also check `instance.slaPremiumPerHour`. A missing `instance.slaPremiumPerHour` before startup is not a failed SLA rent. Requires `instance_read`. You can also read the same fields with `vastai show instances-v1 --raw`. If the filter returns no row, page with `after_token`. Do not use `select_filters` alone to detect an SLA (`has_sla` is not a filterable column).

- **REST** (`GET /api/v1/instances/`): pass an explicit `limit` and page with `after_token` (the response `next_token`). The server default `limit` can be as low as **5** (maximum **25**).
- **CLI** (`vastai show instances-v1`): use `--limit` and `--next-token`. The CLI default `--limit` is **25** unless you set it.

**Billing reconciliation (console):** confirming the SLA does not show service credits. After UTC settlement, open **Account → Billing**. `GET /api/v0/charges/` does not list those credits.

**Automation limitations:** SLA service credits are reconciled in the console (**Account → Billing**). There is no renter API, export, or webhook for those credit line items today. After the UTC day boundary (wait up to about 48 hours if a line is missing), check billing or contact support. Verify an active SLA on instances with `GET /api/v1/instances/` (`target_reliability`, `instance.slaPremiumPerHour`).

| Symptom | Typical response | What to do |
| --- | --- | --- |
| Target on a non-SLA offer | HTTP 400 `invalid_args` | Search with `has_sla=true`; confirm `expected_reliability` |
| Target out of range / invalid | HTTP 400 `invalid_args` | Use `0 < target_reliability < 1`; stay at or below a realistic host reliability commitment |
| Offer not found or not available | HTTP 404 `invalid_args` (`msg` may include `no_such_ask`) | Do not retry that id; search again and rent a current offer |
| Ask cannot start now (`cancel_unavail`) | HTTP 410, error `no_such_ask` | Search for a new offer; this is not a transient glitch to retry on the same id |
| Price mismatch after stale quote | HTTP 400 `invalid_price` | Re-search with the same `target_reliability` and storage (`allocated_storage` / `--storage`), then rent again |
| Too many requests | HTTP 429 | Wait and retry the same rent. The API may return `API requests too frequent` |
| SLA with a bid or interruptible offer | Rent does not turn on an SLA | Search with `"type": "ondemand"`. Do not send `price` or `bid_price` when you want an SLA. |

| Channel | Default storage | Field | Units (label) |
| --- | --- | --- | --- |
| Console | 10 GB | Instance disk size (UI) | GB |
| REST search (`POST /api/v0/bundles/`) | 8 GB | `allocated_storage` | GB |
| CLI (`vastai search offers`) | 5 GiB | `--storage` | GiB |

If you quoted with the CLI (default `--storage` 5), set `--storage` ≥ **8** before REST rent, or match the **same integer** on the console disk slider and REST `"disk"`. Example: `vastai search offers --storage 50` → console slider **50** → `"disk": 50` on `PUT /api/v0/asks/{id}/`.

**Match disk size when comparing prices.** Defaults differ by channel. When you rent with REST after a CLI search, pass the same number you searched with (for example `--storage 50` then `"disk": 50`). REST create-instance `disk` must be ≥ **8** when you pass it. The CLI search default of 5 is below that REST minimum. CLI help labels `--storage` as GiB and REST labels `disk` as GB.

**Quoting rule:** Use the same disk number end-to-end for the channel you rent through (console slider, REST `disk` / `allocated_storage`, or CLI `--storage`). If you mix channels, set disk explicitly on every search and rent step. Treat the same integer as one quote across CLI GiB and REST GB labels unless the API returns a mismatch error (`invalid_price`).

## What happens after you rent

When you rent an SLA-backed offer **with a target set**:

1. **Contract terms lock in** — your reliability target, the host's reliability commitment, and host confidence (how the host priced SLA around their reliability commitment) are fixed for that rental. When comparing offers, use the SLA charge line or `dph_total`. Host confidence is not shown in the client UI and is not a setting you control.
2. **Daily billing** — you pay compute plus the SLA charge each day.
3. **Daily settlement** — Vast measures reliability across multiple timescales and calculates any SLA credit.
4. **Credits appear in billing** — service credits improve your balance; strong days mean you paid the SLA charge with no credit.

### What you pay during an outage

<Warning>
Billing continues during downtime. You are still charged for **compute, storage, and the SLA charge** while the contract exists and the instance is unavailable. Leaving a broken instance running continues those charges until you destroy it.
</Warning>

**Stop vs destroy:** Stopping pauses compute but storage and contract charges can continue. **Destroying the instance** ends future daily charges; final SLA settlement still posts when the contract closes. If you abandon a failed host, destroy only after saving any data you need.

If you qualify for compensation, a **service credit** is applied after daily settlement (UTC), typically within a few hours after UTC midnight for the prior day — not in the same hour as the outage.

### How reliability is measured

Each day, the platform tracks how long your instance was online. Settlement considers **multiple time windows** — from short intervals out to long contract-scale windows — so:

- A single bad hour hurts, but does not always trigger the maximum credit.
- A pattern of unreliable uptime produces larger credits over time.
- One strong day after a weak week does not instantly reset everything.

Scheduled maintenance with adequate advance notice (typically 24+ hours) may be credited toward reliability on a case-by-case basis. Check **Instances** status and any client notifications during downtime to distinguish planned maintenance from an unexpected outage. Credited maintenance is not a separate field on instance webhooks or `GET /api/v0/charges/`. Unplanned outages count fully.

### Credit scenarios (simplified)

Using the H100 example ($84/day compute, ~$0.20/day SLA charge, target 95%, host reliability commitment 99%):

| Scenario | Approx. SLA charge | Approx. service credit | Net vs no SLA (approx.) |
| --- | --- | --- | --- |
| Above target (excellent / good day) | ~$0.20/day | $0 (often) | **−$0.20** (you paid the SLA charge) |
| Near / below target on blended measure (~95%) | ~$0.20/day | ~$42 | **+$41.80** (net credit after SLA charge) |
| Severe shortfall (~90% or less) | ~$0.20/day | ~$84 | **+$83.80** |

**How to read “Net vs no SLA”:** negative = you paid more than without SLA; positive = you received a net credit versus renting the same offer without the SLA.

Production settlement can issue credits even when a single daily snapshot looks close to your target, because measurement uses the blended daily reliability calculation.

<Note>
Production settlement uses the multi-window reliability blend described above, not a single raw daily percentage. Treat these rows as directional, not exact invoice amounts.
</Note>

### Settlement timing

- Settlement runs **once per day** for the previous billing day (UTC).
- Service credits post to your **account balance**. View them under **Account → Billing** in the console. They do **not** appear as `items[].type` on `GET /api/v0/charges/`. Do not use the Charges API or `show charges` to reconcile SLA credits.
- When your contract ends, any remaining unsettled days are resolved at close.

## If your instance goes down

1. Save work and check **Instances** for host/maintenance status.
2. Remember: compute and SLA charges continue until settlement; credits apply to the **previous UTC day**, not the current hour.
3. After settlement, check **Account → Billing** in the console for SLA line items (not `GET /api/v0/charges/`).
4. If credits still look wrong **48 hours** after the outage day, contact support via [Discord](https://discord.gg/hSuEbSQ4X8) or [contact@vast.ai](mailto:contact@vast.ai).

## When SLA is not available

- **Interruptible (bid) rentals** never include SLA, even on SLA-enabled machines. Use on-demand with a reliability target set.
- **Prepaid / reserved-only flows** may reject SLA parameters. Use on-demand rentals for an SLA.
- Offers without SLA (`expected_reliability = 0` / `has_sla=false`) are excluded when you filter with `has_sla=true` or set a positive `target_reliability`.
- If SLA parameters on an offer are invalid for your target, search may flag an SLA pricing error instead of showing a charge.

## FAQ

### Do I need SLA for every rental?

No. For short experiments or fault-tolerant batch jobs, standard on-demand rentals without SLA may be enough. SLA is for workloads where reliability has a real dollar cost.

### Can I change my reliability target mid-rental?

No. The target is fixed when the contract is created. End the instance and rent again with a different search filter if you need a different level.

### Does SLA replace verification?

No. Verification is a platform quality signal (see [Machine Tiers](/guides/instances/choosing/find-and-rent#machine-tiers)). SLA is a financial guarantee on a specific contract.

### Where do I see historical SLA credits?

**Console:** After UTC settlement, open **Account → Billing** and look for **service credit** or SLA credit line items (wording can vary)—not in the instance price panel. Credits are not available via the Charges API, invoices, or billing exports today.

**API:** Prefer **Account → Billing** for service credit reconciliation. Published OpenAPI for `GET /api/v0/charges/` documents charge `type` values `gpu`, `disk`, `bwd`, and `bwu` — not a dedicated SLA settlement type. `GET /api/v1/invoices/` covers payment transactions (top-ups, transfers, payouts), not SLA service-credit line items. Client webhooks for SLA credits are not available. Host-side settlement visibility uses [machine earnings](/api-reference/billing/show-earnings) (`sla_earn`) — that path is for hosts, not renters.
