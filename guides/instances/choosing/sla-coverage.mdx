Some Vast.ai offers include a **Service Level Agreement (SLA)** — an optional reliability promise on an **on-demand** rental. You pay a small hourly **SLA fee** on top of compute only after you set a **reliability target** at rent time. The console shows that fee as the **SLA Fee** line. API fields call it a premium (for example `slaPremiumPerHour`). If measured uptime falls short of your target, you receive a **service credit**, shown as **Service Credit** in Account → Billing. Search can show the price; it does not turn the SLA on by itself.

This page explains SLA from the renter side: how to find SLA offers, how pricing works, and when you get credited.

## SLA in plain language

An SLA is an optional reliability promise on an **on-demand** GPU rental. You do not have to use it.

1. The **host** states a **reliability commitment**: how often they expect the machine to be up.
2. **You** choose a **reliability target**: how much uptime you want. A higher target costs more.
3. You pay an **SLA fee** (a service level fee) on top of the GPU price.
4. Each day, Vast checks how long your instance was actually up.
5. If the blended measure met your reliability target, the host keeps the SLA fee. "Met" uses Vast's blended reliability measure (recent and longer-term uptime), not that day's raw uptime alone. A day whose raw uptime is at or slightly above your target can still produce a partial credit if the blended measure falls below it.
6. If the blended measure fell below your reliability target, you receive a **service credit**. That credit can be larger than the SLA fee you paid that day.

A few things people mix up:

- The **reliability score** on an offer card is a separate marketplace signal. It is not your SLA.
- The GPU bill does **not** stop during an outage. SLA pays you back later as a credit, usually after the next UTC midnight.
- A search filter does **not** turn on an SLA. You have to set a reliability target when you rent, in the web console or with the API. The CLI cannot turn SLA on today.
- SLA is only for **on-demand** rentals, not interruptible (spot) or reserved rentals.
- If the price breakdown has **no SLA Fee line**, you do not have an SLA. In **Account → Billing** the same charge appears as **SLA Fee**, and credits as **Service Credit**. In API responses the hourly amount is `slaPremiumPerHour`.

Hosts who want the same idea from the listing side can read [SLA in plain language](/host/sla-offers#sla-in-plain-language).

## What SLA protects

SLA is a **contractual, per-rental** reliability guarantee with automatic daily settlement. It is **not** the same as verification or the **reliability score** on offer cards — those are platform trust signals (see [Machine Tiers](/guides/instances/choosing/find-and-rent#machine-tiers)).

For on-demand contracts with an SLA:

- You are charged for **compute, storage, and the SLA fee** for the rental day, including periods when the instance is unavailable.
- Offline time is tracked as an outage in reliability measurements.
- If you qualify for compensation, a **service credit** posts after daily settlement (UTC) — typically within a few hours after UTC midnight for the prior day — not in the same hour as the outage.

SLA is most useful for **long-running production workloads** where unexpected downtime has a real cost beyond the hourly rate.

## How pricing works

Quoted hourly cost with SLA in search (`dph_total`):

```
dph_total ≈ GPU + storage + SLA fee
```

Bandwidth is billed separately from usage (`inet_*` rates) and is **not** included in `dph_total`.

| Factor | What it means for you |
| --- | --- |
| Your reliability target | Higher target → higher SLA fee |
| Host reliability commitment | Maximum reliability the host advertises on the listing (`expected_reliability`). Higher commitment → lower SLA fee at a given reliability target |
| Host confidence | Host-side pricing setting that affects SLA fee size. **You do not set this** — the host chooses it, and it is **not shown on offer cards**. Compare offers using `dph_total` or the SLA fee line in the price breakdown |

**Rule of thumb:** your reliability target must be **at or below** the host's reliability commitment. Offers whose commitment is below your target are not shown in search and cannot be rented. At the same target, a host with a higher commitment charges a lower SLA fee. In search results, the host reliability commitment appears as **expected reliability** on the offer (API: `expected_reliability`) — not the Reliability Score on the card.

### Example: H100 at $3.50/hr GPU

Searching with a **reliability target of 95%** on an offer where the host's **reliability commitment is 99%** with normal confidence:

| Cost component | Approx. rate |
| --- | --- |
| GPU compute | $3.50/hr |
| Storage (at search allocation) | ~$0.01/hr |
| SLA fee | ~$0.008/hr |
| **Total (`dph_total`)** | ~$3.52/hr |

## Finding SLA offers

<Warning>
Search **quotes** SLA pricing. The SLA starts only when you set **Reliability target** in the console **Search filters** (left bar) before **RENT**, or pass `target_reliability` on REST `PUT /api/v0/asks/{id}/`. No SLA fee line in the price breakdown means you do not have an SLA. The CLI cannot enable SLA—see [API automation](#api-automation).
</Warning>

### In the web console

1. Open [Search](https://cloud.vast.ai/create/) and confirm **On-demand** is selected (SLA does not apply to interruptible rentals).
2. In Search filters (left filter bar), set **Reliability target** to your desired reliability target — for example **95%** or **99%**. If you do not set a target, you are not opting into SLA.
3. Optionally narrow results with an SLA-enabled / `has_sla` filter if shown. Filtering listings is **not** the same as enabling the SLA.
4. Before you click **RENT**, confirm the price breakdown shows an **SLA Fee** line. No SLA Fee line means that rental has no SLA.
5. **Disk before RENT:** Set instance disk on the console slider before **RENT**. If you are comparing against a CLI or REST quote, use the same disk size so the prices match.
6. Rent as usual. Your target is locked at rent time.

<Note>
**Console-only:** You can stop here. SLA rental in the web console does not require CLI or API keys. Continue below only if you automate search or rent.
</Note>

### Search filters (console and programmatic search)

Console controls use the same concepts; they do not accept CLI query strings. Use the left **Search filters** bar for console rentals. The **Example (CLI / API)** column is for `vastai search offers` and REST only.

| Filter | Meaning | Example (CLI / API) |
| --- | --- | --- |
| `target_reliability` | Your desired reliability level. Also drives SLA fee calculation and ranking. REST and console only (see the Warning below). | REST: `"target_reliability": 0.95` (plain number, not `{"eq": …}`) |
| `has_sla` | Restrict to offers with (or without) SLA enabled. | `has_sla=true` |
| `expected_reliability` | Filter by the host's advertised reliability commitment. | `expected_reliability>=0.99` |

<Note>
**API integrators:** `reliability` is the historical machine score, not the host’s reliability commitment. Use `has_sla=true` and/or `expected_reliability` to find SLA listings.
</Note>

**CLI examples:**

<Warning>
The current CLI cannot quote an SLA fee: it sends `target_reliability=0.95` as `{"eq": 0.95}`, which search rejects with `400 target_reliability: Input should be a valid number`. Use the CLI to find SLA offers (`has_sla`, `expected_reliability`), then get the SLA-inclusive `dph_total` from the console or REST (`"target_reliability": 0.95` as a plain number).
</Warning>

```bash
# SLA offers where the host's reliability commitment is at least 99%
# Set --storage to match the disk you will rent (console often 10; REST often 8+)
vastai search offers 'has_sla=true expected_reliability>=0.99' --storage 10
```

When you set `target_reliability`, search results include:

| Response field | Meaning |
| --- | --- |
| `search.slaPremiumPerHour` | SLA fee for this offer at your target (API field name) |
| `dph_total` | Total hourly cost **including** the SLA fee |
| `expected_reliability` | Host's reliability commitment |

Hover over the price breakdown on an offer card to see GPU, storage, bandwidth, and the SLA fee separately.

<Note>
When you search with an SLA target, reserved-instance discounts may not apply to the displayed total. Confirm in the console price breakdown. SLA fees are never discounted.
</Note>

Web app: [cloud.vast.ai](https://cloud.vast.ai). REST examples use `https://console.vast.ai/api/…`.

For repeated search calls, `POST /api/v0/bundles/` is rate-limited. On HTTP 429, wait and retry. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors).

**1. Search** (prices `dph_total` at your target — include storage explicitly so quotes are comparable). Set `limit` explicitly when you compare many offers. Bundles search has **no pagination** (no offset or page token)—one response returns at most `limit` rows for that query. OpenAPI does not document a maximum `limit`; do not assume a single call walks the full market. To scan a broader SLA market, shard queries with filters such as `gpu_name`, `geolocation`, or `machine_id`, and back off on HTTP 429. See [Rate Limits and Errors](/api-reference/rate-limits-and-errors).

```bash
curl -s -X POST "https://console.vast.ai/api/v0/bundles/" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "limit": 20,
    "type": "ondemand",
    "verified": {"eq": true},
    "rentable": {"eq": true},
    "external": {"eq": false},
    "allocated_storage": 50,
    "order": [["dph_total", "asc"]],
    "target_reliability": 0.95,
    "has_sla": {"eq": true},
    "expected_reliability": {"gte": 0.99}
  }'
```

The CLI default query sends `external=false rentable=true verified=true rented=false` (the `--help` text omits `rented`; see [search offers](/cli/reference/search-offers)). The body above matches the first three filters, and REST `POST /api/v0/bundles/` may default omitted `rented` to `{"eq": false}` per [Search Offers OpenAPI](/api-reference/search/search-offers). Pass `rented` explicitly when you need different behavior.

**2. Rent** the chosen offer. Use `offers[].id` from the search response as `{id}` in `PUT /api/v0/asks/{id}/`. Prefer `id` over `ask_contract_id` when both appear. Never use `bundle_id`. Save `new_contract` from the rent response. Pass the **same** reliability target you searched with:

```bash
curl -s -X PUT "https://console.vast.ai/api/v0/asks/OFFER_ID/" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "image": "pytorch/pytorch:2.1.0-cuda12.1-cudnn8-runtime",
    "disk": 50,
    "target_reliability": 0.95
  }'
```

On-demand REST rent with default `cancel_unavail` may return **HTTP 410** if the offer cannot start immediately. Re-search and pick a new ask—do not backoff-retry the same id (see the error table below).

See [Create Instance](/api-reference/instances/create-instance) and [Search Offers](/api-reference/search/search-offers).

**Rent with a template** (the template supplies the image; still send the same target and enough disk):

A request needs at least one of those fields. A template rent can send `template_hash_id` alone. Request fields override template defaults. `target_reliability` must match the value you searched with, and `disk` must meet the offer minimum, or rent can fail with `invalid_price`. See [Create Instance](/api-reference/instances/create-instance).

**API key permissions:** create a scoped key with `misc` (search/bundles), `instance_write` (create-instance), and `instance_read` (verify with `GET /api/v1/instances/` or `vastai show instances-v1 --raw`). These three categories are the minimum for search → rent → verify. See [Authentication](/api-reference/authentication) and [Renter SLA scoped-key recipe](/api-reference/permissions#renter-sla-scoped-key-recipe).

**3. Verify.** Save `new_contract` from the rent response. Look that contract up with URL-encoded `select_filters` (`id` is a filterable column):

```bash
curl -G "https://console.vast.ai/api/v1/instances/" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  --data-urlencode 'select_filters={"id":{"eq":NEW_CONTRACT}}' \
  --data-urlencode "limit=25"
```

Replace `NEW_CONTRACT` with the id from the rent response. Confirm top-level `target_reliability` on that row. For the SLA fee: if the instance is not yet **running**, use `search.slaPremiumPerHour` (search-context pricing); once **running**, also check `instance.slaPremiumPerHour`. A missing `instance.slaPremiumPerHour` before startup is not a failed SLA rent. Requires `instance_read`. You can also read the same fields with `vastai show instances-v1 --raw`. If the filter returns no row, confirm you used `new_contract` (not the offer id), then retry after a short delay, no more than about once per second (`show_instances` `x-rate-limit` threshold `1.0`). Use `after_token` paging only when listing without an `id` filter. Do not use `select_filters` alone to detect an SLA (`has_sla` is not a filterable column).

- **REST** (`GET /api/v1/instances/`): pass an explicit `limit` and page with `after_token` (the response `next_token`). The server default `limit` can be as low as **5** (maximum **25**).
- **CLI** (`vastai show instances-v1`): use `--limit` and `--next-token`. The CLI default `--limit` is **25** unless you set it.

**Billing reconciliation (console):** Verifying the SLA on an instance (for example via `GET /api/v1/instances/`) does not show service credits. After UTC settlement, open **Account → Billing**. `GET /api/v0/charges/` does not list those credits.

**Automation limitations:** SLA service credits are reconciled in the console (**Account → Billing**). There is no renter API, export, or webhook for those credit line items today. After the UTC day boundary (wait up to about 48 hours if a line is missing), check billing or contact support. Verify an active SLA on instances with `GET /api/v1/instances/`. Confirm `target_reliability > 0`. A present but zero value means the rental has no SLA. Also check `instance.slaPremiumPerHour`. Show-instances uses OpenAPI threshold `1.0` (about one request per second).

## What happens after you rent

When you rent an SLA-backed offer **with a target set**:

1. **Contract terms lock in** — your reliability target, the host's reliability commitment, and host confidence (how the host priced SLA around their reliability commitment) are fixed for that rental. When comparing offers, use the SLA fee line or `dph_total`. Host confidence is not shown in the web console and is not a setting you control.
2. **Daily billing** — you pay compute plus the SLA fee each day.
3. **Daily settlement** — Vast measures reliability across multiple timescales and calculates any SLA credit.
4. **Credits appear in billing** — service credits improve your balance; strong days mean you paid the SLA fee with no credit.

### What you pay during an outage

<Warning>
Billing continues during downtime. You are still charged for **compute, storage, and the SLA fee** while the contract exists and the instance is unavailable. Leaving a broken instance running continues those charges until you destroy it.
</Warning>

**Stop vs destroy:** Stopping pauses compute but storage and contract charges can continue. **Destroying the instance** ends future daily charges; final SLA settlement still posts when the contract closes. If you abandon a failed host, destroy only after saving any data you need.

If you qualify for compensation, a **service credit** is applied after daily settlement (UTC), typically within a few hours after UTC midnight for the prior day — not in the same hour as the outage.

### How reliability is measured

Each day, the platform tracks how long your instance was online. Settlement considers **multiple time windows** — from short intervals out to long contract-scale windows — so:

- A single bad hour hurts, but does not always trigger the maximum credit.
- A pattern of unreliable uptime produces larger credits over time.
- One strong day after a weak week does not instantly reset everything.

When a host schedules maintenance in advance, part of that downtime is counted as uptime for the host. More of the window is forgiven the earlier they give notice, and less is forgiven the longer the window lasts. Forgiven downtime does not earn you a service credit. Check **Instances** status and any notifications to distinguish planned maintenance from an unexpected outage. Unplanned outages count fully.

### Credit scenarios (simplified)

Using the H100 example ($84/day compute, ~$0.20/day SLA fee, target 95%, host reliability commitment 99%):

| Scenario | Approx. SLA fee | Approx. service credit | Net vs no SLA (approx.) |
| --- | --- | --- | --- |
| Above target (excellent / good day) | ~$0.20/day | $0 | **−$0.20** (you paid the SLA fee) |
| Below target (~93–94% for the day) | ~$0.20/day | ~$42 | **+$41.80** (net credit after SLA fee) |
| Severe shortfall (~90% or less) | ~$0.20/day | ~$84 | **+$83.80** |

**How to read “Net vs no SLA”:** negative = you paid more than without SLA; positive = you received a net credit versus renting the same offer without the SLA. Credits grow with the size of the shortfall. In this example, a day 1–2 points below target pays a meaningful share of that day's compute, not a token amount. Figures are illustrative. A day that meets the target does not pay a credit.

Production settlement can issue credits even when a single daily snapshot looks close to your target, because measurement uses the blended daily reliability calculation.

<Note>
Production settlement uses the multi-window reliability blend described above, not a single raw daily percentage. Treat these rows as directional, not exact invoice amounts.
</Note>

### Settlement timing

- Settlement runs **once per day** for the previous billing day (UTC).
- Service credits post to your **account balance**. View them under **Account → Billing** in the console. They do **not** appear as `items[].type` on `GET /api/v0/charges/`. Do not use the Charges API or `vastai show invoices-v1 --charges` to reconcile SLA credits.
- When your contract ends, any remaining unsettled days are resolved at close.

## If your instance goes down

1. Save work and check **Instances** for host/maintenance status.
2. Remember: compute, storage, and SLA fees continue until you destroy the instance. Credits are calculated at the next UTC settlement and apply to the **previous UTC day**, not the current hour.
3. **Console:** Open **Instances**, select the instance, then **Destroy** to stop future charges. Stopping alone may not end billing for a broken instance—see [Stop vs destroy](#what-you-pay-during-an-outage). Destroy permanently deletes the instance and its disk, so copy off anything you need first.
4. After settlement, check **Account → Billing** in the console for SLA line items (not `GET /api/v0/charges/`).
5. If credits still look wrong **48 hours** after the outage day, contact support via [Discord](https://discord.gg/hSuEbSQ4X8) or [contact@vast.ai](mailto:contact@vast.ai).

## Viewing SLA on active instances

### In the web console (active instances)

1. Open **Instances** and select your running instance.
2. Open **price details** (or the instance billing panel) and confirm an **SLA Fee** line is present.
3. If the UI shows your **reliability target**, confirm it matches what you selected at search time. If you do not see a target or SLA fee, you likely rented without the SLA.

### API integrators

Console users: open **Instances** → select your instance → **price details** to confirm the SLA fee and target. Skip the block below if you do not use the API.

<Warning>
**Common mistake:** `vastai show instances` (v0) and `GET /api/v0/instances/{id}/` do not return SLA fields. Verify with `GET /api/v1/instances/` or `vastai show instances-v1 --raw`. Enabling SLA still requires console or REST — see [Finding SLA offers](#finding-sla-offers).
</Warning>

<details>
<summary>API integrators: field names and filters</summary>

**Rent body (SLA):** Among SLA-related fields, send only `target_reliability`. Host listing fields (`sla_r_claim`, `sla_r_target`) are read-only on the contract. Still send `image` or `template_hash_id` and matching `disk`.

Show-instances output may include `target_reliability` and price fields under `search` / `instance` (including `slaPremiumPerHour`).

To find instances with an SLA, post-process the API response in your application (filter or paginate locally)—not in the Vast web console. Prefer filtering the show-instances response (`target_reliability > 0`, `instance.slaPremiumPerHour`) in production. OpenAPI documents optional `select_filters` on stored fields such as `sla_r_target` / `target_reliability` when present; computed fields (for example `has_sla`) are not filterable. Do not rely on `select_filters` alone to detect an SLA.

**You set at search/rent**

| Concept | Search / bundles | After rent (`GET /api/v1/instances/`) |
| --- | --- | --- |
| Your reliability target | `target_reliability` (quote only until rent) | `target_reliability` |
| SLA fee rate | `search.slaPremiumPerHour` | `instance.slaPremiumPerHour` |

**Host-locked on contract (read-only)**

| Concept | Search / bundles | After rent (`GET /api/v1/instances/`) |
| --- | --- | --- |
| Host reliability commitment | `expected_reliability` | `sla_r_claim` |

Host ask field `sla_r_claim` on listings is host-side; on active rentals the locked reliability commitment appears as `sla_r_claim` in show-instances. Host confidence is **not shown on offer cards** — compare offers using `dph_total` or the SLA fee line. Confirm field names against a live `--raw` response before building parsers.

## When SLA is not available

- **Interruptible (bid) rentals** never include SLA, even on SLA-enabled machines. Use on-demand with a reliability target set.
- **Prepaid / reserved-only flows** may reject SLA parameters. Use on-demand rentals for an SLA.
- Offers without SLA (`expected_reliability = 0` / `has_sla=false`) are excluded when you filter with `has_sla=true` or set a positive `target_reliability`.
- If SLA parameters on an offer are invalid for your target, search may flag an SLA pricing error instead of showing a charge.

## FAQ

### Do I need SLA for every rental?

No. For short experiments or fault-tolerant batch jobs, standard on-demand rentals without SLA may be enough. SLA is for workloads where reliability has a real dollar cost.

### Can I change my reliability target mid-rental?

No. The target is fixed when the contract is created. **Destroy** the instance (this deletes its disk; the same machine may not be available again) and rent again with a different **Reliability target**.

### Does SLA replace verification?

No. Verification is a platform quality signal (see [Machine Tiers](/guides/instances/choosing/find-and-rent#machine-tiers)). SLA is a financial guarantee on a specific contract.

### Where do I see historical SLA credits?

**Console:** After UTC settlement, open **Account → Billing** and look for **service credit** or SLA credit line items (wording can vary)—not in the instance price panel. Credits are not available via the Charges API, invoices, or billing exports today.

**API integrators:** Prefer **Account → Billing** for service credit reconciliation. There is no renter API for SLA credits. Published OpenAPI for `GET /api/v0/charges/` documents charge `type` values `gpu`, `disk`, `bwd`, and `bwu` — not a dedicated SLA settlement type. `GET /api/v1/invoices/` covers payment transactions (top-ups, transfers, payouts), not SLA service-credit line items. Client webhooks for SLA credits are not available. Host-side settlement visibility uses [machine earnings](/api-reference/billing/show-earnings) (`sla_earn`) — that path is for hosts, not renters.
